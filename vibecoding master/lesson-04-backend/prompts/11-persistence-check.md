# Lesson 4 — Промт 11: смоук сервиса (auth, валидации, сохранение, файлы)

> **Цель:** убедиться, что сервис работает как таковой — регистрация/логин проходят, формы валидируют ввод, а на КАЖДОМ экране данные реально пишутся в базу и переживают перезагрузку. Ловит баг «в интерфейсе сделал — а оно не сработало/не сохранилось» (мок чтения заменили, а мутацию не подключили; забыт `await`; форма не шлёт запрос; ошибка молча проглочена; нет валидации). После проверки тестовые данные удаляются.

## Главное правило

Проверяй **после жёсткой перезагрузки страницы или прямым запросом к базе**, а не по экрану сразу после сохранения. Оптимистичный UI показывает запись, даже если запись в базу провалилась — именно так баг и прячется.

## Промт

```
Прогони смоук сервиса через Playwright MCP (headed) против <боевой URL>.
Сейчас этап сборки, реальных пользователей нет — создавать и удалять тестовые записи безопасно.

ШАГ 1 — Составь чек-лист ПО СПЕКЕ.
Пройди ../../product/docs/spec.md (разделы «Экраны», «Данные», «Автоматика», «Доступы») — и
../../product/docs/screens/* с ../../product/docs/01-app-map.md, если уже есть. Выпиши:
  - auth-флоу: регистрация, логин, выход, защита приватных страниц;
  - по КАЖДОМУ экрану: действия (кнопки, формы, тоглы, смена статуса, привязки),
    что при каждом должно сохраняться/меняться в базе, переходы и состояния;
  - правила валидации форм: какие поля обязательные, где проверяется формат
    (email и т.п.), какой текст ошибки по спеке.
Это чек-лист — проверяем не «абстрактный CRUD», а ровно ту логику из спеки. Покажи его.

ШАГ 2 — Аутентификация (без неё сервиса нет).
  - Регистрация нового аккаунта (email с маркером, напр. __smoke__ab12cd@example.com).
  - Если включено подтверждение email — пройди флоу подтверждения.
  - Выход и повторный логин этим аккаунтом — успешно.
  - Вход с НЕВЕРНЫМ паролем — отклоняется с понятной ошибкой, внутрь не пускает.
  - Открытие приватной страницы без логина — редирект/блок по спеке.
Любой провал — это БАГ, почини.

ШАГ 3 — Пройди КАЖДЫЙ экран по чек-листу (под залогиненным __smoke__-пользователем).
Для каждой формы/действия:
  a. ВАЛИДАЦИЯ (негативные случаи): отправь форму с пустым обязательным полем и с
     кривым email — должна показаться ошибка из спеки, и запись НЕ должна сохраниться.
     Если невалидные данные «проходят» или сохраняются — это БАГ.
  b. ДЕЙСТВИЕ: выполни валидный сценарий в UI (создай/измени/сохрани). В создаваемые
     записи в уникальное поле впиши маркер "__smoke__ab12cd".
  c. PERSIST (ключевой шаг): ЖЁСТКО перезагрузи страницу (полный reload, не SPA-переход)
     и убедись, что результат соответствует спеке И реально записан в базу (Prisma:
     строка/изменение есть, привязано к userId этого пользователя — изоляция из Шага 7).
     Проверяй по перезагрузке/в базе, НЕ по экрану сразу после действия.
  d. Если после перезагрузки результата нет или поведение расходится со спекой — БАГ.
     Найди причину и почини:
       - мок чтения заменён на Prisma, а мутация (create/update/delete/toggle) — нет;
       - форма не вызывает API (onSubmit ничего не шлёт);
       - забыт await / промис не дождались;
       - ошибка сохранения проглочена try/catch без обработки;
       - неверный userId / RLS / валидация молча отклоняет.
  e. Пройди весь жизненный цикл сущности по спеке: создать → прочитать → изменить →
     сменить статус/тогл (если есть) → удалить — каждое с перезагрузкой и проверкой в базе.
  f. Зафиксируй по экрану: валидация / create / read / update / delete — ✅ или ❌.
Расхождения «спека ↔ реальность» чини, пока экран не сойдётся со своей спекой.

ШАГ 4 — Очистка. Удали ВСЕ записи с маркером __smoke__ (и тестового пользователя
с его данными) — прямым запросом к базе или через UI. Фильтруй строго по __smoke__,
чтобы не задеть seed/боевые данные. Покажи, что после очистки __smoke__-записей нет.

ШАГ 5 — Отчёт. Таблица по экранам (auth / валидации / C-R-U-D / persist) + список
экранов из spec.md, которые НЕ удалось проверить (пропуски покрытия — разобрать
вручную). Любой ❌ — почини и прогони заново, пока всё не зелёное. Сохрани в
../../product/docs/audits/persistence-check-<YYYY-MM-DD>.md.
```

## Почему это ловит «создал — не сохранилось»

Баг живёт в разрыве «форма → мутация → запись в базу». Шаг 4 урока переписывает на Prisma прежде всего функции **чтения** (`getOrders` и т.п.); мутации create/update/delete легко остаются недоделанными или возвращают оптимистичный результат без записи. Перезагрузка сразу после создания показывает правду: если запись исчезла — путь сохранения оборван. Проверка по экрану без перезагрузки этот баг не видит.

## После проверки

- Все CRUD-экраны зелёные, тестовые `__smoke__`-данные вычищены.
- Пропуски покрытия (экраны из spec без проверки) — в отчёте, разобрать вручную.
- Что именно должно сохраняться — стоит закрепить в `../../product/docs/spec.md` / тест-кейсах: это войдёт в полный прогон `/ux-testing` в Уроке 7.
