# Безопасность auth — хеширование, cookie, rate limit, защита от user-enumeration

> **Цель:** базовый набор защит auth включён. Типичные атаки на формы (перебор пароля, перехват cookie, прощупывание email) не проходят.

---

## Промт

```
Auth — самая атакуемая часть сервиса. 90% атак — типовые. Базовый набор должен
быть включён сразу, не "потом".

ПРОВЕРЬ И НАСТРОЙ:

1. Хеширование паролей.

   better-auth по умолчанию использует scrypt или bcrypt — проверь в auth.ts.
   В БД должно быть только hashed_password, никогда password в открытом виде.
   Прогон по таблице User в Prisma Studio: password column не должно быть, только
   hashedPassword.

2. Cookie настройки.

   В auth.ts:
   - HttpOnly: true (default в better-auth)
   - Secure: true (на проде — обязательно; на localhost при разработке — false)
   - SameSite: 'lax'
   - Path: '/'

   Проверь в DevTools (Application → Cookies) после логина — все три флага должны
   быть установлены.

3. Rate limiting на /api/auth/*.

   На этапе деплоя в middleware.ts уже есть жёсткий лимит 5/min на /api/auth/*.
   Дополни: лимит 3/час на регистрацию (`/api/auth/sign-up`):

     if (path.startsWith('/api/auth/sign-up')) {
       if (!rateLimit(`signup:${ip}`, 3, 60 * 60 * 1000)) {
         return new NextResponse('Too many signups', { status: 429 })
       }
     }

4. Защита от user-enumeration.

   Атакующий пытается узнать "есть ли email X в системе". Если на login
   с неверным email и с неверным паролем — разные сообщения, или разное время
   отклика, утечка есть.

   Правила:
   - Сообщение об ошибке логина — одинаковое для обоих случаев:
     "Неверный email или пароль"
   - Время ответа примерно одинаковое (better-auth обычно делает фиктивный bcrypt
     для несуществующих email, чтобы маскировать timing attack — проверь)
   - На регистрации с уже существующим email:
     • Вариант A: всегда возвращаем "успех", фактически не создаём, отправляем
       email на этот адрес "на вашу почту попытались зарегистрироваться, если
       это были не вы — игнорируйте"
     • Вариант B: возвращаем generic-ошибку без указания "email уже занят"

   Это противоречит UX (пользователь хочет знать "email уже занят"). Решение —
   "Forgot password"-flow, где если email есть — отправим инструкцию, если нет —
   тоже якобы отправим (чтобы не утечь). Если в нашем продукте безопасность
   важна — выберем вариант A. Если простой UX — вариант B.

   Спроси у меня: "Какой вариант предпочитаешь? A (security) или B (UX)?"
   Default — B для простоты.

5. CSRF.

   better-auth и NextAuth включают CSRF-защиту по умолчанию через состояние
   (state cookie + проверка). Не выключай.

6. Проверка пароля.

   - Минимум 8 символов (better-auth — minPasswordLength)
   - Опционально: проверка через haveibeenpwned.com (zxcvbn для оценки силы)
     По умолчанию пропустим. Минимум 8 символов.

7. Тестовый прогон:

   1) 6 неудачных попыток входа подряд → последний 429 "Too many requests"
   2) Регистрация с уже существующим email → одинаковое поведение (по выбранному
      варианту A или B)
   3) Кука после логина в DevTools:
      - HttpOnly ✓
      - Secure ✓ (на проде)
      - SameSite=Lax ✓
   4) Запрос curl к защищённому /api/<protected> без сессии → 401
   5) Попытка SQL injection в email при логине: email='admin@test.com'
      OR '1'='1' — должна возвращать обычную ошибку (Prisma экранирует параметры)

8. Создай ../../product/docs/rules/auth-security.md с кратким чек-листом для будущих фич:

# Auth Security — что проверять при добавлении auth-фич

- Все API-routes /api/auth/* проходят через rate limiting
- При логине — единое сообщение для неверного email/пароля
- При регистрации — выбран и реализован вариант A или B защиты от user-enumeration
- Cookie: HttpOnly + Secure (prod) + SameSite=Lax
- CSRF: встроенная защита auth-библиотеки не выключена
- Пароль: минимум 8 символов, всегда хешируется bcrypt/scrypt
- IDOR: каждая операция на ресурсом пользователя проверяет userId

ПОКАЖИ МНЕ:
- Содержимое ../../product/docs/rules/auth-security.md
- Результаты тестов выше (по пунктам 7.1-7.5)
```

## Edge cases

- Если на проде нет HTTPS (что не должно быть — настроено на этапе деплоя) — Secure cookie не выставится. Проверь, что NEXTAUTH_URL начинается с https
- Если используется `localhost` (а не `127.0.0.1`) — cookie на localhost работает по-разному в разных браузерах. Тест на проде — финальный
- haveibeenpwned-check (k-anonymity) — полезен, но по умолчанию можно пропустить. Если хочешь — добавь через `@have-i-been-pwned/passwords` пакет
