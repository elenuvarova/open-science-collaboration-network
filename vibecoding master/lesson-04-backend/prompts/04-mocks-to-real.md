# Замена моков на реальные Prisma-вызовы (UI не переписывается)

> **Цель:** в `entities/<entity>/api/<entity>-api.ts` лежат реальные функции на Prisma вместо моков. UI не трогается — сигнатуры идентичны (заложены на этапе прототипа). И сразу закладываем производительность (loading.tsx, стриминг, лёгкие запросы), чтобы на реальных данных страницы не «висели».

---

## Промт

```
0. СТРАХОВКА АВТО-КОММИТОВ (как в Уроке 3 — на случай если пропущен или версия старая).
   Проверь: есть ли ../../product/docs/rules/commits.md И строка-триггер на него в ../../product/AGENTS.md.
   - ЕСТЬ — ничего не меняй, оставь работающее правило как есть, переходи к п.1.
   - НЕТ — заведи сейчас ../../product/docs/rules/commits.md (создай docs/rules/, если нужно):
       # Commits — авто-коммит после каждого логического шага
       Завершил шаг (фича/фикс/доработка/документ) → СРАЗУ commit, не дожидаясь команды.
       Атомарно (одна фича = один коммит), без `git add -A` вслепую (добавляй файлы шага).
       Формат сообщения: `проект (тип): описание` — `проект` = имя продукта; `тип` = feat/fix/refactor/docs/chore.
       Док-я/спека/тесты — в том же коммите, что код. Push: есть remote → push после коммита;
       если push завязан на автодеплой (push → прод) — сначала спроси.
     И добавь в ../../product/AGENTS.md строку-триггер (только ссылку, не содержимое):
       | Завершил шаг (фича/фикс/доработка) → коммит | `docs/rules/commits.md` |
   Дальше по этому промту каждую переведённую сущность коммить отдельным коммитом в формате
   `проект (тип): описание` (напр. `myapp (feat): user-api на Prisma вместо мока`).

Затем основная работа:

В каждой ../../product/src/entities/<entity>/api/:

1. Переименуй mock-<entity>.ts → <entity>-api.ts

2. Замени тело функций — вместо in-memory массива вызовы Prisma через @/shared/db

3. СИГНАТУРЫ оставь идентичными (get<Entity>ById, list<Entities>, create, update, delete)

Пример замены (на этапе прототипа мы заложили правильные сигнатуры как раз для этого момента):

  // Было (mock-user.ts):
  let items: User[] = [...]
  export async function getUserById(id: string): Promise<User | null> {
    await delay()
    return items.find(i => i.id === id) ?? null
  }

  // Стало (user-api.ts):
  import { db } from '@/shared/db'
  import type { User } from '../model/types'

  export async function getUserById(id: string): Promise<User | null> {
    return db.user.findUnique({ where: { id } })
  }

Параметры list (search, limit, offset, userId) перейдут в where / take / skip Prisma:

  export async function listEntities(params?: {
    search?: string
    limit?: number
    offset?: number
    userId?: string
  }) {
    return db.entity.findMany({
      where: {
        ...(params?.userId && { userId: params.userId }),
        ...(params?.search && {
          OR: [
            { name: { contains: params.search, mode: 'insensitive' } },
            { description: { contains: params.search, mode: 'insensitive' } },
          ],
        }),
      },
      take: params?.limit,
      skip: params?.offset,
      orderBy: { createdAt: 'desc' },
    })
  }

После замены всех файлов:

1. Проверь, что во всех вызовах из UI (страницы, фичи, виджеты) импорт идёт через
   index.ts слайса entities/<entity>:
   ✅ import { listProducts } from '@/entities/product'
   🔴 import { listProducts } from '@/entities/api/product-api'

   Если что-то прямо импортит api/<entity>-api.ts — переделай через index.ts.

2. Прогон проверок:
   - npx tsc --noEmit (типы должны совпадать благодаря Prisma-генерации)
   - grep -r "mock-" ../../product/src/entities (должно быть пусто после переименования)
   - Проверка на моки ВНЕ слоя entities (данные, легшие мимо FSD-конвенции):
       grep -rniE "mock|fixture|dummy|placeholder|hardcod|заглушк" ../../product/src \
         --include=*.ts --include=*.tsx | grep -v "src/entities/"
     Плюс глазами пробегись по ../../product/src/widgets, ../../product/src/features, ../../product/src/app на инлайновые
     массивы-данные (const items = [ { ... }, ... ] прямо в компоненте). Любой
     такой источник данных, который должен жить в БД, — перенеси в
     entities/<entity>/api/ и подключи к Prisma. Статику (тексты, конфиг,
     навигацию, дизайн-токены) НЕ трогай — она законно остаётся в коде.
   - npm run dev → прокликай страницы → данные должны браться из БД

3. Если что-то ломается — Claude чинит, но НЕ ПЕРЕПИСЫВАЕТ UI. Если UI пришлось
   менять — значит сигнатура мока на этапе прототипа была не та. Зафиксируй это как
   F-001 (finding) и адаптируй.

ПРОИЗВОДИТЕЛЬНОСТЬ — сделай сразу, иначе на реальных данных страницы «висят» и
данные появляются долго. Это часть этой же задачи, не отдельный шаг:

1. loading.tsx на каждый роут с данными. Рядом с page.tsx в app/-сегментах добавь
   loading.tsx со скелетоном, повторяющим каркас страницы (карточки / строки
   таблицы — из компонентов UI-кита). Next.js показывает его МГНОВЕННО при переходе,
   пока грузятся данные, вместо «висящей» пустой страницы.

2. Стриминг через Suspense. Не блокируй весь экран одним await на всё. Каркас (шапка,
   меню) рендерится сразу, а блок с данными оберни в <Suspense fallback={<Skeleton/>}>
   — он подтянется отдельно. Медленные секции — каждую в свой Suspense.

2.1. Постоянная обвязка не должна тормозить навигацию. Меню/шапка живут в
   ../../product/src/app/(app)/layout.tsx (заложено в Уроке 2) — этот layout переживает переходы и
   не перемонтируется. Не вешай на него тяжёлый общий await (например, загрузку всего
   меню/счётчиков синхронно) — иначе каждый переход будет ждать этот запрос. Данные
   для самой обвязки (профиль, счётчик уведомлений) либо бери из лёгкого закэшированного
   запроса, либо подгружай внутри своего <Suspense>, чтобы контент страницы не ждал
   обвязку, а обвязка — контент. Переходы между страницами при этом остаются мягкими
   (через <Link>), грузится только динамический контент текущей страницы.

3. Лёгкие запросы (в entities/<entity>/api/):
   - select только нужные поля (не тащи всю строку ради 3 колонок);
   - пагинация: take с лимитом по умолчанию (напр. 20) + skip, не findMany без лимита;
   - связи точечно через select/include, без N+1 (не делай запрос в цикле по списку);
   - независимые запросы на странице — параллельно через Promise.all, не один за другим.

4. Индексы под частые where/orderBy (userId, status, createdAt и т.п.) — `@@index`
   в ../../product/prisma/schema.prisma + миграция.

5. Картинки — через next/image (ленивая загрузка, нужные размеры), не голый <img>.

6. Кэш тяжёлых чтений — ОСТОРОЖНО. Прямые вызовы Prisma в App Router не кэшируются:
   каждый заход = запрос в БД. Часто читаемые и РЕДКО меняющиеся данные (каталог,
   публичные страницы, агрегаты для дашборда/счётчиков) оберни в `unstable_cache`
   с `revalidate` и тегами, и ОБЯЗАТЕЛЬНО инвалидируй на запись —
   `revalidatePath('/...')` / `revalidateTag('...')` после create/update/delete.
   ⚠️ Данные, которые пользователь сам только что создал/изменил, агрессивно НЕ кэшируй:
   иначе свежее не покажется после перезагрузки (это поймает смоук Шага 10). Правило:
   кэш — для общих/редко меняющихся данных, не для личных мутабельных списков.

7. Меньше клиентского JS (если ещё не заложено в Уроке 2): страницы — серверные
   компоненты по умолчанию, `"use client"` только на интерактивных кусках; тяжёлые
   клиентские виджеты (графики, редакторы, карты) — через `next/dynamic`. Это про
   скорость загрузки самой страницы, не только данных.

- Список новых файлов в ../../product/src/entities/*/api/

  данные подтягиваются секциями; в Network страница не ждёт один большой запрос целиком
```

## Edge cases

- Если в моках были поля, которых нет в ../../product/prisma/schema.prisma — добавить их в schema (миграция) или удалить из моков
- Prisma возвращает `Date` объекты для timestamp. Если UI ожидал строки — JSON.stringify их превратит, в JSX `Date` рендерится как строка через `.toLocaleDateString()`
- Если `delay()` был критичен для UI (без него loading-state не виден) — добавь искусственную задержку только для dev (`process.env.NODE_ENV === 'development'`)
