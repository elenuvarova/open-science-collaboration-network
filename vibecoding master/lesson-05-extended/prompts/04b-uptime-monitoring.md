# Uptime-мониторинг — узнать о падении раньше пользователей

## Когда делать

Опционально, когда сервис уже на проде (Урок 3) и хочется узнавать о падении самим, а не от недовольных пользователей. Не привязано к `spec.md` — нужно любому публичному сервису.

## Как это работает

Мониторинг **должен быть независим от приложения**. Если упал контейнер или весь сервер — функция `notify()` / `sendTelegramAlert` из этого же приложения тоже не работает и алерт не уйдёт. Поэтому проверку делает либо внешний сервис, либо отдельный cron на сервере, который дёргает канал напрямую (curl), а не через код приложения.

Канал для алерта берём тот, что **уже настроен**: Telegram-бот (Шаг 4, он как раз для оповещений владельцу) или email-провайдер (из Урока 4, если email подключали). Новых токенов «из ниоткуда» не заводим. Если ни того, ни другого нет — берём внешний сервис с email-уведомлением.

## Вариант A — внешний сервис (проще, без своего кода)

UptimeRobot (free tier, 50 мониторов) или Better Stack: регистрируешь URL `https://<domain>`, проверка каждые 5 минут, при падении приходит email (а в UptimeRobot — опционально и Telegram, если подключить бота в их интерфейсе). Ничего не крутится на твоём сервере, секретов нет.

Это рекомендуемый вариант для большинства проектов. Промт ниже — если хочется держать мониторинг у себя.

## Вариант Б — cron на сервере

На сервер подключаешься сам по SSH (доступ из `.env.deploy`, как в Уроке 3), я ничего не ввожу в терминал.

```
Подними uptime-мониторинг на сервере. Канал для алерта — тот, что уже настроен
в проекте (Telegram-бот из Шага 4 или email-провайдер из Урока 4). Спроси меня, какой
использовать, если настроены оба.

ЕСЛИ канал — Telegram (бот уже поднят в Шаге 4, TELEGRAM_BOT_TOKEN и белый
список TELEGRAM_ALERT_CHAT_IDS уже лежат в .env.production на сервере):
  Переиспользуй этот же токен и тот же белый список — новых переменных не
  заводи. Токен — секрет (в чат я его не отправляю, в скрипт не хардкодим);
  скрипт читает токен и список chat_id из .env.production и шлёт алерт КАЖДОМУ
  получателю из TELEGRAM_ALERT_CHAT_IDS (через запятую).

ЕСЛИ канал — email (провайдер уже настроен в Уроке 4, доступы в .env.production):
  Алерт шлём через того же провайдера (Resend API / SMTP) тем же curl, читая
  доступы из .env.production. Адрес получателя добавь плейсхолдером
  MONITOR_EMAIL= и скажи мне вписать.

Дальше:

1. На сервере создай /usr/local/bin/uptime-check.sh. Скрипт читает доступы из
   .env.production (НЕ хардкодит их), пингует сайт и при недоступности шлёт
   алерт по выбранному каналу:

   #!/usr/bin/env bash
   set -euo pipefail
   set -a; source /var/www/<project-name>/.env.production; set +a
   curl -fsS -m 10 https://<domain> >/dev/null && exit 0
   # сайт не ответил — шлём алерт каждому из белого списка (пример для Telegram):
   IFS=',' read -ra CHAT_IDS <<< "${TELEGRAM_ALERT_CHAT_IDS}"
   for CHAT_ID in "${CHAT_IDS[@]}"; do
     curl -s "https://api.telegram.org/bot${TELEGRAM_BOT_TOKEN}/sendMessage" \
       -d "chat_id=$(echo "$CHAT_ID" | xargs)" \
       -d "text=🔴 <project-name> down: $(date)" >/dev/null
   done

   chmod +x /usr/local/bin/uptime-check.sh
   chmod 600 /var/www/<project-name>/.env.production

2. Поставь cron каждые 5 минут (на сервере):
   */5 * * * * /usr/local/bin/uptime-check.sh

3. ПОКАЖИ МНЕ тест: останови web-контейнер на 5 минут — должен прийти алерт
   по выбранному каналу. После теста подними контейнер обратно.
```
