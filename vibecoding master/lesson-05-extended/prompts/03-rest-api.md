# REST API + API-ключи

Цель: дать наружу управляемый доступ к данным продукта по HTTP — чтобы их можно было подключить к другим сервисам.

> **Сначала разбор, потом код.** REST API наружу — сложный кусок (ключи, scopes, отзыв доступа, фильтрация по владельцу). Прежде чем писать код, разбери фичу со мной: какие интеграции из `spec.md` реально нужны, что им можно читать/писать, нужны ли они вообще. В Claude Code это делает скилл `/new-feature` (интервью → бриф → реализация); если скилла нет (Codex/Cursor/другой AI) — задай мне уточняющие вопросы по `spec.md` и покажи план, и только после согласования реализуй.

## Зачем это вообще (и зачем API-ключ)

Сайт ходит в базу «изнутри» по сессии пользователя. Но иногда данные нужны **снаружи приложения**:

- **Интеграции и автоматизация** — Zapier / Make / n8n: «появился новый заказ → создай строку в Google Sheets / отправь в CRM».
- **Свои выгрузки и аналитика** — забрать заказы в BI-дашборд, экспорт, отчёты.
- **Мобильное приложение или второй фронтенд** — ходит к тому же бэкенду.
- **Вебхуки и сторонние сервисы** — что-то дёргает ваш API по расписанию.

У всех этих «клиентов» нет вашей сессии-куки и логина. Им нужен другой способ доказать «мне можно» — это и есть **API-ключ**: длинная секретная строка, которую вы выдаёте конкретной интеграции. Ключ отвечает на «кто стучится» (Zapier? мобилка?) и «что ему разрешено» (только читать заказы? писать посты?). Если ключ утёк или интеграция больше не нужна — вы его отзываете, не трогая остальные.

**Если наружу отдавать нечего — этот шаг можно пропустить.** Нужен он, когда в `spec.md` есть интеграции/мобилка/выгрузки.

## Шаг 1 — Модель ключа

```prisma
model ApiKey {
  id        String   @id @default(uuid())
  userId    String                // чей ключ
  keyHash   String   @unique       // в базе храним ХЭШ ключа, не сам ключ
  name      String                 // зачем он: "Zapier", "Мобилка", "Экспорт в BI"
  scopes    String[]               // что можно: ['read:orders', 'write:posts']
  lastUsed  DateTime?
  expiresAt DateTime?
  createdAt DateTime @default(now())
}
```

Сам ключ показываем пользователю **один раз** при создании (потом — только хэш). Выдача/отзыв ключа — из админки (`/admin`), каждое действие в лог (`apikey.create` / `apikey.revoke`).

## Шаг 2 — Endpoints `/api/v1/*`

```
GET    /api/v1/<entity>        — список (пагинация)
GET    /api/v1/<entity>/:id    — один
POST   /api/v1/<entity>        — создать
PATCH  /api/v1/<entity>/:id    — обновить
DELETE /api/v1/<entity>/:id    — удалить
```

Версия в пути (`v1`), чтобы позже менять API, не ломая старые интеграции.

## Шаг 3 — Аутентификация по ключу

Middleware на `/api/v1/*`: читает `Authorization: Bearer <key>`, хэширует, ищет в `ApiKey`, проверяет `scope` под операцию (например, `DELETE` требует `write:`), пишет `lastUsed`. Нет ключа / не тот scope / истёк → `401`/`403`. Данные всё так же фильтруются по владельцу (`userId` ключа), как в Уроке 4 — ключ не должен видеть чужое.

## Шаг 4 — Rate limit (строже, чем у людей)

На ключ: 100 req/min, 1000 req/day (числа под свой случай). Превышение → `429` + заголовок `Retry-After`. Защита от того, что кривая интеграция «застучит» ваш сервер.

## Шаг 5 — Документация

`../../product/docs/api.md`: для каждого endpoint — метод, путь, нужный scope, query-параметры, пример `curl`, формат ответа. Без доков интеграцией никто не воспользуется.

```markdown
## GET /api/v1/orders
Список заказов (пагинация). Авторизация: Bearer-ключ со scope `read:orders`.
Параметры: page (1), limit (20, max 100), status (опц).
Ответ: { "data": [...], "pagination": { "page": 1, "total": 150 } }
```

## Примеры сценариев (по желанию — покажи мне 1-2 под мой случай)

Если хочется не просто «поднять API», а сразу увидеть, как им пользоваться, предложи на выбор конкретный сценарий и проведи по нему:

- **n8n у себя (self-hosted, бесплатно).** n8n — визуальный конструктор автоматизаций. Поднимается контейнером рядом с приложением:
  `docker run -d --name n8n -p 5678:5678 -v n8n_data:/home/node/.n8n n8nio/n8n` (или сервисом в docker-compose, за nginx с паролем). Внутри: нода **HTTP Request** с заголовком `Authorization: Bearer <ваш-ключ>` дёргает `GET /api/v1/<entity>` → дальше ноды «отправь в Telegram / запиши в Google Sheets / создай задачу». Получается «забрать данные из моего продукта и куда-то отправить» без кода.
- **Zapier / Make (облако, без своего сервера).** То же, но не самохостинг: триггер по расписанию → HTTP-запрос к вашему API с ключом → действие в другом сервисе.
- **Выгрузка в таблицу/BI.** Скрипт/Apps Script по ключу тянет `GET /api/v1/<entity>?limit=100` и пишет в Google Sheets / собирает отчёт.
- **Обратная сторона (вебхук ОТ вас).** Если внешнему сервису нужно узнавать о событиях сразу — не он опрашивает ваш API, а вы при событии шлёте POST на его URL. Это уже не про ключ к вам, а про исходящий вызов; упомяни как отдельный вариант, если в `spec.md` есть такая интеграция.

Покажи на одном примере полный путь: выдал ключ в админке → настроил n8n (или curl) → данные пришли → отозвал ключ, доступ пропал.

## После реализации

1. Выдай тестовый ключ из админки, покажи запрос:
   `curl -H "Authorization: Bearer <key>" https://<domain>/api/v1/orders`
2. Покажи, что без ключа / с чужим scope — 401/403, а превышение лимита — 429.
3. Отзови ключ из админки → тот же запрос перестаёт работать.
4. Зафиксируй в `spec.md` раздел «API» и ADR (зачем REST, какие scopes).
