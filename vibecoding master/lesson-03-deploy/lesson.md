```
Собери одну HTML-страницу what-is-deploy.html, которая простыми словами и наглядно объясняет, что такое деплой: как код с моего компьютера оказывается доступен в браузере у любого человека в мире, что такое сервер, IP и домен, что значит «компиляция / сборка» в момент деплоя. ## Шаг 0. Плагины Claude Code (опционально)
```

**Результат шага:** при желании Claude Code расширен парой плагинов, которые делают этот и следующие уроки удобнее и безопаснее.

**Нужны ли они?** Нет — это не обязательное условие. Курс полностью проходится без них (в Codex их вообще нет, роль закрывают промты в `prompts/` и правила `AGENTS.md`). Это удобство и фоновая безопасность, а не то, без чего ничего не соберётся. Если уже что-то ставили или пропустили — ничего страшного.



### Еще раз о том, что такое плагин Claude code

Плагин Claude Code – это готовый набор инструментов в одном пакете (хуки, скиллы, команды). Anthropic и сообщество выкладывают их в специальных «магазинах» (маркетплейсах). Поставили один раз – и плагин работает во всех проектах на этом компьютере (если при установке выбрать **user scope**).

Что нужно знать: внутри Claude Code есть **slash-команды**. Пишете `/что-то`, жмёте Enter. Работают они только внутри сессии Claude Code, в обычном терминале zsh их нет.


### Какие плагины ставим и зачем

| Плагин | Что делает | Когда пригодится |
|---|---|---|
| `security-guidance` | Фоновое security-ревью каждого diff'а и коммита (находит IDOR, auth bypass, injection, то что grep не видит) | Шаги 2, 6, 8 этого урока + везде дальше |
| `github` | `/gh` команды прямо из чата: создать PR, посмотреть issues, прочитать комментарии | Шаг 1 (работа с GitHub) и далее |
| `commit-commands` | `/commit`, `/commit-push-pr`: атомарные коммиты с автогенерацией сообщения | Каждый раз когда сохраняете работу |
| `context7` | Актуальная документация любой библиотеки прямо в контексте (Next.js, Prisma, Docker, nginx, certbot, без устаревших обучающих данных) | Шаги 4, 5 (docker, nginx, SSL) |
| `superpowers` | Workflow-навыки для Claude: планирует задачу до кода, дебажит по гипотезам, верифицирует результат перед завершением. Подключается сам — не нужно помнить команду | Любая сессия: перед новой фичей, при отладке, перед завершением крупного блока |
| `playwright` | Проверки фронта, E2E-тесты через MCP: Claude может открыть браузер, кликнуть, проверить |
| `figma` (если работаете с дизайном) | Точные значения и скриншоты из Figma | Любой UI-урок если есть макеты |


### Как ставить

Два способа: проще всего попросить самого Claude (он поставит всё в текущей сессии — работает и в расширении VS Code, и в CLI), либо ввести команды вручную в терминале.

**Способ 1 — попросить Claude (команды печатать не нужно).** Прямо в сессии напишите:

```
Поставь официальный маркетплейс Anthropic и плагины security-guidance, github, commit-commands, context7, playwright, superpowers (scope user). Используй CLI: claude plugin marketplace add anthropics/claude-plugins-official, затем claude plugin install <name>@claude-plugins-official --scope user на каждый плагин. В конце напомни мне набрать /reload-skills.
```

Claude выполнит установку командами `claude plugin ...` в терминале — вы только подтвердите их запуск. Потом **один раз** наберите `/reload-skills`, чтобы плагины активировались в текущей сессии (или просто перезапустите Claude Code). Тонкость: сам `claude plugin install` Claude запускает за вас, а вот slash-команды `/plugin` и `/reload-skills` он печатать не может — это пользовательский ввод, поэтому `/reload-skills` в конце набираете вы.

**Способ 2 — вручную, командами `claude plugin` в терминале.** Откройте терминал (в VS Code: Terminal → New Terminal) и выполните:

```bash
claude plugin marketplace add anthropics/claude-plugins-official
claude plugin install superpowers@claude-plugins-official --scope user
claude plugin install security-guidance@claude-plugins-official --scope user
claude plugin install github@claude-plugins-official --scope user
claude plugin install commit-commands@claude-plugins-official --scope user
claude plugin install context7@claude-plugins-official --scope user
claude plugin install playwright@claude-plugins-official --scope user
```

`--scope user` ставит плагин для всех проектов на компьютере (рекомендуется); `--scope project` — только для текущего.

> **Видите `/plugin isn't available in this environment`?** Это нормально. Слэш-команда `/plugin` есть только в Claude Code CLI (терминал) — в чате расширения VS Code и в облаке её нет. Поэтому ставьте через **Способ 1** (Claude сам прогонит установку) или командами `claude plugin ...` из терминала выше — они работают везде. Слэшем (`/plugin marketplace add ...`, `/plugin install ...`) можно только если вы запустили Claude Code в терминале.

После установки активируйте плагины: наберите `/reload-skills` (если команда доступна), либо обновите окно VS Code (Cmd+Shift+P → `Developer: Reload Window`), либо перезапустите Claude Code.

## Шаг 1. Git и GitHub

**Результат шага:** код прототипа из Урока 2 лежит в репозитории GitHub.


### Задание 1. Git: как это работает

Git – это история всех изменений в коде. Каждое сохранение (коммит) – отдельная запись в журнале: что поменялось, когда и кто это сделал. В любой момент можно вернуться к прошлой версии, посмотреть, что в ней было, или попробовать новую идею отдельно от основной работы (в своей «ветке»). Без git правки наслаиваются друг на друга, и непонятно, когда что сломалось и кто что менял.

Прежде чем грузить прототип на сервер, разберём общую картину. Но не стеной текста в чате, а наглядной HTML-страницей со схемами — как делали `web-intro.html` (Урок 1) и `architecture-intro.html` (Урок 2). Промт соберёт `git-intro.html`: чем git отличается от GitHub и GitLab, как выглядят ветки, что такое commit / push / pull / diff / откат на примерах «было → стало», и как идёт работа с веткой main, параллельными ветками и merge.

```
Выполни `prompts/01-git-concepts.md` — собери наглядную HTML-страницу `git-intro.html`: git vs GitHub vs GitLab (почему это разные понятия и как связаны), ветки визуально (граф коммитов), commit / push / pull / diff / откат с примерами «было → стало», работа с main + параллельные ветки + merge (и зачем так делать). Со схемами и аналогией, открой в браузере и покажи.
```

**Результат:** появится `git-intro.html` — наглядная страница про git: видно отличие git / GitHub / GitLab, как выглядят ветки и merge, что делают commit / push / pull / diff / откат. Открывается двойным кликом. Проект ещё не трогаем — это разбор перед практикой, дальше в Задании 2 делаем первый push.


### Задание 2. Создаём репозиторий и пушим код

GitHub – это онлайн-хранилище для git-репозиториев. На вашем компьютере git хранит историю изменений локально, а GitHub держит копию в облаке. Так можно зайти с другого компьютера, поделиться кодом или прямо отсюда выложить его на сервер. Под каждый проект заводится отдельный репозиторий (private видите только вы и те, кого пригласите; public открыт всем).

Чтобы локальный git мог отправлять код на GitHub, нужно подтвердить, что это правда вы (аутентификация). Есть 4 способа: `gh` CLI (самый простой), SSH-ключ (классика, через `~/.ssh/id_ed25519`), PAT (personal access token, токен прямо в адресе), логин с паролем (устарел).

**Как безопаснее — коротко.** Рекомендуем **SSH-ключ (`ed25519`)**: приватная половина ключа никогда не покидает ваш компьютер, в адресе репозитория ничего не светится, GitHub видит только публичную половину. По желанию ключ защищается ещё и passphrase. Если хочется без возни — **`gh` CLI**: он сам заведёт доступ и хранит токен безопасно (тоже нормальный вариант). А вот **PAT прямо в адресе и пароль не используем**: токен легко утекает в логи и историю команд, а пароль GitHub уже отключил. Главное правило для любого варианта — приватный ключ под `chmod 600`, права на `~/.ssh` под `700`, и никогда не коммитить ключи в репозиторий.

Заодно на этом шаге AI сразу проговорит **карту доступов** на весь урок — по принципу минимальных прав: ваша машина управляет GitHub (создать репо, push) через выбранный способ входа; сервер позже получит доступ к репо только на чтение через отдельный read-only deploy key (не ваш личный ключ); а вход на сам сервер — по SSH-ключу из `.env.deploy`. Так каждой стороне выдаётся ровно столько прав, сколько нужно, и «связать git с сервером» получается безопасно.

Сейчас инициализируем git в проекте (в Уроке 2 его намеренно не было — приложение создавалось с `--disable-git`), поставим pre-commit хук **«спека-гейт»** (не даёт закоммитить код без обновления спеки), выберем способ входа на GitHub, проверим безопасность ключей и сделаем первый коммит и push в свой private-репозиторий. Заодно в `.gitignore` сразу добавим папку `lessons/` (материалы и модули курса), чтобы они не попадали в репозиторий продукта.

**С этого момента включается правило коммитов.** Раз git появился — заводим `../../product/docs/rules/commits.md`: каждый завершённый функционал (фича / багфикс / законченная доработка) → **коммит сразу, автоматически, не дожидаясь команды**; атомарно (одна фича = один коммит), без `git add -A` вслепую. Дальше AI коммитит сам после каждого шага. Политику **push** (пушить каждый коммит или только проверенное) привяжем к режиму деплоя на следующем шаге — выборе стратегии.

**Вход:** локальный код приложения из Урока 2 (git ещё не инициализирован), `.gitignore` от create-next-app.
**Выход:** git инициализирован в `../../product/`, настроен pre-commit хук спека-гейта (`../../product/scripts/hooks/pre-commit`), правило `../../product/docs/rules/commits.md` (авто-коммит после шага) + строка-триггер в `AGENTS.md`, private-репозиторий на GitHub с кодом, настроенная аутентификация (gh CLI или SSH-ключ).

```
Запусти `prompts/02-git-github.md` — разбери со мной варианты аутентификации (gh CLI / SSH-ключ / PAT / логин-пароль), настрой выбранный, инициализируй git в `../../product/` (git init), поставь pre-commit хук спека-гейта, создай private-репо на GitHub, прогони проверки безопасности ключей (chmod 600, права `~/.ssh`), сделай первый коммит и push. По ходу объясни принцип атомарных коммитов. И заведи правило `../../product/docs/rules/commits.md` (+ триггер «коммит» в `AGENTS.md`): завершил функционал → коммить сразу, автоматически, атомарно, без `git add -A` вслепую, формат сообщения `проект (тип): описание` (тип = feat/fix/refactor/docs/chore) — push-политику под режим деплоя допишем на шаге выбора стратегии.
```

**Результат:** в `../../product/` инициализирован git, настроен pre-commit хук спека-гейта, заведено правило `commits.md` (AI коммитит каждый завершённый шаг сам), настроен способ входа на GitHub (gh CLI или SSH-ключ), создан private-репо, проверена безопасность ключей (chmod 600, права на ~/.ssh), сделан первый коммит и push. Открыв github.com, увидите свой репозиторий с кодом. Файлы `.env`, `node_modules/` и папка `lessons/` (материалы курса) в коммит не попали – их не пустил `.gitignore`.

## Шаг 2. .env и секреты

**Результат шага:** все секреты (API-ключи, токены, пароли БД) живут в `.env`, не в коде.


### Задание 3. Настраиваем .env

Секреты – это любые данные, которые не должны стать публичными: API-ключи (OpenAI, Stripe), пароли от баз данных, JWT-секреты, токены доступа. Если они попадут в код и уйдут в git-историю, вычистить их оттуда тяжело. Даже если переписать историю, копии останутся у всех, кто уже скачал репозиторий. Сейчас настроим эту изоляцию. В `.gitignore` добавим `.env` и `.env.*` (с исключением `!.env.example` – это шаблон без настоящих значений, его как раз коммитить нужно). Создадим `.env.local` для ваших локальных секретов с правами 600 (читать может только владелец). И прогоним поиск по коду (grep) – вдруг вы или AI случайно вписали ключ прямо в файл.

**Вход:** существующий `.gitignore` и код проекта.
**Выход:** обновлённый `.gitignore`, новые `.env.local` (chmod 600) и `.env.example` с заглушками.

```
`prompts/03-env-secrets.md`: добавь в `.gitignore` `.env` и `.env.*` с исключением `!.env.example`, создай `.env.local` (chmod 600) и `.env.example` с заглушками будущих переменных, прогони grep по коду на хардкод секретов и проверь git-историю что `.env` раньше не закоммичен. На выходе `git status` чист.
```

**Результат:** в `.gitignore` появятся `.env` и `.env.*` с исключением `!.env.example`. Локально создан `.env.local` с правами 600 и `.env.example` с заглушками будущих переменных. Поиск секретов в коде ничего не нашёл, проверка истории git тоже чистая – `.env` раньше не коммитили. `git status` больше не показывает `.env` среди отслеживаемых файлов.

> **Карта env-файлов проекта — запомните, больше их быть не должно.** К концу Урока 3 у вас ровно **четыре** `.env`-файла (`.env.deploy` и `.env.production` добавятся ниже, при настройке сервера). У каждого своя роль, и они не дублируют друг друга:
>
> | Файл | Что внутри | В git? | Где |
> |---|---|---|---|
> | `.env.example` | шаблон: имена переменных с пустыми значениями | **да** | в репо |
> | `.env.local` | все ваши **локальные** секреты (ключи; в Уроке 4 — `DATABASE_URL` для команд с вашей машины) | нет | на ноуте |
> | `.env.production` | **боевые** секреты | нет | на сервере |
> | `.env.deploy` | доступ к серверу для деплой-скрипта (IP, SSH) | нет | на ноуте |
>
> Правило: **один секрет — одна строка в одном файле.** Локальные секреты держим только в `.env.local`, голый `.env` отдельно не заводим. Если AI создал что-то сверх этих четырёх (`.env`, `.env.production.db` и подобное) — это лишнее: перенесите значения в нужный файл и удалите дубль.


### Задание 3.1 (опционально). Бэкап `.env` и передача проекта

## Шаг 3. Деплой-стратегия

**Результат шага:** выбран и зафиксирован подход к деплою.


### Задание 4. Выбор стратегии

Деплой – это когда вы выкладываете свой код в интернет так, чтобы пользователи могли открыть его в браузере. Способов много, и они сильно различаются по сложности, цене и контролю. Можно через AI заливать код на свой сервер руками. Можно настроить так, чтобы push автоматически запускал деплой. А можно взять готовую платформу вроде Vercel / Railway / Render: нажал кнопку – задеплоилось. У каждого свои плюсы и минусы: контроль или удобство, цена или способность держать нагрузку, быстрый старт или привязка к одному поставщику.

Главный выбор сводится к двум вариантам — готовая платформа (Vercel и подобные) или свой сервер (наш ручной деплой на VPS). Коротко:

| | Vercel (и Railway / Render) | Наш ручной деплой (VPS + Docker) |
|---|---|---|
| Запуск | нажал кнопку, подключил репозиторий — быстрее | по шагам, чуть дольше, но с полным контролем |
| Скорость по миру (CDN) | встроенный CDN, страница отдаётся с сервера рядом с пользователем | сервер в регионе аудитории; при необходимости CDN через Bunny (работает в РФ) |
| Цена на росте | бесплатно/дёшево на старте, сильнее дорожает с ростом трафика пользователей | стабильно дёшево ($5-30/мес) |
| Контроль | платформа решает за вас | сервер полностью ваш |
| Данные / 152-ФЗ для РФ | часто на серверах вне РФ | данные где хотите, можно РФ |
| Привязка | завязка на одного поставщика | переносится на любой сервер |

**Про скорость по миру и распределенные сервера (CDN).** Реальное техническое преимущество Vercel в том, что у него встроенный CDN — сеть из десятков серверов по всему миру. Ваши страницы и статика раздаются автоматически, и пользователь в любой точке получает ответ от ближайшего сервера. У нас сервер один. Но мы ставим его в регионе своей аудитории: для РФ это хостинг в России, и тогда сервер физически рядом с пользователями, а глобальный CDN большой роли не играет. Привычный Cloudflare в России мы не используем — он заблокирован, гнать через него трафик ненадёжно. Если CDN всё же нужен (аудитория по миру, тяжёлая статика, видео), берётся Bunny — он работает и в России, и за рубежом, и докручивается к нашему VPS отдельным шагом (само подключение разбираем в Уроке 6). Любой CDN — это в внешний сервис, так что от какой-то зависимости от доп сервисов тут не уйти ни на Vercel, ни у нас. Но главное отличие не в скорости, а в данных: у нас приложение и база лежат на вашем VPS, вы их контролируете и держите в нужной юрисдикции. У Vercel же на платформе оказывается всё, включая данные пользователей, и отсюда вопрос с законами о хранении данных (для РФ — 152-ФЗ).

**Когда что подходит:**
- **Vercel и подобные** — быстрый MVP за выходные, аудитория по миру, статика + лёгкий API, нет желания разбираться с сервером.
- **Наш ручной деплой** — нужен контроль, предсказуемая цена на росте, своя БД / realtime / видео, аудитория из РФ (152-ФЗ), и понимание того, как всё устроено.

**В курсе идём в ручной деплой.** Если хотите совсем просто — Vercel это рабочий лёгкий путь: подключил репозиторий, нажал кнопку, и готово. Но я рекомендую пройти полный путь и поднять всё самому. Вы по сути ничего не теряете, зато всё остаётся под вашим контролем, и вы понимаете, как оно устроено. Для внутреннего инструмента готовая платформа вполне годится — это вы дальше разберёте сами. А вот если строите продукт, где будут храниться данные пользователей и вы реально собираетесь что-то на нём продавать, Vercel, скорее всего, не подойдёт: данные окажутся на чужой стороне и под чужой юрисдикцией (для РФ-аудитории это упирается в 152-ФЗ). Выбор под ваш конкретный проект зафиксируем в ADR-002.

**Авто-деплой или по команде.** Есть два режима, как код попадает на сервер. Первый — автоматический: вы пушите в ветку `main`, и деплой запускается сам (так работает Vercel — он подтягивает свежий коммит из вашей ветки и сразу выкатывает). Второй — по команде: код лежит в GitHub, но на сервер уезжает только когда вы говорите «задеплой», и AI запускает `deploy.sh`. У авто-режима плюс в скорости и в том, что прод всегда совпадает с `main`; минус — случайный пуш сразу уходит в прод, сломать его легче. У режима по команде плюс в контроле (сами решаете момент выката и видите каждый шаг), минус — нужна дисциплина не забывать деплоить. Для обучения и небольшого проекта удобнее по команде, для зрелого проекта с тестами — авто. «Единственно правильного» тут нет, поэтому промт ниже предложит оба варианта, а вы выберете свой.

**Push — осознанно, по выбранному режиму.** Правило коммитов (`commits.md`) уже заведено при создании git (Задание 2): коммит после каждого завершённого шага идёт автоматически. Здесь, когда выбран режим деплоя, **дописываем в него push-политику**: при **авто-деплое** (push в `main` → прод) пушим только то, что проверено и работает — не каждый коммит, а осознанно, когда «всё ок» (иначе сломанный коммит уедет в прод); при деплое **по команде** push безопасен — пушьте свободно, прод обновится только по `./deploy.sh`. Итог: коммит — всегда после шага; push — по режиму, а при авто-деплое AI спрашивает перед push в `main`.

Выбор запишем в формате **ADR**. ADR (Architecture Decision Record, «запись об архитектурном решении») — это короткий markdown-файл, в котором зафиксировано одно важное решение: что выбрали, почему, какие варианты рассматривали и от чего отказались. Лежат такие файлы в `../../product/docs/memory/decisions/` и нумеруются по порядку: стратегия деплоя — это ADR-002 (первым, ADR-001, был выбор стека). Внутри простая структура — Context (что за задача), Decision (что решили), Alternatives (что ещё рассматривали), Consequences (что из этого следует), Status и дата. Нужны они затем, что причины решений и вы, и AI забываете уже через пару недель. Без записи на вопрос «а почему у нас так?» Claude начнёт гадать или предложит переделать всё заново. С ADR он открывает файл и видит готовый ответ — поэтому каждое весомое решение в курсе мы фиксируем именно так. Сейчас разберём 5 основных способов деплоя под ваш проект и выберем один.

**Вход:** ваш проект и его требования (аудитория, нагрузка, бюджет).
**Выход:** `ADR-002` в `../../product/docs/memory/decisions/` + дописанная push-политика в `../../product/docs/rules/commits.md` (под выбранный режим деплоя) + строка в `../../product/docs/memory/INDEX.md`.

```
Выполни `prompts/04-deploy-strategy-adr.md` — разбери со мной 5 подходов к деплою (ручной AI/SSH, git-based VPS, CI/CD, managed-платформы, scp/rsync) с плюсами и минусами под мой проект. Помоги выбрать, зафиксируй решение как `ADR-002` в `../../product/docs/memory/decisions/` с обоснованием и добавь строку в `../../product/docs/memory/INDEX.md`. И допиши push-политику в `../../product/docs/rules/commits.md` (он уже заведён при настройке git) под выбранный режим: при авто-деплое (push в main → прод) пушить только проверенное и спрашивать перед push в main; при деплое по команде — пушить свободно. Спроси меня, какой режим выбрали.
```

**Результат:** разобраны 5 способов деплоя, выбран один под ваш проект и записан как `ADR-002`. В правило `commits.md` дописана push-политика под выбранный режим (при авто-деплое — пушим только проверенное, с вопросом перед push в `main`; по команде — свободно). Строка добавлена в `INDEX.md`. Через месяц AI прочитает причину выбора и не станет предлагать всё переписать.

## Шаг 4. VPS + docker-compose

**Результат шага:** сервис запущен на сервере, доступен по IP.


### Задание 5. Поднимаем сервер

VPS (Virtual Private Server) – это арендованный кусочек мощного компьютера в дата-центре. У него есть постоянный публичный адрес (IP) и интернет. Стоит $5-10 в месяц. Заходите на него по SSH (это терминал, только удалённый, на чужой машине) и работаете как с обычным linux-сервером.

**Где брать VPS.** Для РФ-аудитории берите хостинг в России — например Timeweb: оплата картой РФ, а сервер и данные сразу в нужной юрисдикции (152-ФЗ). Если у вас есть иностранный способ оплаты или VPN, подойдёт Hetzner — за те же деньги мощнее и быстрее, но дата-центры в ЕС, поэтому для данных под 152-ФЗ он не годится. В курсе шаги одинаковые для любого провайдера: дальше нужен только IP сервера и SSH-доступ.

Docker – это способ упаковать приложение вместе со всем, что ему нужно для работы, в один «контейнер». Тогда на сервере не придётся вручную ставить Node.js, библиотеки и базы данных. Всё описано в `Dockerfile`, и любой компьютер с Docker запустит ровно такую же сборку.

Сейчас соединим три вещи. Поставим Docker на сервер. Опишем приложение в `Dockerfile` и `docker-compose.yml`. И напишем `deploy.sh` – скрипт, который заходит на сервер, забирает свежий код из git, пересобирает контейнер и перезапускает приложение. Заодно поставим лёгкий nginx, чтобы приложение **сразу открывалось по `http://your-server-ip` в браузере — ещё до домена**. Домен и HTTPS (зелёный замок) подключим на следующем шаге; сам контейнер при этом останется доступен только изнутри сервера (на 127.0.0.1 и своём порту — по умолчанию 3000), а наружу его отдаёт nginx.

> **Сразу со страховками для слабого VPS.** Промт по ходу настроит то, без чего бокс на ~1 ГБ со временем тормозит: ротацию логов Docker (иначе забьют диск), `vm.swappiness=10` (чтобы ядро не свопило горячее приложение), `mem_limit` + `healthcheck` + `restart` на каждый сервис, и пост-деплой гигиену (`docker builder prune`). Важная мысль: на слабом сервере тяжёлую сборку образа лучше **не делать на самом сервере** — она раздувает Docker и роняет бокс в swap; правильнее собирать в CI и выкатывать готовый образ. Этот выбор зафиксируете в ADR-002.

На свежем VPS у вас есть только то, что выдал провайдер: IP, пользователь (обычно `root`) и пароль — SSH-ключа на сервере ещё нет. Поэтому в `.env.deploy` вы вписываете именно этот стартовый доступ (IP + root + пароль), а AI при первом входе по паролю сам ставит ваш SSH-ключ и дальше работает уже по ключу. Полное отключение пароля и входа под root — позже, в Задании 7 (безопасность сервера). Порт `3000` — это стандартный порт Next.js; если ваше приложение слушает другой, AI подставит его одинаково в Dockerfile, `docker-compose.yml`, nginx и проверках.

**Вход:** private-репо с кодом на GitHub + купленный VPS с root-доступом от провайдера (IP, пользователь, пароль).
**Выход:** `.env.deploy` с доступом к серверу (значения вписаны в файл, не в чат). На VPS установлен ваш SSH-ключ (первый вход — по паролю), docker/git, для сервера заведён read-only deploy key, склонирован репо, созданы `../../product/Dockerfile`, `../../product/docker-compose.yml`, `.env.production` (на сервере), `deploy.sh` (на сервере), `../../product/scripts/deploy-remote.sh` (локально), поднят лёгкий nginx. Приложение открывается по `http://<IP>` в браузере — ещё без домена и HTTPS.

```
Перед запуском убедись что VPS куплен. Доступ к серверу я не ввожу в чат: создай `.env.deploy` с плейсхолдерами (SERVER_IP, SERVER_USER=root, SERVER_PASSWORD, SSH_KEY_PATH, DOMAIN — `GITHUB_URL` ты подставишь сам из `git remote get-url origin`, репо уже подключён), я впишу стартовый доступ от провайдера прямо в файл. Затем выполни `prompts/05-vps-docker-compose.md`: первый раз подключись по паролю и сам поставь мой SSH-ключ на сервер (дальше только по ключу), поставь на сервере docker / docker-compose / git, заведи для сервера read-only deploy key и склонируй репо в `/var/www/<project>/`, собери Dockerfile (multi-stage) и `docker-compose.yml`, создай на сервере `.env.production` (chmod 600), напиши `deploy.sh` на сервере и `scripts/deploy-remote.sh` локально, подними контейнер `web`, поставь лёгкий nginx-reverse-proxy (catch-all по IP) и покажи мне открыть приложение по `http://<IP>` в браузере — ещё до домена и HTTPS.
```

**Результат:** на VPS поставлен ваш SSH-ключ (первый вход — по паролю от провайдера, дальше по ключу), установлены docker, docker-compose и git, для сервера заведён read-only deploy key (доступ к репо только на чтение, не ваш личный ключ), репозиторий склонирован в `/var/www/<project>/`, созданы Dockerfile (multi-stage) и `docker-compose.yml`. `GITHUB_URL` подставлен автоматически из подключённого remote. На сервере есть `.env.production` с правами 600, написаны `deploy.sh` на сервере и `scripts/deploy-remote.sh` локально. ## Шаг 5. Домен + HTTPS

**Результат шага:** сервис доступен по `https://your-domain.com`.


### Задание 6. Домен и HTTPS

Домен – это понятное человеку имя вместо адреса из цифр (`your-domain.com` вместо `185.123.45.67`). Покупается у регистратора на год. В DNS добавляете A-запись – она говорит «этот домен ведёт на этот IP», и через 5-30 минут сайт открывается по всему миру. HTTPS – это шифрование: данные между браузером пользователя и сервером идут в закрытом виде, чужой их не прочитает. Без HTTPS браузер показывает предупреждение «Not Secure», поиск ставит сайт ниже, а люди не доверяют формам и не вводят туда данные.

HTTPS включить можно по-разному, мы берём самый простой и бесплатный путь. **Let's Encrypt** – это центр сертификации, который выдаёт SSL-сертификаты (они и включают HTTPS) бесплатно и автоматически. Выдаёт их не он один: есть платные центры и другие бесплатные (например ZeroSSL), но Let's Encrypt стал стандартом именно потому, что бесплатно, открыто и думать особо не о чем. **Certbot** – программа, которая получает сертификат от Let's Encrypt и сама обновляет его каждые 60 дней. Она тоже не обязательна: ту же задачу решают `acme.sh` или веб-сервер Caddy, который выпускает и продлевает сертификаты сам, без отдельной утилиты. В курсе идём через nginx + Certbot как самый распространённый и хорошо документированный вариант — если позже выберете Caddy, шаги будут проще, а смысл тот же. Между интернетом и нашим приложением ставим **nginx**. Он работает как привратник (reverse-proxy): принимает зашифрованный HTTPS-трафик, расшифровывает и передаёт на 127.0.0.1:3000 (наше Next.js-приложение). Заодно он добавляет security headers – защиту от классических уязвимостей вроде clickjacking и MIME-sniffing.

Заодно настроим **канонический хост** — одну основную версию адреса. Сайт обычно открывается и как `your-domain.com`, и как `www.your-domain.com`. Если обе версии отдают контент, поиск считает их двумя разными сайтами и делит между ними вес. Поэтому выбираем одну основную (единого «правильного» стандарта нет, оба варианта валидны; по умолчанию берём версию с www), а вторую 301-редиректим на неё. Для этого нужны три согласованные вещи — DNS-запись `www`, сертификат на оба имени и редирект в nginx; промт сделает всё это и спросит, какую версию сделать основной.

Заодно настроим **кэш статики на nginx**. Бандлы JS/CSS и шрифты Next.js (в `/_next/static/`) собираются с хэшем в имени файла и не меняются без передеплоя — значит, их можно отдавать браузеру с «вечным» кэшем (`Cache-Control: immutable`). Тогда общий код, меню и шрифты скачиваются один раз, а при переключении страниц и повторных заходах берутся из кэша браузера, а не качаются снова. Вместе с постоянной обвязкой из Урока 2 (меню в `layout.tsx`) это и убирает «долгое переключение между страницами»: статика закэширована, по сети подтягивается только динамический контент. HTML-страницы при этом долгим кэшем не накрываем — иначе заморозим обновления контента.

**Вход:** работающий по IP сервис + купленный домен.
**Выход:** A-записи в DNS (домен и www), конфиг nginx, SSL-сертификат Let's Encrypt на оба имени с auto-renewal, канонический редирект (www ↔ голый домен), security headers, кэш статики (`/_next/static/` immutable) + gzip. Сервис открывается по `https://your-domain.com`.

```
`prompts/07-domain-https.md`: дай мне конкретные DNS-записи под мой регистратор (Type / Host / Value / TTL — A `@` и A `www` на IP сервера, или CNAME `www` → домен) и точный путь, куда их вставить. Обнови nginx (он уже работает по IP с прошлого шага) — замени заглушку `server_name _` на твой домен, proxy_pass не трогай (он уже указывает на реальный порт приложения из промта 05, не хардкодь 3000). Получи через certbot сертификат Let's Encrypt на оба имени с auto-renewal, настрой канонический редирект (одна основная версия, вторая — 301 на неё), добавь security headers (X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy). Настрой кэш статики: `/_next/static/` отдавай с `Cache-Control: immutable` (HTML — не кэшируй надолго), включи gzip. В конце — `https://your-domain.com` с зелёным замком, `http://` и не-каноническая версия редиректят на основную.
```

**Результат:** в DNS прописаны A-записи на IP сервера (домен и www), конфиг nginx обновлён доменом (nginx уже работал по IP с прошлого шага, передаёт трафик на локальный порт приложения — тот же, что из промта 05, по умолчанию 3000), certbot получил сертификат Let's Encrypt на оба имени и настроил авто-обновление. Настроен канонический хост: одна основная версия адреса, вторая (www или голый домен) отдаёт 301 на неё. Добавлены security headers (X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy). Открыв `https://your-domain.com`, увидите зелёный замок, а `http://` и вторая версия адреса сами переводят на основную.

### Задание 7. Базовая security на сервере

Сервер с публичным IP начинают атаковать с первой же минуты. Боты перебирают IP подряд, подбирают типичные пароли по SSH, ищут открытые порты, проверяют известные дыры. **Вход:** работающий сервер с доменом и HTTPS.
**Выход:** на сервере настроены SSH-by-key, UFW, fail2ban. В коде новый файл `../../product/src/middleware.ts` с rate limiting.

```
Открой `prompts/08-security-basics.md` и пройди по защите сервера (на сервер подключаешься сам, доступ из `.env.deploy`, я ничего не ввожу в терминал): SSH только по ключу (парольную аутентификацию выключи), UFW на 22/80/443, fail2ban с защитой SSH и nginx-limit-req. В коде заведи `../../product/src/middleware.ts` с rate limiting на `/api/auth` и `/api/`. На сервере `fail2ban-client status` должен показывать активную защиту.
```

**Результат:** SSH-вход только по ключу (вход по паролю отключён), UFW настроен на 22/80/443, fail2ban установлен и работает (защита SSH + nginx-limit-req). ### Задание 8. Хуки-guardrails (для любого AI)

Хуки (hooks) – это небольшие скрипты, которые AI запускает сам в определённые моменты: перед запуском команды в терминале, перед записью в файл, в начале сессии. Правило в `AGENTS.md` AI может пропустить в шуме длинного разговора, а хук срабатывает всегда. Это код, а не текст: сказал хук «нет» – действие не выполнится, и никак иначе. Поэтому хуки – самый надёжный слой защиты внутри сессии.

Главное: хуки – это **кросс-тул механизм, а не фишка Claude Code**. Те же shell-скрипты работают в Claude Code (`../../.claude/settings.json`), OpenAI Codex (`../../.codex/hooks.json`) и Cursor 1.7+ (`../../.cursor/hooks.json`) – меняется только путь конфига и имена событий. Поэтому промт `09` универсальный: запускаете его один раз под свой инструмент, и он настраивает всё сразу. Если инструмент совсем без хуков – тот же промт даёт текстовый fallback через `AGENTS.md`.

Соберём весь набор за один проход. **Блокирующие** хуки: `pre-tool-use-bash.sh` (опасные команды – `rm -rf /`, force push в main) и `pre-tool-use-write.sh` (секреты в коде по шаблонам `sk-...`, `ghp_...`). **Напоминалки** (ничего не блокируют, только подсказывают): `pre-tool-use-security-reminder.sh` и `post-tool-use-security-counter.sh` напоминают прогнать `/security-check`, когда правок в чувствительных местах накопилось много или перед коммитом. Плюс `pre-compact-snapshot.sh` (снимок состояния перед сжатием контекста) и `context-alert.sh` (напоминание при длинной сессии). После записи в конфиг всё работает тихо, в фоне.

**Вход:** существующий `../../.claude/settings.json` проекта (или `../../.codex/hooks.json` / `../../.cursor/hooks.json` — смотря какой у вас инструмент).
**Выход:** хуки в `../../.claude/hooks/` (`pre-tool-use-bash.sh`, `pre-tool-use-write.sh`, `pre-tool-use-security-reminder.sh`, `post-tool-use-security-counter.sh`, `pre-compact-snapshot.sh`, `context-alert.sh`) + маркер `../../.claude/scripts/security-check-mark.sh`, их регистрация в конфиге вашего инструмента, описание в `../../product/docs/rules/hooks-guardrails.md`. На инструменте без хуков — правила-эквиваленты в `AGENTS.md`.

```
Выполни `prompts/09-bash-write-hooks.md` — он универсальный, сам определит твой инструмент (Claude Code / Codex / Cursor / без хуков). В конце прогони тестовые команды для проверки что хуки срабатывают. Внутри: блокирующие хуки `pre-tool-use-bash.sh` (rm -rf, force push) и `pre-tool-use-write.sh` (секреты вроде sk-...); напоминалки `pre-tool-use-security-reminder.sh` и `post-tool-use-security-counter.sh` (напоминают прогнать /security-check) + маркер `security-check-mark.sh`; плюс `pre-compact-snapshot.sh` и `context-alert.sh`. Зарегистрируй всё в конфиге моего инструмента, опиши в `../../product/docs/rules/hooks-guardrails.md`. Если инструмент без хуков — собери эквивалент правилами в `AGENTS.md`.
```

**Результат:** в `../../.claude/hooks/` появятся блокирующие `pre-tool-use-bash.sh` и `pre-tool-use-write.sh`, напоминалки `pre-tool-use-security-reminder.sh` и `post-tool-use-security-counter.sh`, а также `pre-compact-snapshot.sh` и `context-alert.sh`; маркер `../../.claude/scripts/security-check-mark.sh`. Всё зарегистрировано в конфиге вашего инструмента (на Codex/Cursor — в их файлах хуков; без хуков — правила в `AGENTS.md`). Проверка: опасную команду хук блокирует, секрет в код не записывается, после серии правок в чувствительных местах приходит напоминание про `/security-check`. Описание в `../../product/docs/rules/hooks-guardrails.md`.

> **Три механизма, и зачем нужны все.** Блокирующие хуки – **простой слой**: поиск по известным шаблонам (`sk-...`, `eval()`, `rm -rf`), действие блокируется сразу. Плагин `security-guidance` (Шаг 0) – **умный слой**: фоновая проверка каждого изменения и коммита Claude'ом, он замечает то, что шаблон не видит (обход прав, IDOR, инъекции в SQL через переменные), пишет находку в чат, и Claude чинит её в той же сессии. Хуки-напоминалки – **мостик к аудиту**: сами ничего не находят, но не дают забыть прогнать `/security-check`. Это важно по двум причинам: плагин платный и работает только в Claude Code, а на Codex/Cursor его нет вообще — там напоминалки остаются единственным автоматическим способом вспомнить про аудит, и при этом они бесплатны и работают всегда. Три механизма не дублируют друг друга, а складываются в защиту в несколько слоёв. Подробнее о слоях – в Уроке 7 («защита от регрессий»).

> **Не Claude Code?** Хуки – уже кросс-тул механизм, а не фишка одного редактора. Те же скрипты переносятся, меняется только путь конфига и имена событий:
> - **OpenAI Codex** – конфиг в `../../.codex/hooks.json` (или `[hooks]` в `../../.codex/config.toml`). Имена событий почти совпадают с Claude Code: `PreToolUse`, `PostToolUse`, `SessionStart`, `PreCompact` + `matcher: "Bash"`. Блокировка – `exit 2` или `permissionDecision: "deny"`. Наши `pre-tool-use-bash.sh` / `pre-tool-use-write.sh` переносятся почти без правок. Управление и «доверие» к хукам – командой `/hooks` (Codex просит подтвердить новый хук по хэшу перед запуском).
> - **Cursor** (с 1.7) – конфиг `../../.cursor/hooks.json`. Идея та же, но события называются иначе: `beforeShellExecution`, `afterFileEdit`, `preToolUse` / `postToolUse`, `sessionStart`, `preCompact`, `stop`. Блокировка – `exit 2` или `{"permission":"deny"}`; флаг `failClosed: true` заставляет блокировать действие даже если сам хук упал.
> - **Универсальный слой для всех инструментов** – git-хуки (`pre-commit` / `pre-push`). Они не зависят от AI вообще: срабатывают при любом коммите, кто бы его ни делал – человек, Codex, Cursor, Aider. Наш spec-gate из Задания 2 – ровно такой git-хук; туда же вешается секрет-сканер (`gitleaks`). Это самый надёжный слой, потому что обойти его, не отключив руками, нельзя.
> - **Совсем без хуков** (редкие инструменты) – остаётся текстовый fallback: жёсткое правило в `AGENTS.md`. Самый слабый слой – AI может пропустить правило в шуме длинной сессии, – но лучше, чем ничего.

## Шаг 8. Сквозной аудит безопасности, Свой `/security-check` скилл для постоянной фоновой проверки безопасности

### Задание 10. Аудит безопасности + сборка своего `/security-check`

## Шаг 9. Pre-deploy gate

**Результат шага:** `deploy.sh` автоматически прогоняет security-check перед каждым деплоем.


### Задание 11. Security-check в деплой

Pre-deploy gate – это автоматический фильтр между «у меня локально работает» и «уехало в прод». Перед каждым деплоем скрипт прогоняет набор проверок: нет ли секретов в коде, не разрешены ли опасные команды, верные ли body limits в конфиге, правильные ли права на файлах `.env`. Если хоть одна проверка не прошла, деплой отменяется, а прод остаётся рабочим.

Это страховка от классической истории: «быстренько правил конфиг, забыл убрать тестовый ключ, прод упал». Скрипт встраивается в `deploy.sh` первым шагом: прошло – едем дальше, не прошло – стоп. Запуск занимает пару секунд, а один предотвращённый сбой окупает весь курс.

**Вход:** готовые `../../product/scripts/deploy-remote.sh` (локально) и `deploy.sh` (на сервере).
**Выход:** новый `../../product/scripts/security-precheck.sh`, подключённый к обоим deploy-скриптам как gate + обновлённый раздел «Деплой» в `../../product/docs/memory/infrastructure.md`.

```
`prompts/13-security-precheck-deploy-gate.md` — в конце прогони тест с фейковым секретом, должно блокировать деплой. Внутри: собери `../../product/scripts/security-precheck.sh` с 6 проверками (секреты в коде, опасные команды, body limits, права на .env и т.д.), подключи к локальному `../../product/scripts/deploy-remote.sh` и серверному `deploy.sh` как gate (при — отказ), обнови раздел «Деплой» в `../../product/docs/memory/infrastructure.md`.
```

**Результат:** создан `../../product/scripts/security-precheck.sh` – быстрый bash-фильтр с 6 проверками (секреты в коде, опасные команды, body limits, права на .env и т.д.), подключён к локальному `../../product/scripts/deploy-remote.sh` и серверному `deploy.sh`. Если проверка не проходит, деплой не происходит. Тест с поддельным секретом блокирует деплой. Раздел «Деплой» в `../../product/docs/memory/infrastructure.md` обновлён. Теперь каждый `./deploy.sh` проходит через этот фильтр.

> **Чем pre-deploy gate отличается от хуков Claude (Задание 8) и git-хука (Задание 2).** Это три слоя одной защиты, расставленные в разные моменты пути кода в прод. Каждый следующий слой труднее обойти и срабатывает ближе к боевому серверу.
> - **Хук Claude** (`pre-tool-use-bash.sh` / `pre-tool-use-write.sh`, Задание 8) срабатывает раньше всех — в тот момент, когда AI собирается записать файл или запустить команду прямо в сессии. Он защищает от ошибок самого ассистента, но работает только пока вы действуете через AI: команду, набранную руками в терминале, он не видит.
> - **Git-хук спека-гейта** (`pre-commit`, Задание 2) срабатывает на коммите. Он уже не зависит от того, кто пишет код — человек, Claude, Codex или Cursor проходят через него одинаково. Туда же вешается секрет-сканер (`gitleaks`).
> - **Pre-deploy gate** (`security-precheck.sh` в `deploy.sh`, это задание) срабатывает последним — прямо перед тем как код уедет на сервер. Он ловит даже то, что проскочило мимо первых двух: правку в обход AI или коммит, который почему-то прошёл без хука. Это последний рубеж, обойти его можно только убрав вызов из `deploy.sh` руками.
>
> Проверки частично совпадают по содержанию (например, поиск секретов есть и в `pre-tool-use-write.sh`, и в `security-precheck.sh`) — это не дублирование, а защита в несколько слоёв: одна и та же ошибка ловится в разных точках, и чем ближе к проду, тем дороже её пропустить. Полную карту слоёв (плагин, хуки, git, gate) собираем в Уроке 7.

## Шаг 10. Zero-downtime deploy — обновление без обрыва запросов

**Результат шага:** при `./deploy.sh` ни один активный запрос не обрывается.

### Задание 12. Graceful shutdown

Когда вы выкатываете новую версию (`./deploy.sh`), контейнер перезапускается. Без настройки в этот момент рвётся **любой запрос, который сейчас выполняется** — и это касается не только кнопки «Сохранить»:
- POST формы (сохранение, оплата, регистрация) — транзакция оборвётся на середине;
- загрузка или обработка файла — прервётся;
- фоновая задача (письмо, обработка) — не завершится;
- открытые WebSocket / SSE — отвалятся.

Решение — **graceful shutdown** («мягкое выключение»): по сигналу `SIGTERM` старая версия перестаёт брать новые запросы, доделывает текущие, аккуратно закрывает соединения с БД и фоновые задачи и только потом выключается. Собирается из четырёх слоёв: `STOPSIGNAL SIGTERM` и `NEXT_DRAINING_PROCESS_TIMEOUT_MS` в `Dockerfile`, `stop_grace_period` в `docker-compose.yml` и обработчик сигнала в `instrumentation.ts` (Next.js 14+ подхватывает его сам). Готовый код и команды — в промте.

**Вход:** `Dockerfile` и `docker-compose.yml` (Задание 5).
**Выход:** в `Dockerfile` — `STOPSIGNAL SIGTERM` + `NEXT_DRAINING_PROCESS_TIMEOUT_MS=20000`, в `docker-compose.yml` — `stop_grace_period: 30s`, новый `instrumentation.ts` с graceful shutdown.

```
Открой `prompts/14-zero-downtime.md` и настрой zero-downtime deploy: добавь `STOPSIGNAL SIGTERM` и `NEXT_DRAINING_PROCESS_TIMEOUT_MS=20000` в `../../product/Dockerfile`, `stop_grace_period: 30s` в `../../product/docker-compose.yml`, создай `../../product/instrumentation.ts` с обработчиком SIGTERM (доделать активные запросы → закрыть Prisma и Redis/очереди → выйти). В конце проверь: запусти долгий запрос и в этот момент сделай деплой — запрос должен дозавершиться, а не оборваться. Обнови раздел «Деплой» в `../../product/docs/memory/infrastructure.md`.
```

**Результат:** добавлены все четыре слоя graceful shutdown (`../../product/Dockerfile`, `../../product/docker-compose.yml`, `../../product/instrumentation.ts`). Тест: активный запрос (сохранение / загрузка / оплата) при деплое дозавершается с ответом 200, а не обрывается. Раздел «Деплой» в `../../product/docs/memory/infrastructure.md` обновлён.

Промт `14-zero-downtime.md` идёт двумя уровнями: Уровень 1 (graceful shutdown, выше) убирает обрыв активных запросов; Уровень 2 (blue-green в том же промте) поднимает новую версию рядом и переключает трафик только когда она готова, а старая дорабатывает ещё `DRAIN_SECONDS` — так пропадает и окно 502 на новые запросы. Для учебного проекта достаточно Уровня 1, blue-green включайте, если важен трафик без единой ошибки при выкатке.
