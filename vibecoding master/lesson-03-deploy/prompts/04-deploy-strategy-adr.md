# ADR-002 — выбор стратегии деплоя

## Промт

```md
Объясни мне основные подходы к деплою и их компромиссы коротко и практично.

1. Ручной deploy через AI/SSH
   - Я говорю AI: «задеплой»
   - AI подключается к серверу, запускает понятный deploy.sh, проверяет логи и ссылку
   - Плюсы: видно каждый шаг, удобно учиться, легко дебажить
   - Минусы: деплой не происходит сам после push, нужна дисциплина

2. Git-based на VPS
   - Push в GitHub → на сервере git pull + перезапуск через deploy.sh
   - Плюсы: версия = коммит, есть история, понятный откат
   - Минусы: серверу нужен доступ к репо, надо понимать git pull на проде

3. CI/CD
   - Push в main → CI прогоняет сборку/тесты → если всё зелёное, запускает деплой
   - Плюсы: удобно для зрелого проекта и команды
   - Минусы: секреты в CI, сложнее дебажить, можно случайно сломать прод одним push

4. Платформы: Vercel / Netlify / Render / Railway
   - Push → платформа сама билдит и деплоит
   - Плюсы: быстрый старт, меньше DevOps, хорошо для простых фронтендов и MVP
   - Минусы: ограничения зависят от backend, БД, файлов, фоновых задач, региона и цены

5. scp / rsync / копирование артефактов
   - Готовые файлы копируются на сервер
   - Плюсы: просто для статических сайтов и маленьких проектов
   - Минусы: хуже повторяемость, история и откат; легко получить «на сервере не то, что в репо»

Отдельно поясни ключевую развилку: деплой может запускаться сам при пуше в ветку
main (так делает Vercel — подтягивает свежий коммит и сразу выкатывает) или только
по моей команде «задеплой». Назови плюсы и минусы каждого режима: авто — быстро и
прод всегда совпадает с main, но случайный пуш сразу уходит в прод; по команде —
полный контроль момента выката, но нужна дисциплина не забывать деплоить.

Ещё одна важная развилка — **ГДЕ собирается Docker-образ**. Объясни на моём железе:
- **Сборка на сервере** (`docker compose up -d --build` в deploy.sh) — просто, но
  `next build` внутри BuildKit прожорлив по памяти, а dockerd после сборки НЕ
  возвращает память ОС. На слабом VPS (~1 ГБ) это выедает RAM → сервер уходит в swap
  → сайт тормозит (TTFB секунды). Само приложение в 1 ГБ умещается — узкое место
  именно в СБОРКЕ на сервере.
- **Сборка в CI / локально → push в реестр (GHCR) → на сервере только `docker
  compose pull && up -d`.** Тяжёлая сборка уходит с VPS: dockerd не пухнет, swap под
  деплой не нужен, перезапуск демона не требуется (важно для zero-downtime). Цена —
  настроить GitHub Actions + GHCR (чуть больше инфраструктуры на старте).
Рекомендация: на боксе ≤1-2 ГБ — собирать НЕ на сервере (CI/локально + pull). Если
пока остаёшься на сборке на сервере — обязательна пост-деплой гигиена из промта 05
(`docker builder prune -f`, перезапуск демона при раздутии, swap + swappiness=10).

После объяснения спроси меня, какой стиль деплоя мне ближе:
- ручной запуск через AI/SSH по команде «задеплой»;
- git-based на VPS;
- CI/CD сразу;
- платформа вроде Vercel/Render/Railway;
- другой вариант.

Если я не знаю, предложи базовый дефолт:
VPS + docker-compose + deploy.sh, где деплой запускается вручную через AI/SSH.
Внутри deploy.sh можно использовать git pull, если код обновляется через GitHub.

# ADR-002: Стратегия деплоя

## Context
Нам нужен понятный способ выкладывать проект в публичный доступ.
Пользователь — дизайнер, поэтому стратегия должна быть прозрачной, повторяемой и достаточно безопасной.
Сложность зависит от типа проекта: статический сервис, приложение с сервером, БД, файлами, интеграциями.

## Decision
Выбранный вариант: <заполнить после ответа пользователя>.

Базовый вариант, если пользователь не выбрал иначе:
- VPS + docker-compose
- deploy.sh на сервере как единая точка деплоя
- локально или через AI: команда «задеплой» запускает deploy.sh по SSH
- внутри deploy.sh может быть git pull + docker compose up -d --build, если код обновляется через GitHub
- ГДЕ собирается образ: на боксе ≤1-2 ГБ RAM по умолчанию НЕ на сервере — сборка
  в CI (GitHub Actions) / локально → push в GHCR → на сервере `docker compose pull
  && up -d`. Если пока собираем на сервере — обязательна пост-деплой гигиена (промт 05).

## Alternatives Considered

### Ручной deploy через AI/SSH
Хорошо: максимальная прозрачность, удобно для обучения, можно буквально сказать AI «задеплой и проверь логи».
Риск: нет автоматического деплоя после каждого push, нужна дисциплина.

### Git-based на VPS
Хорошо: версия = коммит, откат понятен, сервер сам забирает код.
Риск: надо настроить доступ сервера к репо, понимать git pull на проде.

### CI/CD
Хорошо: стандартно для команды, деплой после push.
Риск: секреты в CI, сложнее дебажить, можно случайно сломать прод одним push.
Можно включить позже, когда ручная цепочка понятна.

### Платформы Vercel / Netlify / Render / Railway
Хорошо: быстрый старт, меньше DevOps.
Риск: ограничения зависят от backend, БД, файлов, регионов, background jobs и стоимости.
Для простого публичного фронтенда может быть лучшим выбором.

### scp / rsync
Хорошо: просто для статических проектов.
Риск: слабее повторяемость, история и откат.

## Consequences
- Все будущие команды «задеплой», «откати», «посмотри логи» должны опираться на этот ADR.
- Выбранную стратегию нужно описать в ../../product/docs/memory/infrastructure.md после настройки.
- Если стратегия изменится, создать новый ADR или обновить этот с причиной.
- Размер VPS: 1 ГБ / 1 vCPU — это потолок для учебного проекта. Его хватает, чтобы
  ПРИЛОЖЕНИЕ работало (Next ~150-300 МБ + Postgres + MinIO укладываются с swappiness=10
  и mem_limit). Узким местом он становится на: сборке образа на сервере (выносим в CI),
  тяжёлых параллельных запросах/росте трафика, больших миграциях, активном MinIO под
  файлы. Признаки «пора апгрейдить»: постоянный swap (vmstat si/so > 0 не только на
  деплое), OOM-kill контейнеров, CPU в потолке (uptime load > числа ядер). Тогда — 2 ГБ+.
```

## Edge cases

- Если у пользователя уже есть рабочий проект на Vercel / Render / Railway — не ломайте его. Зафиксируйте текущую стратегию, риски и условия, когда стоит переехать.
- Если у пользователя нет VPS — отложите VPS-часть, ADR-002 пометьте `Status: Deferred` с причиной.
- Если проект простой и публичный без БД, файлов и server-side задач — платформа может быть лучшим выбором, чем VPS.
