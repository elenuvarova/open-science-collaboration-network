### Промт «Объясни Git и GitHub концептуально»

```
Объясни мне коротко (5-7 минут чтения):

1. Git концептуально:
   - Что такое репозиторий, коммит, ветка, remote
   - Зачем GitHub (cloud-копия + история + совместная работа)
   - Что происходит при git add, commit, push на пальцах
   - Зачем при работе со мной не делать git push --force на main

2. Способы аутентификации в GitHub:
   - Раньше можно было через логин+пароль через CLI. С 2021 года GitHub
     запретил — небезопасно, пароли легко угоняли через фишинг. Сейчас
     логин+пароль работает только в самом браузере github.com.
   - Personal Access Token (PAT) — типа очень длинного пароля для CLI.
     Можно ограничить по правам и сроку. Но всё равно: если утечёт — атакующий
     получает доступ. Нужно периодически обновлять.
   - SSH-ключ — пара ключей: публичный (отдаём GitHub) + приватный (живёт у нас).
     При каждом git push GitHub проверяет подпись приватным ключом — без передачи
     самого ключа по сети. Если кто-то перехватит трафик — ключ не утечёт.
   - GitHub CLI (gh) с OAuth — самый простой путь. Браузер открывает
     окошко "разрешить gh", после чего gh сам управляет токенами и обновляет их.

3. Что такое SSH (на пальцах):
   - SSH = Secure Shell, протокол для безопасного соединения с удалённой машиной
   - Аналогия: пара "замок + ключ". Публичный ключ — это замок, который ты
     ставишь на сервере (или на GitHub). Приватный ключ — это ключ, который
     открывает замок. У тебя на ноуте один комплект ключей; ты раздаёшь "замки"
     на все сервисы куда хочешь подключаться без пароля.
   - Когда ты делаешь "git push" по SSH — твой git подписывает запрос приватным
     ключом, GitHub проверяет подписью с помощью публичного ключа, который у
     него лежит. Совпало → пускает. Сам ключ не передаётся.
   - Тот же механизм — для подключения к VPS. Один формат, две
     разные точки применения.

4. В чём разница между логином через интерфейс GitHub и через SSH:

   Логин в браузере на github.com:
   - Логин + пароль + двухфакторка (если включена)
   - Браузер хранит сессию в куки
   - Если кто-то увёл куки — попал в твой аккаунт
   - Подходит для чтения интерфейса, создания репо, настройки
   - НЕ подходит для git push с CLI — это отключено

   git push по SSH:
   - На стороне твоего ноута лежит приватный ключ ~/.ssh/id_ed25519
     (по умолчанию права 600 — только владелец читает)
   - На GitHub в Settings → SSH keys лежит публичный ключ ~/.ssh/id_ed25519.pub
   - При git push: SSH-клиент твоего ноута создаёт криптографическую подпись,
     GitHub проверяет, при совпадении — принимает
   - Преимущества: ключ привязан к машине, не передаётся, не нужно вводить пароль
     каждый раз
   - Риски: если приватный ключ утёк (например, забэкапили в публичное облако)
     — атакующий получает доступ ко всем репо, куда привязан ключ. Защита: chmod
     600 на ключе, не коммитить ~/.ssh/, использовать passphrase на ключе

5. Что выбираем:
   - GitHub CLI (gh) с OAuth — для тех кому удобно браузерное подтверждение.
     Простой setup, gh обновляет токены сам.
   - SSH-ключ — для тех кто хочет один раз настроить и забыть. Долгосрочно
     надёжнее, особенно когда у тебя несколько проектов и устройств.

   Покажи пользователю обе опции, дай выбрать.

6. Карта доступов, которые понадобятся в этом уроке (назови мне её явно, чтобы я
   сразу понимал, что и зачем выдаю — по принципу минимальных прав):
   - Моя машина ↔ GitHub: полный доступ на управление (создать репо, push). Это
     gh CLI (OAuth) или мой SSH-ключ — его сейчас и настраиваем.
   - Сервер (VPS) ↔ GitHub: только ЧТЕНИЕ одного репо, чтобы тянуть код при
     деплое. Мой личный ключ для этого НЕ используется и широкий токен не нужен —
     на сервере заводится отдельный read-only deploy key (сделаем в задании про
     VPS). Так у сервера минимум прав: даже если ключ сервера утечёт, у атакующего
     будет только чтение одного репо, а не весь мой GitHub.
   - Моя машина ↔ сервер: вход по SSH-ключу (доступ из .env.deploy) — это уровень
     сервера, отдельно от GitHub.
   Это и есть «связать git с сервером» безопасно: каждой стороне — ровно столько
   прав, сколько ей нужно.

После объяснения — задай мне один вопрос: "Какой способ аутентификации
выбираешь — gh CLI или SSH-ключ?"
```

## Практическая часть — выбор и настройка

> Настройку выполняешь ты (AI). Я ничего не набираю в терминал и не ввожу
> секреты в чат. От меня нужны только действия в браузере, которые AI не может
> сделать за меня (одноразовый код OAuth, вставка публичного ключа в веб-форму
> GitHub) — на них ты явно меня попросишь.

### Если выбран `gh CLI`

```

1. Установи gh CLI сам (определи ОС и поставь):
   - macOS: brew install gh
   - Linux (Ubuntu/Debian): sudo apt install gh
   - Windows: winget install GitHub.cli

2. Запусти аутентификацию (gh auth login): GitHub.com, протокол HTTPS,
   Login with: web browser. Откроется браузер с одноразовым кодом — это
   единственный шаг от меня: я введу код на github.com в браузере. Сам код
   ты мне в чат не выводишь и у меня не запрашиваешь.

3. Проверь сам: gh auth status
   Должен показать "Logged in to github.com as <username>".

4. Готово — теперь gh может делать всё: создавать репо, делать push, управлять
   issues. Никаких ключей вручную настраивать не надо.
```

### Если выбран SSH-ключ

```

1. Сгенерируй ключ сам (без passphrase или с passphrase — спроси меня, что
   удобнее; passphrase = доп. пароль на приватный ключ, полезно если ноут
   потеряется):
   ssh-keygen -t ed25519 -C "<мой email на GitHub>" -f ~/.ssh/id_ed25519

2. Запусти SSH-агент и добавь ключ (чтобы не вводить passphrase каждый раз):
   eval "$(ssh-agent -s)"
   ssh-add ~/.ssh/id_ed25519

   На macOS — добавь в ~/.ssh/config:
     Host github.com
       AddKeysToAgent yes
       UseKeychain yes
       IdentityFile ~/.ssh/id_ed25519

3. Покажи мне содержимое публичного ключа ~/.ssh/id_ed25519.pub (это публичная
   часть, не секрет — её и нужно отдать GitHub).

4. Это единственный шаг от меня (действие в браузере): я открою
   https://github.com/settings/keys → New SSH key → Title (имя ноута) →
   Key type: Authentication Key → вставлю публичный ключ → Add SSH key.

5. Проверь сам: ssh -T git@github.com
   Должен ответить: "Hi <username>! You've successfully authenticated..."

6. Если в проекте уже была настройка remote через HTTPS — переключи на SSH сам:
   git remote -v
   # Если origin = https://github.com/<user>/<repo>.git → меняем:
   git remote set-url origin git@github.com:<user>/<repo>.git
```

## Инициализация git, спека-гейт и первый push

В Уроке 2 git намеренно не трогали — приложение создавалось с `--disable-git`, поэтому ни репозитория, ни коммитов ещё нет. Инициализируем git здесь, ставим pre-commit хук «спека-гейт», делаем первый коммит и push.

### Шаг 1 — git init + защита секретов в .gitignore

Здесь git появляется впервые. В Уроках 1–2 уже могли появиться env-файлы (например `.env.local` с Figma-токеном) — они НЕ должны попасть в первый же коммит. Поэтому `.gitignore` приводим к каноничному виду **сразу после `git init`, до первого `git add`**.

```
В папке ../../product/ инициализируй git: git init, затем git branch -M main.

Сразу, до первого коммита, защити секреты. Открой .gitignore (create-next-app его создаёт) и убедись, что блок env приведён к каноничному виду — добавь или поправь, если отличается:

  # env (секреты) — никогда в git
  .env
  .env.*
  !.env.example

  # материалы курса — не пушим в репозиторий продукта
  lessons/

Полагаться на дефолт create-next-app нельзя: правило .env* заигнорит и .env.example (а его коммитим как шаблон — появится в 03-env-secrets), а старые шаблоны ловят только .env*.local, тогда .env.production / .env.deploy остаются открытыми. Заодно проверь, что игнорируются node_modules и .next.

Если рядом с продуктом (или внутри него) лежит папка lessons/ с уроками и модулями курса — добавь строку lessons/ в .gitignore сразу, чтобы учебные материалы и модули никогда не попадали в git продукта. Если такой папки нет — строку можно не добавлять, она ничему не мешает.

Проверь, что ни один реальный env-файл не попадёт в коммит:
  git add -A && git status --short
  # .env / .env.local / .env.production в списке быть НЕ должно
  git check-ignore .env.local .env.production .env.deploy
  # каждая существующая из них строка должна вывестись (значит игнорируется)
Если какой-то .env виден в git status — он НЕ игнорируется: поправь .gitignore и при необходимости убери из индекса (git rm --cached <файл>) до коммита.
```

### Шаг 2 — спека-гейт (pre-commit хук)

Хук не даёт закоммитить изменения кода без обновления спеки. Срабатывает на **каждом** `git commit` независимо от того, какой AI (или человек) коммитит — гарантия на уровне git, а не «AI вспомнил правило».

```
Заведи pre-commit хук спека-гейта в ../../product/:
1. mkdir -p scripts/hooks && git config core.hooksPath scripts/hooks
2. Создай scripts/hooks/pre-commit с содержимым (sh):
     #!/bin/sh
     # Спека-гейт: код в src/ нельзя закоммитить без обновления спеки.
     # Обход для не-поведенческих правок: SKIP_SPEC=1 git commit ...
     [ "$SKIP_SPEC" = "1" ] && exit 0
     staged=$(git diff --cached --name-only)
     echo "$staged" | grep -qE '^src/.+\.(tsx?|jsx?)$' || exit 0
     echo "$staged" | grep -qE '^docs/(spec\.md|screens/.+\.md)$' && exit 0
     echo "Изменён код в src/, но спека не тронута (docs/spec.md или docs/screens/*.md)."
     echo "Обнови спеку в этом же коммите. Не-поведенческая правка — SKIP_SPEC=1 git commit ..."
     exit 1
3. chmod +x scripts/hooks/pre-commit
4. Если в Уроке 2 (10-images) создан scripts/optimize-staged-images.sh — добавь первой строкой хука (сразу после shebang) `sh scripts/optimize-staged-images.sh`, чтобы картинки сжимались на каждом коммите. Один pre-commit на проект.
```

**Это не 100% гарантия корректности:** хук проверяет, что спеку *тронули*, а не что её обновили верно по смыслу. Семантику добивают правило в `AGENTS.md` и шаг `08-verification.md` (Урок 2).

Создай мне репозиторий на GitHub (всё делаешь ты, я только подтверждаю):

## Один коммит — одна логическая правка

Объясни пользователю до того, как он начнёт коммитить регулярно.

```
Объясни мне, что значит «атомарный коммит» и почему важно коммитить
небольшими шагами, а не раз в день или раз в фичу.
```

### Что объяснить

**Один коммит = одна завершённая мысль.**

Это может быть:
- добавил одну страницу
- поправил стиль одного компонента
- обновил зависимость
- исправил опечатку в тексте

Не «поработал над авторизацией» — это сразу 5-10 вещей в одном коммите.

**Почему это важно:**

Когда коммиты большие — `git log` теряет смысл. «WIP», «fix», «разное» в истории — и невозможно понять, что когда появилось.

Маленькие коммиты дают три преимущества:

1. **Откат:** `git revert <sha>` отменяет ровно одно изменение, не задевая соседние. При большом коммите — откатываешь всё сразу.

2. **Поиск бага:** `git bisect` делит историю пополам и находит, в каком коммите появился баг. Работает только если коммиты маленькие и атомарные.

3. **Ревью:** сам себе проще объяснить, что изменилось, когда это одна вещь.

**Как выглядит плохая история:**

```
fix bugs
wip
WIP auth
все изменения за вторник
```

**Как выглядит хорошая** (формат `проект (тип): описание`, где `проект` — короткое имя вашего продукта):

```
myapp (feat): форма входа с валидацией email
myapp (fix): кнопка не активировалась при пустом поле
myapp (feat): страница профиля — загрузка аватара
myapp (chore): обновил next.js до 15.3
```

### Проверка перед коммитом

Перед `git commit` — убедись что проект собирается:

```bash
# TypeScript-проект:
npm run build     # или npx tsc --noEmit если только типы

# Если билд прошёл — коммитишь (формат: проект (тип): описание)
git add src/features/login/
git commit -m "myapp (feat): форма входа"

# Если билд упал — не коммитишь, откладываешь изменения и чинишь
git stash     # изменения временно убраны
# ... чинишь причину ошибки ...
git stash pop # возвращаешь обратно и коммитишь уже работающее
```

Это защита от ситуации «закоммитил сломанное, пошёл спать, утром деплой упал по непонятной причине».

### Заведи правило авто-коммитов (`commits.md` + триггер в AGENTS.md)

Чтобы это не осталось разовым объяснением, а работало всегда — фиксируем правило файлом. Без записанного правила модель забывает про коммиты уже через несколько сообщений (поэтому «почему-то не коммитит сам» — это норма без правила). Push-политику (пушить сразу или только проверенное) допишем в это же правило на шаге выбора деплоя (Задание 4), когда станет понятно, завязан ли push на прод.

```
Заведи правило авто-коммитов в ../../product/docs/rules/commits.md (создай папку docs/rules/, если её нет):

# Commits — авто-коммит после каждого логического шага

## Принцип
Завершил логический шаг (фича, багфикс, законченная доработка, оформленный документ) →
СРАЗУ делай commit, не дожидаясь отдельной команды и не спрашивая «закоммитить?».
Коммит — часть выполнения шага, а не отдельное действие.

## Правила
1. После каждого завершённого шага: `git add <конкретные файлы шага>` + `git commit` — сам, сразу.
2. Атомарность: одна фича / один фикс = один коммит. Разное не сваливать в один коммит.
3. НЕ `git add -A` вслепую — добавляй только файлы этого шага (не утащить .env, дампы, мусор).
4. Формат сообщения (на русском): `проект (тип): описание`
   - `проект` — короткое имя вашего продукта (один и тот же во всех коммитах);
   - `тип` — один из: feat (новое), fix (багфикс), refactor, docs, chore (зависимости/конфиг/рутина);
   - описание — что сделано, по-человечески.
   Примеры: `myapp (feat): форма входа с валидацией email`,
            `myapp (fix): кнопка не активировалась при пустом поле`.
5. Документация / спека / тесты — в ТОМ ЖЕ коммите, что и код (см. спека-гейт).
6. Push — допишется на шаге выбора деплоя (Задание 4). Пока: есть remote → push после коммита.

Затем добавь в ../../product/AGENTS.md в раздел всегда-on правил (или в таблицу «Правила (читать по триггеру)») строку-триггер:
| Завершил шаг (фича/фикс/доработка) → коммит | `docs/rules/commits.md` |
Содержимое правила в AGENTS.md не копируй — только ссылку, AGENTS.md остаётся компактным.
```

## Безопасность ключей — что обязательно

```
Прогон проверок безопасности после настройки (выполняешь сам, я не набираю
ничего в терминал — только подтверждаю результат):

1. Права на приватный ключ (если SSH):
   ls -l ~/.ssh/id_ed25519
   # Должно быть -rw------- (chmod 600)
   # Если другие — chmod 600 ~/.ssh/id_ed25519

2. Папка ~/.ssh:
   ls -ld ~/.ssh
   # Должно быть drwx------ (700)
   # Если другое — chmod 700 ~/.ssh

3. ~/.ssh/ НЕ должна попадать в git проектов:
   В .gitignore любого проекта: ~/.ssh/ не должно быть, потому что её там и не
   будет (она вне проекта). НО — никогда не запускай git init в домашней папке.

4. Если работаешь на чужой машине / временной — не оставляй там приватный ключ.
   Удалить:
   ssh-add -d ~/.ssh/id_ed25519
   rm ~/.ssh/id_ed25519
   На GitHub удали соответствующий публичный ключ из Settings → SSH keys.

5. Если потерял ноут с ключом:
   - Я открою github.com/settings/keys в браузере и удалю публичный ключ
     потерянного ноута (это действие в браузере)
   - На новом устройстве AI сгенерирует новый ключ, я добавлю его на GitHub
     через ту же веб-форму
   - Аналогично — на VPS AI удалит старый ключ из authorized_keys и добавит
     новый, читая доступ из .env.deploy
```

## Edge cases

- Если у пользователя нет аккаунта GitHub — проведи через регистрацию (5 минут): https://github.com/signup
- Если уже была настроена аутентификация через `https` без gh — это работает только пока пароль/PAT не истёк. Переключение на SSH или gh — рекомендация
- Если первый коммит был в ветке `master` (старые версии git) — переименуй: `git branch -M main` перед push
- На Windows + WSL2 — ключ генерится в WSL, доступен оттуда. Из Windows-стороны (PowerShell) видно отдельные ключи. Обычно работаем только в WSL
- Если используешь несколько GitHub-аккаунтов на одной машине — настраивай через `~/.ssh/config` с разными хостами:
  ```
  Host github.com-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_personal
  Host github.com-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work
  ```
  И в repo: `git@github.com-personal:<user>/<repo>.git`
