# Концепции Git — наглядная HTML-страница

> **Цель:** пользователь понимает базовые понятия Git до первого push — не из стены текста в чате, а из одной наглядной HTML-страницы со схемами и примерами «было → стало». Читается один раз, открывается двойным кликом.

> Этот промт идёт **до** первого push на GitHub. Сначала разбираемся, что вообще такое, потом действуем.

---

## Промт

```
Собери одну HTML-страницу `git-intro.html`, которая наглядно и простыми словами
объясняет Git — будто я раньше не работал с системами контроля версий. Каждое
понятие — с маленьким примером и схемой прямо на странице (диаграммы рисуй через
HTML/CSS-блоки или inline SVG; графы коммитов можно как кружки на линии со
стрелками). Везде, где уместно, показывай «было → стало».

Что раскрыть:

1. Зачем Git вообще. История всех версий + страховка от потери. Аналогия с
   историей версий в Google Docs, только мощнее (сам выбираешь, когда сохранить,
   даёшь имя, делаешь параллельные ветки). Покажи на схеме «папка без Git
   (одна версия, перезаписал — потерял)» против «Git (цепочка сохранённых версий,
   можно вернуться к любой)».

2. Git ≠ GitHub ≠ GitLab — это РАЗНЫЕ вещи, объясни почему:
   - **Git** — сама система контроля версий, программа на твоём компьютере.
     Работает локально и без интернета.
   - **GitHub** и **GitLab** — это облачные хостинги репозиториев (remote): сайты
     компаний (GitHub — Microsoft, GitLab — отдельная компания), где лежит копия
     твоего репозитория + веб-интерфейс, issues, CI/CD, права доступа.
   - Связь: Git — инструмент, GitHub/GitLab — где хранится облачная копия. Можно
     пользоваться Git вообще без них; можно переехать с GitHub на GitLab — Git
     тот же. Покажи схемой: локальный repo (Git) ⇄ push/pull ⇄ remote (GitHub
     ИЛИ GitLab).
   - Дай маленькую таблицу GitHub vs GitLab (популярность/экосистема vs
     встроенный CI/CD и self-host) — коротко, без религии.

3. Базовые понятия, каждое с примером:
   - **Репозиторий** — проект целиком: файлы + вся история.
   - **Commit** — снимок проекта с именем. Покажи цепочку коммитов кружками на
     линии: `init → "added login" → "fixed style"`, и что к любому можно вернуться.
   - **Diff** — что именно изменилось между «до» и «после». Покажи мини-пример:
     слева старая строка (красным, `-`), справа новая (зелёным, `+`).
   - **Push** — отправить локальные коммиты на remote (GitHub/GitLab). Схема:
     3 коммита локально → push → они появились в облаке.
   - **Pull** — забрать коммиты из облака к себе. Схема в обратную сторону.
   - **Откат** — вернуть прошлое состояние. Покажи два случая: «отменить
     незакоммиченные правки» и «вернуться к старому коммиту». Подчеркни: в Git
     почти всё откатывается, паниковать не нужно; опасны только
     `reset --hard` и `push --force` без понимания.

4. Ветки — визуально (это главная часть):
   - **main** — основная линия, тут «рабочая, проверенная» версия.
   - Покажи граф: от main отходит ветка `feature-x`, в ней свои коммиты, main при
     этом не меняется. Нарисуй это как две линии со стрелками.
   - **Параллельная работа**: две ветки одновременно (`feature-login` и
     `fix-header`) растут независимо от main — покажи три линии рядом.
   - **Merge** — слияние ветки обратно в main: покажи, как линия `feature-x`
     вливается в main одним узлом-слиянием. Объясни ЗАЧЕМ так: эксперименты и
     новые фичи делаются в стороне, main всегда остаётся рабочим; если ветка не
     зашла — выбросил, main не пострадал; несколько людей/задач не мешают друг
     другу.
   - Отметь: в одиночной работе часто живёшь в main — это нормально; ветки
     нужны, когда пробуешь рискованное или ведёшь несколько задач сразу.

5. Типичный день: pull → правки → add → commit → push (короткая схема-цепочка).

6. Private vs Public репозиторий — коротко: Private по умолчанию, Public виден
   всему миру и попавший в историю секрет остаётся навсегда.

Сам реши, что ещё добавить для полноты картины.

Оформление:
- Один файл git-intro.html, все стили внутри, открывается двойным кликом.
- Весь контент в одном центрированном контейнере с равными отступами слева и
  справа (`max-width` + `margin: 0 auto` на одном общем родителе, например `<main>`).
- Наглядно и спокойно: заголовки, короткие блоки, схемы графов коммитов и веток,
  блоки «было → стало». Без стен текста.
- В конце — раздел с единой аналогией на весь материал (например, книга с
  историей версий и параллельными черновиками) и 3 вопроса на самопроверку
  («что такое commit», «чем push отличается от pull», «зачем нужны ветки и merge»).

Когда соберёшь файл, открой его в браузере и покажи результат.
```

## Что важно запомнить пользователю

- **Git ≠ GitHub/GitLab.** Git — система версий на твоём компьютере; GitHub и GitLab — облачные хостинги (remote), где лежит копия. Git работает и без них.
- **commit / push / pull** — три действия на 90% времени.
- **Ветки + merge** — эксперименты и фичи в стороне от main, main всегда рабочий. В одиночной работе можно почти всегда жить в main.
- **Откат** — в Git почти всё возвращается; опасны только `reset --hard` и `push --force` без понимания.
- **Private** по умолчанию.

## Edge cases

- Если пользователь уже знает Git — можно пропустить генерацию и сразу к первому push.
- На Windows + WSL2 концепции и команды те же.
- Если страница вышла перегруженной — попроси разнести на аккуратные секции с якорями-оглавлением сверху.
