# Шпаргалка-копипаст для деплоя на свой сервер

> **Цель:** простые, готовые к копипасту формулировки промтов для типовых сценариев деплоя. Не «настройка с нуля» (это отдельный промт), а **повседневные** команды: «обнови на сервере», «откати», «глянь логи», «перезапусти».

> Этот промт — справочник. К нему возвращаешься каждый раз когда хочешь что-то сделать на сервере, не вспоминая команды.

---

## Шпаргалка №1: Первый деплой проекта на твой сервер

Используется ОДИН раз — при первичной настройке деплоя. Если уже сделал — пропусти эту шпаргалку, она для понимания.

```
Я хочу поднять свой проект на VPS. Сначала создай файл ../../product/.env.deploy по шаблону с плейсхолдерами для доступа к серверу и скажи, что мне в нём заполнить:

SERVER_IP=
SERVER_USER=
SSH_KEY_PATH=~/.ssh/id_ed25519
GITHUB_URL=
DOMAIN=

После того как я заполню .env.deploy — прочитай его и сам подключись к серверу. В чат данные доступа я не ввожу, ничего в терминал тоже. Затем сделай первичную настройку: установи docker и docker-compose если их нет, создай папку /var/www/<project-name>, склонируй репозиторий из GITHUB_URL, создай docker-compose.yml + Dockerfile + deploy.sh + .env.production по нашему шаблону. Запусти контейнер, проверь что приложение отвечает на http://127.0.0.1:3000.

После настройки покажи мне:
- docker compose ps на сервере
- curl http://127.0.0.1:3000 (первые 20 строк ответа)
- список файлов в /var/www/<project-name>
```

## Шпаргалка №2: Обновить прод после правок (повседневный сценарий)

Самая частая команда. Используется каждый раз, когда хочешь увидеть свои правки на проде.

```
Я закоммитил и запушил изменения в main. Обнови прод-версию на сервере.

Шаги:

1. Прогон локального security-precheck (если настроен)

2. ssh на сервер, запуск /var/www/<project-name>/deploy.sh

3. После деплоя — curl https://<domain> для проверки что приложение
   отвечает 200 OK

4. Если упало — покажи docker compose logs --tail=50 web и предложи что
   починить, прежде чем запускать ещё раз

Ничего не пуш-ай в git без моего подтверждения. Не трогай миграции БД
без моего согласия (deploy.sh их сам применит, проверь логи что прошло).
```

Если у пользователя уже есть `../../product/scripts/deploy-remote.sh` — этот промт сводится к одному `(cd ../../product && ./scripts/deploy-remote.sh)`. Шпаргалка — для тех случаев, когда хочется чтобы Claude **сам прогнал** и проверил что вышло.

## Шпаргалка №3: Глянь логи / что-то сломалось

```
Сервис не отвечает / тупит / показывает ошибку. Помоги разобраться.

Что мне видно: <описание — например: "504 на /dashboard", "белая страница",
"Error 500 в Network tab DevTools", "просто не открывается">.

Сделай (подключаешься по SSH сам, доступ читаешь из .env.deploy):

1. ssh на сервер, docker compose ps — что в каком статусе

2. docker compose logs --tail=200 web — последние ошибки приложения

3. docker compose logs --tail=100 db — БД жива?

4. Если nginx не отдаёт — sudo journalctl -u nginx --since "10 minutes ago"

5. df -h и free -h — место на диске и память

6. Сформируй гипотезу что именно сломалось и предложи 1-2 варианта починки
   (от меньшего к большему: рестарт контейнера → пересборка → откат коммита)

Не делай fix-команд без моего "ок" — особенно `docker compose down`,
миграции, `git reset --hard`. На критичных шагах останавливайся и спрашивай.
```

## Шпаргалка №4: Откатить деплой к предыдущей версии

```
Последний деплой что-то сломал на проде. Нужно откатиться к предыдущему
рабочему коммиту прямо сейчас.

Шаги (на сервер подключаешься сам, доступ читаешь из .env.deploy):

1. ssh на сервер, cd /var/www/<project-name>

2. git log --oneline -5 — покажи мне последние коммиты, чтобы я выбрал
   до какого откатывать

3. После моего выбора (например, "откати к hash abc1234"):
   - git checkout <hash>
   - docker compose up -d --build (НЕ git pull — мы откатились)
   - проверь что https://<domain> отвечает 200

4. После подтверждения что прод работает — мне нужен ADR в
   ../../product/docs/memory/decisions/ с пометкой что был откат, причиной и какие коммиты
   были откачены

5. На локалке — git log <bad-hash>, объясни что было в плохом коммите
   и предложи как его переделать чтобы не повторить ошибку

Откат — временный костыль. Через ADR фиксируем причину, потом нормально
переписываем плохой коммит и катим заново.
```

## Шпаргалка №5: Подключить новый ENV-секрет на сервере

```
Я добавил новую переменную окружения в код (например, OPENROUTER_API_KEY).
Локально она работает (есть в .env.local). Нужно положить её на сервер.
Значение секрета я в чат не ввожу и в терминал не набираю.

Сделай:

1. Подключись по SSH (доступ из .env.deploy), открой
   /var/www/<project-name>/.env.production и добавь строку с плейсхолдером:
   <KEY>=
   Скажи мне: «открой .env.production на сервере и впиши значение в строку
   <KEY>=». Значение я впишу прямо в файл, тебе в чат не отправляю.

2. После того как я подтвержу что вписал — поставь права:
   chmod 600 .env.production (не должно быть group/world readable)

3. docker compose restart web — чтобы контейнер подхватил новую переменную

4. Проверь что приложение отвечает 200 после рестарта

5. Если фича, использующая этот секрет, имеет тестовый эндпоинт —
   проверь его одним curl

ВАЖНО: значение секрета у меня в чате не запрашивай и в саммари не выводи.
Только подтверди что записал и работает.
```

## Шпаргалка №6: Бэкап БД руками (внепланово)

```
Хочу сейчас сделать внеплановый бэкап БД, перед тем как пересобирать
схему / накатывать большую миграцию.

Сделай (подключаешься по SSH сам, доступ читаешь из .env.deploy):

1. ssh на сервер

2. /usr/local/bin/backup-db.sh (он создан на этапе БД)

3. ls -lh /var/backups/postgres | head -3 — покажи что свежий файл
   создался и какого размера

4. Подтверди что бэкап на месте — теперь можно делать рискованные операции

Если backup-db.sh ещё не существует — сначала создадим его (по образцу
из этапа БД), потом запустим.
```

## Шпаргалка №7: Сайт работает, но ТОРМОЗИТ — найти узкое место

Когда сервис не «упал», а медленный (TTFB секунды, страницы «висят»). На слабом VPS
это почти всегда память/swap. Быстрая диагностика (на сервер по SSH сам, доступ из `.env.deploy`):

```
Сайт открывается, но очень медленно (TTFB <N> сек). Подключись к серверу и найди
узкое место. Прогони и покажи мне вывод, потом сформулируй диагноз:

  free -h                      # RAM и swap: used почти всё + растёт swap → не хватает памяти
  vmstat 1 5                   # колонки si/so: НЕ нули → система активно свопит (это и есть тормоза)
  ps aux --sort=-%mem | head   # кто ест RAM (распух dockerd после сборки? один контейнер?)
  docker stats --no-stream     # память/CPU по контейнерам
  uptime                       # load average; > числа ядер → упор в CPU
  nproc                        # сколько ядер (на учебном VPS обычно 1)
  df -h                        # не забит ли диск (полный диск тоже тормозит и ломает сборки)

Типовой диагноз → что делать:
- swap идёт (si/so > 0) и dockerd на сотни МБ → раздулся после сборки на сервере.
  Лечение: docker builder prune -f, при раздутии sudo systemctl restart docker;
  по-нормальному — собирать образ в CI, а не на сервере (промты 04 и 05).
- один контейнер ест всю RAM → поставь/понизь ему mem_limit (промт 05 / Урок 4).
- памяти хватает, но load > числа ядер постоянно → упор в CPU, пора на VPS помощнее.
- диск забит (df -h ~100%) → почисти старые образы (docker image prune -a) и логи.

Сначала покажи цифры и диагноз — fix-команды (restart docker, prune) только после моего «ок».
```

> **Про размер VPS.** 1 ГБ / 1 vCPU — потолок для учебного проекта: приложение в нём
> живёт, но он становится узким на сборке образа (выносим в CI), тяжёлых запросах и
> росте трафика, больших миграциях, активном MinIO. Признак «пора на 2 ГБ+»: swap
> идёт постоянно (не только в момент деплоя) или регулярные OOM-kill контейнеров.

## Когда какая шпаргалка

| Сценарий | Шпаргалка |
|---|---|
| Первый раз поднимаю проект на новом VPS | №1 (детально настраиваем — основной промт деплоя) |
| Обычный деплой после правок | №2 |
| Что-то лежит, не понимаю почему | №3 |
| Только что задеплоил и сломал прод — откат | №4 |
| Добавил новый ENV (API key, секрет) | №5 |
| Перед опасной операцией с БД — внеплановый бэкап | №6 |
| Сайт работает, но тормозит (TTFB высокий, «висит») | №7 |

## Антипаттерны

- 🔴 Пушить любое изменение прямо в main без локального тестирования — на проде увидишь сломанное приложение
- 🔴 Делать `git reset --hard` на сервере «чтобы откатиться» — теряются возможные неподтянутые правки. Используй `git checkout <hash>` (детачнутый HEAD)
- 🔴 Хранить .env.production в git «потому что Claude его создал» — это ровно то, чего pre-deploy gate не пускает (правильно)
- 🔴 Делать миграции БД руками без бэкапа — даже если уверен. Бэкап через шпаргалку №6 — это две команды, цена очень низкая

## Edge cases

- Если у тебя нет домена (только IP) — везде где `<domain>` подставляй `<IP>`. Работает то же самое, только без HTTPS
- Если используется отличный от docker-compose стек (например, PM2 + node прямо) — формулировки те же, конкретные команды Claude адаптирует под твой `deploy.sh`
- Если на сервере несколько проектов — всегда указывай в промте конкретный путь `/var/www/<project-name>`, иначе Claude может перепутать
