# new-feature — наш универсальный промт разработки фичи

> **Универсальный промт.** Это наш собственный промт: он вбирает лучшее из подхода Claude-плагина `/feature-dev` (исследование кода → архитектура → реализация → ревью) и практик продакт-дискавери (Cagan, Jobs-to-be-Done, Shape Up, Teresa Torres). Работает под любым AI и не зависит от `.claude/` или установленных плагинов.
>
> На Claude Code этот промт можно обернуть в скилл `/new-feature` (вызов одной строкой, авто-триггеры, параллельные sub-агенты). На Codex / Cursor / любом другом AI — просто «прочитай этот файл и выполни». Логика одна и та же.

Промт из двух частей:
1. **Интервью** — поймать намерение и контекст (2-6 вопросов). Одинаково для всех.
2. **Реализация** — исследование → архитектура → код → ревью. Параллельно (если AI умеет sub-агентов) или последовательно (если нет).

---

## Шаг 0 — Определи, как будешь реализовывать

Часть 1 (интервью) одинаковая везде. Способ реализации в Части 2 зависит от твоих возможностей:

| Возможности AI | Способ реализации |
|---|---|
| Есть параллельные sub-агенты (Claude Code: `Agent` + `SendMessage` или `Task`) | Запусти роли параллельно (кодер + ревьюеры общаются между собой). Если доступен плагин `/feature-dev` — можешь делегировать ему фазы реализации, передав готовый бриф. |
| Параллельных агентов нет (Codex, Cursor, Aider и большинство) | Выполняй роли **последовательно в одном контексте**, явно меняя «шляпу»: исследователь → архитектор → кодер → ревью логики → ревью безопасности → тех-лид. Качество чуть ниже параллельного, но промт полноценный. |

Ни тот, ни другой путь не требует никаких внешних файлов ролей — все роли описаны прямо здесь, в Части 2.

---

## PRD-first: не пиши код без спецификации

Перед любой разработкой проверь, что поведение фичи описано. Источники правды: `../../product/docs/spec.md` (общая логика и модель данных), `../../product/docs/screens/<url>.md` (логика + раздел `## Визуал` конкретного экрана) и `../../product/docs/PRD.md` (продуктовый контекст).

| Что есть | Действие |
|---|---|
| `spec.md` / `screens/<url>.md` описывают эту фичу | Идём дальше: интервью → бриф → реализация |
| Спека есть, но фича / экран не описаны | Сначала допиши: общую логику — в `spec.md`, поведение и визуал конкретного экрана — в `../../product/docs/screens/<url>.md`, потом код |
| Спеки нет совсем | Предложи сначала собрать спеку. Минимум: что строим, для кого, зачем |

Меняешь экран — правишь его `../../product/docs/screens/<url>.md` в том же коммите, что и код (это же проверяет спека-гейт, он настраивается в Уроке 3). Разработка без спеки допустима только для мелких правок и багфиксов.

# Часть 1 — Интервью

## Принцип: спрашивай только то, что нельзя вывести самому

Ты сам можешь определить (НЕ спрашивай): файлы, архитектуру внутри уже выбранного стека, существующие паттерны, риски, сложность, подход к тестированию.

Спрашивай (это знает только пользователь и чего ещё нет в спеке): **что строим, что за рамками, как ведёт себя в крайних случаях**. Аудиторию, цель продукта и критерии успеха бери из `PRD.md`/`spec.md`, если они там есть — не переспрашивай.

**Про технологии — отдельно.** Если фича требует **новой** технологии, библиотеки или внешнего сервиса (новая БД, платёжка, очередь, авторизация, аналитика, Supabase/Firebase и т.п.) — не выбирай молча. Предложи разумный вариант по умолчанию и **спроси, подходит ли он или есть своё требование**. У пользователя может быть конкретное пожелание (например, «делаем на Supabase») — узнай его до реализации. Если стек проекта уже задан и фича в него вписывается — следуй ему, не переспрашивай.

## Протокол

- Один вопрос за раз. Жди ответа, потом следующий.
- Где возможно — предлагай 2-3 готовых варианта на выбор, чтобы не печатать много.
- Пропускай вопросы, на которые ответ уже есть в первом сообщении.
- Разговорный тон, без жаргона. 2-6 вопросов, меньше 5 минут.

Перед интервью быстро изучи проект (точки входа, похожие фичи, конвенции, модель данных) и прочитай `../../product/docs/spec.md`, `../../product/docs/screens/<url>.md` (если фича — экран) и `../../product/docs/PRD.md`. Аудитория, цель продукта и критерии успеха — продуктовый уровень, они уже описаны там: бери оттуда, **не переспрашивай**. Интервью нужно для пробелов конкретной фичи, которых в спеке нет.

### Вопросы (адаптивно, 2-6)

1. **Намерение** — что именно меняет эта фича. Возьми из `../../product/docs/screens/<url>.md` / `spec.md`, если описано, и подтверди одной формулировкой. Спрашивай заново, только если там пусто или размыто.
2. **Аудитория и критерии успеха** — обычно уже в `PRD.md`/`spec.md` (продуктовый уровень). НЕ спрашивай повторно — бери оттуда. Спрашивай, только если PRD/спеки нет вообще (greenfield без подготовки).
3. **Крайние случаи** — «Что происходит при пустом списке / ошибке / нет доступа / очень длинных данных?» Это чаще всего и не дописано в спеке экрана — главная польза интервью.
4. **Исключения** — «Что точно НЕ нужно включать?» (когда скоуп кажется широким).

Дальше 0-2 уточнения — только при двусмысленности, противоречии или критической неизвестной. После 6 вопросов собирай бриф с тем, что есть.

### Бриф и одобрение

Собери короткий бриф и покажи пользователю на подтверждение:

```markdown
# Бриф фичи: [название]

## Намерение
[что изменится, для кого, зачем]

## Аудитория
[кто пользуется]

## Критерии успеха
[конкретные, наблюдаемые: «пользователь может X», «на экране видно Y», «при Z происходит ...»]

## Исключения
[что НЕ строим]

## Контекст проекта
[стек, релевантные фичи, паттерны — из изучения проекта]

## Чеклист ревью
- [ ] [критерий 1]
- [ ] [критерий 2]
- [ ] исключения соблюдены
```

Спроси: «Вот план. Всё верно — запускаю?» Не начинай код, пока бриф не одобрен.

Сохрани бриф внутри проекта: `../../product/docs/briefs/[feature-name].md`. Никогда не клади брифы в корень.

# Часть 2 — Реализация

## Шаг 1: Сложность

| Уровень | Триггеры | Кто участвует |
|---|---|---|
| **SIMPLE** | 1-2 файла, один компонент, без новых зависимостей и миграций | кодер + один общий ревьюер (логика + безопасность вместе) |
| **MEDIUM** | 3-5 файлов, новые зависимости, затрагивает API или БД | кодер + ревью логики + ревью безопасности + тех-лид |
| **COMPLEX** | 6+ файлов, несколько доменов, миграции БД, auth/платежи | то же + разбивка на части + анализ рисков до кода |

MEDIUM/COMPLEX, если фича трогает auth, платежи, персональные данные, миграции БД, новые внешние API, несколько модулей, или может сломать существующие тесты.

## Шаг 2: План

Разбей бриф на конкретные задачи: какие файлы, что делать, зависимости между задачами. Для MEDIUM/COMPLEX — сначала покажи план пользователю.

## Шаг 3: Реализация ролями

Если есть параллельные sub-агенты — раздай роли агентам, пусть общаются между собой. Если нет — пройди роли **по очереди**, явно меняя «шляпу»:

1. **Исследователь** — прочитай 5-10 ключевых файлов: точки входа, похожие фичи, конвенции, откуда берутся типы. Выпиши паттерны, которым надо следовать.
2. **Архитектор** — предложи 2-3 варианта реализации (минимальный / чистый / прагматичный), выбери один с обоснованием.
3. **Кодер** — реализуй выбранный вариант, следуя найденным конвенциям.
4. **Ревью логики** — перечитай свой код по чеклисту брифа (критерии успеха, исключения), найди логические ошибки и edge cases.
5. **Ревью безопасности** — перечитай с фокусом на безопасность: доступ к чужим данным (IDOR), авторизация, секреты, инъекции, XSS. Сверься с правилами безопасности проекта.
6. **Тех-лид** (только MEDIUM/COMPLEX) — не противоречит ли решение прошлым архитектурным решениям, не плодит ли дублирование.

Критичные замечания (🔴) применяй сразу, остальные предложи пользователю.

## Шаг 4: Верификация

Перед тем как сказать «готово»:
1. Запусти код / тесты / dev-сервер.
2. Проверь, что работает.
3. Если веб-приложение — пройди путь пользователя в браузере.
4. Если есть тесты — убедись, что они проходят.

## Шаг 5: Итог

```markdown
## Результат: [фича]

**Статус:** готово / частично / не завершено
**Сложность:** SIMPLE / MEDIUM / COMPLEX

### Выполнено
- [задача] — готово

### Файлы
- [файл] — что изменено

### Ревью
- логика / безопасность / архитектура — статус

### Нерешённые вопросы
[если есть]
```

После реализации обнови спеку (`../../product/docs/spec.md`) и память проекта, если она заведена.

## Оформи это в инструмент — чтобы запускался сам по ключевым словам

Этот файл — рецепт. Чтобы он включался не только по «прочитай этот файл», но и сам, когда пользователь говорит «сделай фичу» / «добавь функцию», оформи его как инструмент. Сам рецепт держи в `../../product/prompts/new-feature.md` (едет с репо к команде), а механизм запуска зависит от AI:

**Claude Code → тонкая обёртка-скилл.** В корне воркспейса создай `.claude/skills/new-feature/SKILL.md` (не копию этого файла, а обёртку со ссылкой):

```
---
name: new-feature
description: Полный цикл разработки фичи — интервью (намерение, edge cases) → бриф → реализация ролями (исследование → архитектура → код → ревью логики и безопасности) со сверкой со спекой. Запускай, когда пользователь говорит «сделай фичу», «разработай», «добавь функцию», «новая функция», «реализуй», «давай обсудим перед реализацией».
---

# /new-feature

Прочитай рецепт `../../product/prompts/new-feature.md` и выполни.
Если в проекте есть плагин `/feature-dev` — на Шаге 3 (реализация) можешь делегировать ему фазы, передав готовый бриф из Части 1.
```

По `description` Claude подтянет скилл сам, когда задача под него подходит — без `/команды`.

**Codex / Cursor / другой AI → скиллов нет**, собираем аналог из этого же рецепта: добавь в `../../product/AGENTS.md` правило-триггер, которое по тем же ключевым словам читает и выполняет рецепт:

```markdown
## Разработка фичи — авто-запуск
Если пользователь говорит «сделай фичу» / «добавь функцию» / «реализуй» / «новая функция» — прочитай `prompts/new-feature.md` и выполни (интервью → бриф → реализация). Codex/Cursor читают AGENTS.md в начале каждой сессии — это и есть авто-триггер вместо скилла.
```
