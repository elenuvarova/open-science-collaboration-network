# Генерация экранов: кликабельный прототип с mobile + handlers + mock-state

> ⛔ **Этот этап — только локальный запуск, без выкладки наружу.** Единственный «запуск» здесь — `npm run dev` у тебя на компьютере (это разрешено и нормально). Нельзя: разворачивать приложение на хостинг/сервер (Vercel / Netlify / Render / VPS), подключать git-remote / GitHub, делать `git push`, запускать деплой-скиллы или предлагать деплой. Если кажется, что «ничего не задеплоено» — так и задумано: публикация в интернет, git и GitHub — отдельно, в Уроке 3.

Цель: для каждого экрана (список — в индексе `../../product/docs/spec.md`, детали — в `../../product/docs/screens/<url>.md`) создать рабочую страницу через UI-кит из `shared/ui/`, **сразу в двух версиях (mobile + desktop) в одном компоненте**, **с реальным handler на каждом интерактивном элементе** и **с локальным состоянием для интерактивности данных** (фильтры/сортировка/поиск через `useState` + filter/sort/search над моками). Не статическая вёрстка моков — рабочий продукт на mock-state.

Применяется дисциплина `../../product/docs/rules/prototype-interactivity.md`. Прочитай её прежде чем начнёшь — это критическая часть.

**Стек:** прочитай `../../product/docs/spec.md` раздел «Стек». Все упоминания shadcn, Tailwind, Radix в этом файле — дефолтный вариант. Если в spec.md указан другой стек — используй его.

## Проверка спеки перед стартом

Прежде чем генерировать экраны — убедись, что спека готова. Неполная спека даёт неполный экран.

**Пройди по каждому экрану (список — индекс в `spec.md`, детали — в `../../product/docs/screens/<url>.md`) и проверь:**
- Есть секция «Действия» — и она не пустая
- Каждое действие имеет конкретный результат: «Клик на "Сохранить" → переход на /dashboard» — не просто «Клик на кнопку»
- Нет строк вида «уточнить позже», «TBD», «?»

**Если что-то не заполнено — не начинай генерацию, пока не получишь ответ:**
- Предложи логику: «Вот эта кнопка "[название]" на экране "[экран]" — предлагаю [вариант]. Подходит?»
- Или спроси точно: «Что происходит при клике на "[элемент]" на экране "[экран]" — переходим куда-то или остаёмся?»

Одна неопределённая точка — вернись к спеке, не игнорируй.

## Главные правила

1. **Логика — из файла экрана `../../product/docs/screens/<url>.md`.** Состояния (default/loading/empty/error), действия, связи, валидация — оттуда; общие данные/доступы — из `spec.md`. Если чего-то нет — уточни, не придумывай самостоятельно.

2. **Визуал — из UI-кита + раздела `## Визуал` в `../../product/docs/screens/<url>.md`.** Все элементы через компоненты из `shared/ui/`. Никакого хардкода. Точные значения по каждому экрану берутся из того же файла, что и логика — раздел `## Визуал` (Layout Desktop, Layout Mobile, компоненты с привязкой к UI-киту, визуальные состояния, edge-cases). См. `../../product/docs/rules/figma-design-fidelity.md`.

3. **Mobile сразу с desktop, в одном компоненте.** Не «потом адаптируем» — оба варианта собираются за один проход через `md:` / `desk:` префиксы. Базовые классы — mobile-first, override через `md:` для desktop. Если в Figma есть отдельный мобильный фрейм — точные значения для mobile берутся из раздела `## Визуал → Layout Mobile` в файле экрана. Если нет — универсальные правила адаптации (грид → стек, меню → бургер, hover → tap, tap-таргеты ≥ 44×44 px).

4. **Каждый интерактивный элемент имеет handler.** `<Button>`, `<a>`, `<Input>`, `<Select>`, кликабельная `<Card>`, табы, переключатели — ни одного `onClick={() => {}}`, ни одного `<Input>` без `onChange`. Если реальной логики нет — mock-action с **видимой реакцией**: `router.push('/...')`, `setState`, `toast.info('В разработке')`. Не «пустой handler пока что» — это разваливает прототип.

5. **Интерактивность данных через mock-state.** Фильтры, сортировка, поиск, выбранные элементы, активные табы — через `useState`. Производные данные через `useMemo` + filter/sort/search над моками. Пользователь выбрал дату → состояние изменилось → видимый список перерендерился с другими элементами. Прототип реагирует на ввод, не статически рендерит моки. См. `../../product/docs/rules/prototype-interactivity.md`.

6. **Данные источник — моки.** Каждая страница использует моки из `entities/<entity>/api/mock-*.ts`. Хуки `useUser`, `useOrders` — обёртки над моками, чтобы при подключении БД заменить на реальные API без переписывания страниц.

7. **По одному экрану.** Не пытайся сгенерировать всё разом — будут поверхностные. Между группами экранов делай `/clear` для управления контекстом.

8. **Курсор на любом кликабельном элементе на экране.** Если на странице есть кастомный кликабельный `<div>` или `<a>` с переопределённым `cursor`, или ссылка ведёт через JS-навигацию, а не через `<a href>` — на нём должен быть `cursor-pointer`. Если элемент в `disabled`-состоянии — `cursor-not-allowed`. Это работает автоматически, если используешь компоненты из `shared/ui/` (они уже содержат курсоры в `cva()`). Подробнее: `../../product/docs/rules/ui-components-first.md` секция 2.1.

9. **Обвязка — в layout, не в странице. Навигация — через `<Link>`.** Меню, шапку (`Header`), сайдбар, подвал страница **не рендерит** — они уже живут в `../../product/src/app/(app)/layout.tsx` (см. `04-fsd-architecture.md`, Шаг 5.1). Страница — только свой контент. Так общая обвязка переживает навигацию и не перезагружается при каждом переходе. Все внутренние переходы — через `<Link href="/...">` из `next/link` (мягкая навигация + префетч + Router Cache), а не `<a href>` (он перезагружает всю страницу вместе с каркасом). `<a href>` — только для внешних ссылок. Навигация из обработчика — `router.push()`.

## Железное правило DESIGN.md → UIKit → Экран

Перед генерацией каждого экрана:

1. Нужен новый токен (цвет, шрифт, отступ)? → Сначала добавить в `../../product/docs/DESIGN.md`, потом использовать.

2. Нужен новый вариант компонента (кнопка другого цвета, карточка с акцентом)? → Добавить `variant` в `shared/ui/<component>.tsx`, потом использовать на экране.

3. На экране нужен элемент, которого нет в UIKit? → Создать новый компонент в `shared/ui/`, потом импортировать.

4. Отступы, gap, padding, ритм между секциями — **только из spacing-шкалы DESIGN.md** (именованные шаги xs/sm/md/lg/xl/2xl по их usage), а не произвольные Tailwind-значения «на глаз». Один и тот же тип отступа (padding карточки, gap между полями, разрыв секций) одинаков на всех экранах — это и держит единый вид. Нет подходящего шага → сначала добавь в DESIGN.md, потом используй.

**Запрещено:** хардкодить классы, хексы, отступы напрямую на странице или в виджете; брать отступы вне spacing-шкалы. Даже «временно». Экран целиком собирается из компонентов `shared/ui/` — никаких «почти как кит, но по-своему».

После каждого экрана — обязательный grep:

```bash
cd ../../product
grep -E '#[0-9a-fA-F]{3,8}|\[\d+px\]' src/pages/<screen>/
```

Если нашлось — не переходи к следующему экрану, поправь через токен или UIKit.

## Дисциплина интерактивности — обязательно (оба режима)

Применяется к каждому экрану независимо от пути работы с дизайном (A или Б/В). Закрывает три проблемы прототипа: «mobile не сделан», «кнопки не работают», «выбираю фильтр — ничего не меняется».

### Mobile одновременно с desktop

- **Один компонент, два набора классов.** Базовые классы — mobile values (mobile-first). Через `md:` / `lg:` — desktop overrides.
- **В режиме A:** Mobile-значения из раздела `## Визуал → Layout Mobile` в `../../product/docs/screens/<url>.md` (если в Figma есть отдельный мобильный фрейм). Если фрейма нет — TODO + спросить пользователя или применить универсальные правила.
- **В режиме Б/В:** Универсальные правила (грид → стек, меню → бургер, hover → tap, tap-таргеты ≥ 44×44 px, отступы меньше).
- **НЕ делай `MobileHero.tsx` + `DesktopHero.tsx`.** Один компонент, разные классы. Исключение — если в Figma структура реально разная (другой порядок секций), тогда два компонента в `widgets/` с `hidden md:block` / `md:hidden`.

### Handlers на каждом интерактивном элементе

После генерации каждого экрана прогон grep:

```bash
cd ../../product
# Пустые обработчики
grep -rE 'onClick=\{[()=>\s]*\}|onClick=\{undefined\}' src/pages/<screen>/

# <button> или <Button> без действия
grep -rE '<(button|Button)\b' src/pages/<screen>/ | grep -v 'onClick\|href\|type="submit"\|asChild'

# <Input> без onChange
grep -rE '<Input\b' src/pages/<screen>/ | grep -v 'onChange\|readOnly\|disabled'
```

Что-то нашлось — это баг прототипа, чини до перехода к следующему экрану. Если реальной логики ещё нет:

```tsx
// ✅ Mock-action c видимой реакцией
<Button onClick={() => toast.info('Покупка — в разработке')}>
  Купить
</Button>

// ✅ Навигация (если ведёт на другой экран по spec.md)
<Button onClick={() => router.push('/checkout')}>
  Купить
</Button>

// ✅ Локальный state
<Button onClick={() => setIsFavorite(!isFavorite)}>
  {isFavorite ? '★' : '☆'}
</Button>
```

### Mock-state для интерактивности данных

Для **каждого** экрана с фильтрами / сортировкой / поиском / выбором — `useState` для локального состояния + `useMemo` для производных данных от моков. Пример:

```tsx
function FlightSearch() {
  const [departureDate, setDepartureDate] = useState<Date>()
  const [from, setFrom] = useState('')
  const [to, setTo] = useState('')

  const filtered = useMemo(
    () => mockFlights.filter(f =>
      (!departureDate || isSameDay(f.date, departureDate)) &&
      (!from || f.from.includes(from)) &&
      (!to || f.to.includes(to))
    ),
    [departureDate, from, to]
  )

  return (
    <div className="grid grid-cols-1 md:grid-cols-[auto_1fr] gap-4">
      <Filters
        departureDate={departureDate} onDateChange={setDepartureDate}
        from={from} onFromChange={setFrom}
        to={to} onToChange={setTo}
      />
      <FlightList flights={filtered} />
    </div>
  )
}
```

Пользователь выбрал дату → `departureDate` изменился → `useMemo` пересчитал → список перерендерился. Прототип ведёт себя как продукт.

После сборки экрана проверь в браузере: открой экран, нажми каждую кнопку, измени каждый фильтр — UI должен **видимо** реагировать. Если что-то нажалось и ничего не изменилось — это баг (даже если state технически обновился).

### Прогон через Playwright MCP — обязательно три ширины

> **Не Claude Code (нет Playwright MCP)?** Тот же Playwright, но скриптом: AI пишет короткий скрипт (открыть страницу → viewport нужной ширины → скриншот в `../../product/docs/local-snapshots/`), запускает `npx playwright`, читает скриншоты. Результат тот же. В Cursor Playwright MCP можно подключить как в Claude Code.

После сборки каждого экрана (в обоих режимах):

```
browser_navigate("http://localhost:3000/<url>")
browser_resize(375, 800)  → browser_take_screenshot   # iPhone
browser_resize(768, 1024) → browser_take_screenshot   # iPad
browser_resize(1440, 900) → browser_take_screenshot   # Desktop
```

Все три скриншота должны быть «нормальными»: нет горизонтального скролла, нет вылезающего текста, грид/флекс переключаются корректно, кнопки и инпуты адекватной ширины.

В режиме A дополнительно: 1440px скриншот сверяется с Figma desktop frame, 375px — с Figma mobile frame (если есть).

## Подход в зависимости от выбранного пути работы с дизайном

### Режим A — Figma

В режиме A два подслучая (те же, что в `01-design-system.md`): **A1** — в Figma была библиотека компонентов; **A2** — только макеты. На этапе экранов **они собираются одинаково** — разница только в происхождении UI-кита (готовая библиотека / вычленен из макетов). Шаги ниже общие для обоих.

Для каждого экрана:

1. **`get_design_context` по `node-id` из `spec.md`.** Figma MCP вернёт **Tailwind-каркас** — это штатно, не ошибка. Каркас используешь как подсказку по layout, а сами кнопки/карточки/поля ставишь **своими компонентами из `shared/ui/`**. Точные размеры, отступы и состояния берёшь из раздела `## Визуал` файла `../../product/docs/screens/<url>.md` (Задание 5) и сверяешь с `get_screenshot` экрана как с эталоном.

   > Если на тарифе Org/Enterprise был настроен Code Connect (`03-code-connect.md`, опционально), этот вызов вернёт **готовый JSX с твоими `<Button>`, `<Card>`, `<Input>`** — тогда копируешь его как есть. Если Code Connect не настраивали (дефолт) — никакой ошибки в «голом» Tailwind нет, идёшь по обычному пути выше. **Не пытайся чинить Code Connect, если его не подключали.**

2. **Собирай экран из своих компонентов UI-кита.** Ставишь компоненты по `## Визуал` + скриншоту (или копируешь готовый JSX, если есть Code Connect). Никаких «адаптаций», «упрощений», «возьму за основу»: layout, отступы, gap, max-width — точно как в Figma.

3. **Перед сборкой — скачай все ассеты** этого экрана: пройдись по фрейму, через `get_screenshot` сохрани каждое изображение / иллюстрацию / иконку (не из lucide), gradient-фон. Складывай в `../../product/public/assets/<screen>/`. На экране используй пути `/assets/<screen>/<file>.png`. Без ассетов экран будет с битыми картинками — отдельная категория багов.

4. **Реализуй логику и состояния** из `spec.md` (default / loading / empty / error / success).

5. **Подключи моковые данные** через хуки (см. ниже эталон).

6. **После рендера экрана — обязательная визуальная сверка** (без неё экран не считается готовым):
   - `get_screenshot` Figma frame этого экрана (desktop) → сохрани в `../../product/docs/figma-snapshots/<screen>-desktop.png`
   - `get_screenshot` Figma mobile frame этого экрана (если есть в Figma) → сохрани в `../../product/docs/figma-snapshots/<screen>-mobile.png`. Если мобильного фрейма нет — пропусти, сравнение mobile будет с универсальной адаптацией
   - Открой локальный экран через Playwright MCP на двух ширинах: `browser_navigate("http://localhost:3000/<url>")` → `browser_resize(1440, 900)` → `browser_take_screenshot` (→ `<screen>-desktop.png`) → `browser_resize(375, 800)` → `browser_take_screenshot` (→ `<screen>-mobile.png`). Сохрани оба в `../../product/docs/local-snapshots/`
   - Сравни пары side-by-side. Сверь по чек-листу (для каждой пары — desktop и mobile):
     - [ ] Общий layout совпадает (что где находится)
     - [ ] Пропорции блоков совпадают (нет «случайно узкого блока на широком экране»)
     - [ ] Отступы между блоками совпадают
     - [ ] Padding внутри блоков совпадает
     - [ ] Цвета совпадают (фон, текст, акценты)
     - [ ] Типографика совпадает (размеры, веса)
     - [ ] Иконки и картинки на правильных местах правильного размера
     - [ ] Состояния (loading / empty / error) соответствуют тому что в Figma (если нарисованы)
     - [ ] **Mobile:** меню → бургер, грид → стек, hover-эффекты не используются, tap-таргеты ≥ 44×44 px
     - [ ] **Интерактивность:** нажатие любой кнопки даёт видимую реакцию (router.push / setState / toast), фильтры реально меняют список (mock-state работает)

   Если хоть один пункт расходится — **СТОП**. Не двигайся к следующему экрану. Спрашивай пользователя: «Вижу расхождение в [конкретно что]: Figma говорит [X], в коде получилось [Y]. Чиним токены / variant / layout / handler, или оставляем с обоснованием?» Жди ответа.

7. **Не считай экран готовым, пока:**
   - Скриншоты Figma vs local на обеих ширинах не совпадают
   - Все кнопки экрана нажимаются и дают видимую реакцию
   - Все фильтры / сортировка реально меняют выдачу через mock-state

### Режимы Б/В — без Figma

В режиме Б/В нет Figma для прямой сверки. Но **визуальная адекватность** всё равно обязательна — просто проверяется по другим критериям: разумные ожидания + responsive + extreme content.

Для каждого экрана:

1. **Прочитай раздел экрана в `spec.md`.** Особое внимание — на Layout (если задан): max-width контейнера, padding, gap, особенности адаптации. Если Layout не задан — спроси пользователя или используй разумные дефолты по типу экрана (form → max-width 480px, dashboard → container 1280px, full-bleed lendings → 100% с container padding).

2. **Если есть скриншоты / референсы** в `../../product/docs/screens/` — посмотри для понимания компоновки.

3. **Если пользователь дал ассеты** (картинки, иконки, иллюстрации) — скопируй их в `../../product/public/assets/<screen>/` сразу, до сборки экрана. Не пиши экран без ассетов «потом подложу» — забудется, останется placeholder.

4. **Реализуй экран** через компоненты UI-кита + Tailwind для layout (grid / flex / max-width / padding — см. правило `ui-components-first.md` секция «Tailwind vs Shared UI»).

5. **Реализуй все состояния** из `spec.md` (default / loading / empty / error).

6. **Подключи моковые данные** через хуки.

7. **После рендера — обязательный прогон через Playwright MCP** на трёх ширинах:
   - 320px (small mobile) — `browser_resize(320, 800)` → `browser_take_screenshot` → `browser_snapshot`
   - 768px (tablet) — `browser_resize(768, 1024)` → ...
   - 1440px (desktop) — `browser_resize(1440, 900)` → ...

8. **Чек-лист визуальной адекватности на каждой ширине** (все 3 ширины × все пункты):
   - [ ] Никакой текст не вылезает за пределы своего контейнера (включая длинные слова — `overflow-wrap: break-word`)
   - [ ] Никакой блок не оказывается мистически узким на широком экране (200px на 1440px viewport — почти всегда баг)
   - [ ] Никакой блок не оказывается мистически широким на узком экране (горизонтальный скролл — баг)
   - [ ] Грид/флекс переключаются корректно: 3 колонки → 2 → 1 при сужении (если уместно для типа контента)
   - [ ] Кнопки и инпуты не растягиваются на всю ширину там где не должны (form-кнопка может, кнопка-действие в шапке — нет)
   - [ ] Картинки масштабируются пропорционально, не растягиваются и не обрезаются неудачно
   - [ ] Длинный текст переносится, не обрезается, не выезжает за блок
   - [ ] Кнопки сохраняют достаточный размер для тапа на mobile (минимум 44×44px высота)
   - [ ] Карточки / блоки выровнены — нет случайно сдвинутых элементов
   - [ ] Sticky / fixed элементы (хедер, бургер, bottom-bar) не перекрывают важный контент

9. **Прогон с extreme контентом** — на одной из ширин (обычно 1440px):
   - Замени имя в моке на короткое («Иван») и на очень длинное («Александрина-Кристина Воронцова-Дашкова-Орлова») — экран должен выглядеть нормально на обоих. Если ломается — починить (truncate / multi-line / гибкий контейнер).
   - Замени список с 1 элементом и со 100 элементами — пагинация / скролл / sticky-элементы работают, layout не разваливается.
   - Пустой список → empty state виден и читаем (не пустой экран и не «0 элементов» мелким текстом).
   - Поле формы с очень длинным значением (email из 60 символов) — не выезжает.

10. **Если любой пункт чек-листа провален — СТОП.** Чини. Не двигайся к следующему экрану с поломанным текущим. Это самая частая причина того что прототип «выглядит сделанным», но при первой реальной проверке разваливается.

## Структура страницы (эталон)

> **Меню/шапки тут нет намеренно.** Эталон ниже — только контент экрана. Общая обвязка (`Header`, `Sidebar`, `Footer`) подключена один раз в `../../product/src/app/(app)/layout.tsx` и оборачивает все внутренние страницы; здесь её повторять не нужно (иначе она будет перемонтироваться на каждом переходе). Внутренние ссылки на эталоне — через `<Link>` из `next/link`.

```tsx
// ../../product/src/pages/profile/ui/ProfileScreen.tsx
'use client'

import { useUser } from '@/entities/user'
import { useOrders } from '@/entities/order'
import { Button } from '@/shared/ui/button'
import { Card } from '@/shared/ui/card'
import { Skeleton } from '@/shared/ui/skeleton'
import { EmptyState } from '@/shared/ui/empty-state'
import { ErrorState } from '@/shared/ui/error-state'

export function ProfileScreen() {
  const user = useUser()
  const { data: orders, isLoading, error } = useOrders()

  // loading state
  if (isLoading) return <Skeleton />

  // error state
  if (error) return <ErrorState onRetry={() => refetch()} />

  return (
    <div className="container mx-auto py-8">
      <Card variant="elevated">
        <h1 className="text-2xl font-semibold">{user.name}</h1>
        <p className="text-muted-foreground">{user.email}</p>
      </Card>

      <section className="mt-6">
        <h2 className="text-xl font-semibold">Мои заказы</h2>
        {/* empty state */}
        {orders.length === 0 && (
          <EmptyState
            title="У вас пока нет заказов"
            cta={<Button variant="primary" href="/shop">Сделать заказ</Button>}
          />
        )}
        {/* default state */}
        {orders.length > 0 && (
          <div className="grid gap-4 mt-4">
            {orders.map(order => <OrderCard key={order.id} {...order} />)}
          </div>
        )}
      </section>

      <Button variant="ghost" onClick={signOut}>Выйти</Button>
    </div>
  )
}
```

```ts
// ../../product/src/entities/user/api/mock-user.ts
import { User } from '../model/types'

export const mockUser: User = {
  id: 'u-001',
  email: 'user@example.com',

  role: 'user',
  createdAt: '2025-01-15T00:00:00Z',
}

// ../../product/src/entities/user/api/getUser.ts
import { mockUser } from './mock-user'

export async function getUser(): Promise<User> {
  // При подключении БД заменится на реальный fetch
  await new Promise(r => setTimeout(r, 300)) // имитация задержки
  return mockUser
}

// ../../product/src/entities/user/model/useUser.ts
import { useQuery } from '@tanstack/react-query' // или просто useState/useEffect
import { getUser } from '../api/getUser'

export function useUser() {
  const { data } = useQuery({ queryKey: ['user'], queryFn: getUser })
  return data
}
```

При подключении БД в `getUser.ts` `mockUser` заменится на `fetch('/api/user')` — страница не меняется.

## Подключение к Next.js routing

Для каждой страницы из `pages/` добавь тонкий адаптер в `../../product/src/app/`:

```tsx
// ../../product/src/app/(app)/profile/page.tsx — имя page.tsx обязательно (Next.js)
import { ProfileScreen } from '@/pages/profile'
export default ProfileScreen
```

**Корневая `/` — обязательно замени dev-редирект на настоящую главную.** В шаге UI-кита `../../product/src/app/page.tsx` был поставлен на редирект `/style-guide` (только в dev, в проде — заглушка). Когда генерируешь экран «главная» — **перезапиши `../../product/src/app/page.tsx` целиком** тонким адаптером на реальную главную продукта:

```tsx
// ../../product/src/app/page.tsx
import { HomeScreen } from '@/pages/home'
export default HomeScreen
```

Если по `spec.md` корень должен сразу вести на вход — поставь вместо адаптера `redirect('/login')`. После этого `/` показывает продукт и в dev, и в проде, а временный редирект на витрину исчезает. Сама витрина остаётся доступной по `/style-guide`.
