# Проверка прототипа — хардкод + запуск + кликабельность

> ⛔ **Этот этап — только локальный запуск, без выкладки наружу.** Единственный «запуск» здесь — `npm run dev` у тебя на компьютере (это разрешено и нормально). Нельзя: разворачивать приложение на хостинг/сервер (Vercel / Netlify / Render / VPS), подключать git-remote / GitHub, делать `git push`, запускать деплой-скиллы или предлагать деплой. Если кажется, что «ничего не задеплоено» — так и задумано: публикация в интернет, git и GitHub — отдельно, в Уроке 3.

Цель: убедиться что прототип чистый (всё через токены), запускается и **совпадает со спецификацией**.

## Шаг 0 — Спека синхронизирована с кодом

Здесь проверяем, что спека совпадает с кодом *по смыслу*. (В Уроке 3 появится спека-гейт — pre-commit хук, который не даёт закоммитить код без правки спеки; он ловит «забыл обновить». А этот шаг ловит другое — «обновил неправильно или неполно».)

Пройди по `../../product/docs/spec.md` и файлам `../../product/docs/screens/<url>.md`, сверь с кодом в `../../product/src/`:

1. **Экраны.** Каждый экран из индекса `spec.md` существует как слайс в `../../product/src/pages/`. Нет экранов в коде, которых нет в спеке (и наоборот).
2. **Поведение.** Действия и состояния из `../../product/docs/screens/<url>.md` (что по клику, состояния default/loading/empty/error, кто что видит) реализованы в коде. Нет поведения в коде, не описанного в спеке.
3. **Данные.** Поля и сущности из раздела «Данные» `spec.md` совпадают с моками в `entities/<entity>/api/`. Новых полей в моках, которых нет в спеке, быть не должно.
4. **Стек / адаптация.** Разделы «Стек» и «Адаптация» отражают то, что реально в проекте.

Любое расхождение — это либо код ушёл вперёд спеки (обнови спеку), либо спека описывает то, чего нет (доделай код или убери из спеки). Покажи пользователю список расхождений и что с каждым делаешь, и почини сразу же (git/коммиты — в Уроке 3, здесь просто правим файлы).

## Шаг 1 — Хардкод

Прогон grep по всему `src/`:

```bash
cd ../../product

# Хексы цветов
grep -rE '#[0-9a-fA-F]{3,8}' src/ \
  --include="*.tsx" --include="*.ts" --include="*.css" \
  | grep -v 'shared/ui/' \
  | grep -v 'DESIGN.md'

# Pixel-значения в квадратных скобках Tailwind
grep -rE '\[\d+px\]' src/ --include="*.tsx" --include="*.ts"

# Inline-стили
grep -rE 'style=\{\{' src/ --include="*.tsx"

# Конкретные шрифты в коде
grep -rE 'font-\[[A-Z]' src/ --include="*.tsx"
```

Что делать с находками:
- **В страницах / widgets / features:** заменить на токен из DESIGN.md или добавить вариант в компонент UI-кита
- **В `shared/ui/`:** допустимо, если это базовое определение компонента (но лучше тоже через токены)

Покажи пользователю список нарушений и план их исправления (что меняем на что).

## Шаг 2.5 — Курсоры на интерактивных элементах

```bash
cd ../../product
# Компоненты UI-кита — каждый <button> и интерактив должен иметь cursor-pointer
grep -rE "<button|onClick|onMouseDown" src/shared/ui/ --include="*.tsx" | grep -v "cursor-"
```

Каждая строка вывода — это интерактивный элемент без явного `cursor-pointer`. Tailwind 3+ убирает курсор-руку у `<button>` по умолчанию, и пользователь не понимает что элемент кликабельный. Добавь `cursor-pointer` в базовый класс компонента через `cva()`, плюс `disabled:cursor-not-allowed` для disabled-варианта.

То же для страниц — если в `pages/`/`widgets/`/`features/` есть кастомные кликабельные `<div>` с `onClick`:

```bash
cd ../../product
grep -rE "<div[^>]*onClick" src/pages/ src/widgets/ src/features/ --include="*.tsx" | grep -v "cursor-"
```

## Шаг 3 — FSD-импорты

Проверь что слайсы не импортят соседей на том же уровне:

```bash
cd ../../product
# features не импортят друг друга
grep -rE "from '@/features/" src/features/ | grep -v "from '@/features/index'"

```

Если найдено → пересмотри (общий код в entities или shared).

## Шаг 3.5 — Постоянная обвязка и навигация (меню не перезагружается)

Проверяем, что общая обвязка живёт в layout, а не дублируется по страницам, и что переходы — мягкие.

```bash
cd ../../product

# 1. Обвязка должна быть в (app)/layout.tsx — этот файл обязан существовать
ls src/app/**/layout.tsx 2>/dev/null || echo "НЕТ сегментного layout — обвязка скорее всего в страницах"

# 2. Header/Sidebar НЕ должны импортироваться внутри страниц/слайсов pages — только в layout
grep -rnE "from '@/widgets/(header|sidebar|footer)'" src/pages/ --include="*.tsx"
grep -rnE "<(Header|Sidebar|Footer)\b" src/pages/ --include="*.tsx"

# 3. Внутренние ссылки — через <Link>, а не <a href="/..."> (внешние http(s) — ок)
grep -rnE '<a [^>]*href="/' src/pages/ src/widgets/ src/features/ --include="*.tsx"
```

Что значат находки:
- Шаг 1 ничего не нашёл (`layout.tsx` отсутствует) → обвязка, скорее всего, лежит в страницах. Перенеси `Header`/`Sidebar`/`Footer` в `../../product/src/app/(app)/layout.tsx` (см. `04-fsd-architecture.md`, Шаг 5.1).
- Шаг 2 что-то нашёл → страница сама рендерит обвязку, она будет перемонтироваться при каждом переходе. Убери из страницы, оставь только в layout.
- Шаг 3 что-то нашёл → внутренняя ссылка через `<a href>` делает полную перезагрузку (каркас тоже перегружается). Замени на `<Link href="/...">` из `next/link`.

**Живая проверка в браузере (обязательно):** открой приложение, переключись между 2–3 внутренними страницами и смотри на меню/шапку. Меню **не должно** мигать или перерисовываться — меняется только контент. Если меню «вспыхивает» при каждом переходе — обвязка не в layout или навигация идёт через `<a href>`. В DevTools → Network при переходе по `<Link>` не должно быть запроса документа целиком (`document`), подтягиваются только данные/сегмент.

## Шаг 4.5 — Визуальная сверка экранов (блокирующая)

Эта проверка **обязательна** для каждого экрана. Не «когда успею» — это блокер: пока не пройдено, прототип не считается готовым.

Метод зависит от того, по какому режиму шёл пользователь (A или Б/В).

> **Не Claude Code (нет Playwright MCP)?** Везде ниже, где `browser_navigate` / `browser_take_screenshot` — замени тем же Playwright скриптом: AI пишет короткий скрипт (открыть страницу → viewport нужной ширины → скриншот в `../../product/docs/local-snapshots/`), запускает `npx playwright`, читает скриншоты. Результат тот же. В Cursor Playwright MCP можно подключить как в Claude Code.

### Если режим A (Figma)

Для каждого экрана из `spec.md`:

1. Возьми сохранённые на этапе `06-screens.md` скриншоты:
   - `../../product/docs/figma-snapshots/<screen>.png` — Figma
   - `../../product/docs/local-snapshots/<screen>.png` — локальный рендер

2. Если каких-то скриншотов нет — пересоздай:
   - `get_screenshot` Figma frame экрана
   - Playwright MCP: `browser_navigate("http://localhost:3000/<url>")` → `browser_take_screenshot`

3. Открой пары side-by-side. Сверь по чек-листу:
   - [ ] Общий layout совпадает
   - [ ] Пропорции блоков совпадают (нет неожиданно узких или широких блоков)
   - [ ] Отступы между блоками и padding внутри блоков совпадают
   - [ ] Цвета совпадают
   - [ ] Типографика совпадает (размеры, веса, line-height)
   - [ ] Иконки и картинки на правильных местах правильного размера

4. Любое расхождение по layout / пропорциям / отступам / цветам / шрифтам — **баг, фиксируй и чини**. Не пропускай «незаметные» расхождения — на масштабе всего продукта они складываются в «выглядит криво».

### Если режим Б/В (без Figma)

Для каждого экрана из `spec.md` — прогон через Playwright MCP на трёх ширинах:

```
browser_resize(320, 800)  → browser_take_screenshot
browser_resize(768, 1024) → browser_take_screenshot
browser_resize(1440, 900) → browser_take_screenshot
```

На **каждой** ширине пройди чек-лист адекватности:
- [ ] Никакой текст не вылезает за пределы своего контейнера
- [ ] Никакой блок не оказывается мистически узким на широком экране
- [ ] Никакой блок не оказывается мистически широким на узком экране (нет горизонтального скролла)
- [ ] Грид / флекс переключаются корректно при сужении
- [ ] Кнопки и инпуты адекватной ширины (form-кнопки full-width, action-кнопки нет)
- [ ] Картинки масштабируются пропорционально
- [ ] Длинный текст переносится, не обрезается
- [ ] Тач-таргеты ≥ 44×44px на mobile
- [ ] Sticky / fixed элементы не перекрывают важный контент

Прогон с **extreme контентом** (на 1440px):
- [ ] Короткое имя («Иван») и длинное («Александрина-Кристина Воронцова-Дашкова») — оба корректно
- [ ] Список с 1 элементом и со 100 элементами — оба корректно
- [ ] Пустой список → empty state виден и читаем
- [ ] Длинный email / длинное значение в поле формы — не выезжает

Любой провал — фиксируй и чини. Не двигайся дальше с поломанным экраном.

## Шаг 7 — Цветовые пары и читаемость

Убедись, что цвета из `DESIGN.md` обеспечивают достаточный контраст. Минимум по WCAG AA:
- **4.5 : 1** — для текста < 18px и **< 14px bold**
- **3 : 1** — для крупного текста (≥ 18px или ≥ 14px bold) и UI-элементов

```bash
cd ../../product
# Если установлен линтер:
npx @google/design.md lint docs/DESIGN.md

# Или проверь ключевые пары вручную на contrast-ratio.com:
# Открой docs/DESIGN.md → найди primary + on-primary, foreground + background
```

Что должно быть в `DESIGN.md` для каждого цвета:
```yaml
colors:
  primary: "#1A1C1E"
  on-primary: "#FFFFFF"    ← цвет текста поверх primary
  background: "#FFFFFF"
  foreground: "#1A1C1E"   ← цвет текста поверх background
```

Если нет `on-*` токенов — добавь их в `DESIGN.md` прямо сейчас. Это базовая гарантия читаемости.

## Шаг 8 — Анимации и переходы

Проверь, нет ли хардкода длительностей анимаций:

```bash
cd ../../product

# Хардкод duration прямо в классах Tailwind
grep -rE 'duration-\[[0-9]+ms\]' src/ --include="*.tsx"

# Хардкод в CSS transition
grep -rE 'transition:[^;]+[0-9]+ms' src/ --include="*.css" --include="*.scss"
```

Если находки есть — выбери три стандартных значения и добавь в `DESIGN.md`:

```yaml
animation:
  duration-fast: 150ms    # hover, мелкие эффекты
  duration-normal: 250ms  # появления, скрытия
  duration-slow: 400ms    # сложные transitions, модалки
```

После этого в коде используй CSS-переменные вместо конкретных цифр:
```tsx
className="transition-opacity duration-[var(--animation-duration-normal)]"
```

Проверь также: нет ли у тебя анимаций которые нужно отключать при `prefers-reduced-motion`:
```bash
grep -rE '@media.*prefers-reduced-motion' src/ --include="*.css"
```

Если анимаций нет — пропусти. Если есть motion-heavy компоненты — добавь базовое:
```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; }
}
```

## Шаг 9 — Тёмная тема (если планируется)

Если в `DESIGN.md` или `spec.md` указана тёмная тема — проверь что архитектура готова.

**Проверка 1:** `tailwind.config` содержит `darkMode: 'class'`

```bash
cd ../../product
grep "darkMode" tailwind.config.* 2>/dev/null || echo "darkMode не настроен"
```

**Проверка 2:** В компонентах используются `dark:` классы, а не хардкод

```bash
cd ../../product
# Хардкод цветов в dark:-вариантах (нарушение)
grep -rE 'dark:.*#[0-9a-fA-F]' src/ --include="*.tsx"

# Правильно — токены:
# dark:bg-background-dark или dark:text-foreground-dark
```

**Проверка 3:** Все color-токены из DESIGN.md имеют dark-варианты

```bash
cd ../../product
# Ищем on-* токены в DESIGN.md
grep "on-" docs/DESIGN.md | head -10
```

Если тёмная тема не планируется — пропусти этот шаг, отметь в `state.md`:
```
Тёмная тема: не планируется в v1.0
```
