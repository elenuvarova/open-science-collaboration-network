# Поэкранный контракт — `docs/screens/<url>.md` (логика + визуал)

> ⛔ **Этот этап — только локальный запуск, без выкладки наружу.** Единственный «запуск» здесь — `npm run dev` у тебя на компьютере (это разрешено и нормально). Нельзя: разворачивать приложение на хостинг/сервер (Vercel / Netlify / Render / VPS), подключать git-remote / GitHub, делать `git push`, запускать деплой-скиллы или предлагать деплой. Если кажется, что «ничего не задеплоено» — так и задумано: публикация в интернет, git и GitHub — отдельно, в Уроке 3.

**Обязательный промежуточный шаг между FSD-структурой и генерацией экранов в любом режиме (A с Figma или Б/В без Figma).** Превращает обзорную карту `screens-map.md` в подробный контракт **по каждому экрану**: на каждый экран один файл `../../product/docs/screens/<url>.md` с **логикой** (доступ, данные, состояния, действия, связи, валидация) и **визуалом** (раздел `## Визуал` — как экран должен выглядеть). До того как пишется первая строка JSX.

**Принцип «один файл на экран».** Если поэкранных файлов ещё нет (на продуктовом этапе собрали только `screens-map.md`) — этот промт **создаёт их** из карты + `spec.md` (логика), а затем дописывает в тот же файл раздел `## Визуал` (Layout Desktop / Mobile, маппинг компонентов на UI-кит, визуальные состояния). Если файлы уже есть — логику не трогаем, только добавляем визуал. Двух источников правды по одному экрану не бывает: логика и визуал лежат в одном файле.

Без визуального контракта экраны собираются «по интерпретации» (читаем логику, дорисовываем визуал «как обычно бывает»), и результат расходится с задуманным: не та позиция элементов, не тот календарь, чужой sidebar, съехавшие модалки.

## Когда этот промт пропускается

**Никогда** — если в проекте есть UI, визуальный контракт обязателен. Раньше шаг пропускался в режиме Б/В (без Figma), но это давало те же расхождения «как AI понял» что и пропуск в режиме A. Теперь:

- **Режим A (с Figma):** раздел «Визуал» заполняется через `mcp__figma__get_design_context` + `mcp__figma__get_screenshot` по каждому экрану
- **Режим Б (свой дизайн без Figma):** раздел «Визуал» заполняется через **интервью с пользователем** по каждому экрану + скриншоты-референсы если есть
- **Режим В (без дизайна вообще):** раздел «Визуал» заполняется через **интервью с пользователем** + универсальные дефолты на «решай сам» с явной пометкой

## Предусловия

- Есть `../../product/docs/screens-map.md` (карта экранов с продуктового этапа). Поэкранные файлы `../../product/docs/screens/<url>.md` либо уже есть, либо будут созданы здесь из карты — наличие самих файлов не обязательно, обязательна карта
- DESIGN.md готов (`01-design-system.md`)
- UI-кит в `shared/ui/` собран (`02-ui-kit.md`)
- **Режим A:** Figma MCP подключён со ссылкой на файл. Code Connect (`03-code-connect.md`) — опциональный (только Org/Enterprise) и для раздела `## Визуал` не нужен: layout/размеры/состояния читаем через `get_design_context` + `get_screenshot`, это работает на любом тарифе
- **Режим Б/В:** пользователь готов отвечать на вопросы про каждый экран
- FSD-структура папок создана (`04-fsd-architecture.md`)

## Параметры

| Параметр | Значение |
|---|---|
| `<frontend-dir>` | `../../product/` (относительно папки, где лежит этот промт) |
| Источник списка экранов | индекс «Экраны» в `../../product/docs/spec.md` |
| Куда дописывать визуал | **в существующий файл** `../../product/docs/screens/<url>.md` — новый раздел `## Визуал` |
| Куда сохранять Figma-скриншоты (только режим A) | `../../product/docs/figma-snapshots/<screen-slug>.png` |
| Куда сохранять скриншоты-референсы (режим Б, если есть) | `../../product/docs/screens-references/` |

## Алгоритм

1. **Зафиксируй список экранов и заведи поэкранные файлы.** Прочитай индекс экранов в `../../product/docs/spec.md` и карту `../../product/docs/screens-map.md`. На каждый экран нужен отдельный файл `../../product/docs/screens/<url>.md` с **логикой** (доступ, данные, состояния, действия, связи, валидация).
   - **Если файла ещё нет** (на продуктовом этапе собрали только `screens-map.md`, без поэкранных файлов) — **создай его**: возьми экран из `screens-map.md` + общие разделы из `spec.md` (данные, доступы, роли) и разверни в полноценную поэкранную спеку — доступ / данные / состояния (default · loading · empty · error · success) / действия по элементам / связи с другими экранами / валидация форм. По одному файлу на экран, в папке `../../product/docs/screens/`. Пробел, которого нет ни в карте, ни в спеке → `TODO: <что> + вопрос пользователю`.
   - **Если файл уже есть** — используй как есть, логику не переписывай.
   Итог в обоих случаях одинаковый: на каждый экран один файл `../../product/docs/screens/<url>.md` с логикой, в который ниже допишем раздел `## Визуал`. Так screens-map (обзорная карта) превращается в подробный контракт по каждому экрану.

2. **В режиме A — проверь Figma node-id** в каждом файле экрана (поле «Источник»). Если у какого-то экрана `node-id` нет — спроси пользователя.

3. **Покажи карту пользователю**: «Покрываем эти N экранов: [список]. Подтверди или скажи что добавить/убрать». Жди ответа.

4. **Для каждого экрана в цикле — режим A:**
   - `mcp__figma__get_design_context(nodeId)`
   - `mcp__figma__get_screenshot(nodeId)` → сохрани в `../../product/docs/figma-snapshots/<screen-slug>.png`
   - **Открой существующий файл** `../../product/docs/screens/<url>.md` и **допиши в конец** раздел `## Визуал` по шаблону ниже
   - Деталь не нарисована в Figma → `TODO: <что именно> + вопрос пользователю`

5. **Для каждого экрана в цикле — режим Б/В:**
   - Если есть скриншот-референс — посмотри, опиши вслух что видишь, перепроверь с пользователем
   - **Структурированное интервью** по блокам шаблона:
     - «Layout Desktop: max-width контейнера, сетка, padding, sticky элементы?»
     - «Layout Mobile: то же что desktop с переключением, или другая структура? Меню → бургер? Грид → стек?»
     - «Компоненты экрана по порядку сверху вниз — название, размер примерно, цвет (token), что внутри, какая иконка»
     - «Визуальные состояния: что показываем в loading / empty / error — иконка/текст/CTA?»
     - «Edge cases визуально: длинный текст, пустой список, 100 элементов?»
   - **Записывай по ходу разговора** в раздел `## Визуал` файла `../../product/docs/screens/<url>.md` — не «потом запишу»
   - Пользователь говорит «решай сам / как обычно» — применяй разумные дефолты (грид → стек на мобильном, меню → бургер, hover → tap, tap-таргеты ≥ 44px, токены из DESIGN.md), но **явно помечай в секции** что это AI-решение, чтобы пользователь видел где принимать решение

6. **Большой `get_design_context` (>50 KB)** — если ответ Figma слишком большой для одного контекста, запусти sub-агента (Claude Code: `Task`) который прочитает design context одного экрана и вернёт сжатую выжимку (Layout + компоненты + визуальные состояния), а не сырой JSON. В Codex без sub-агентов — обрабатывай экраны по одному, не загружая все сразу.

7. **После цикла — обязательно спроси пользователя «Что упустил?»** Это критическая точка валидации до кода. Часть багов с интерпретацией ловится здесь.

## Шаблон раздела «Визуал» (дописывается в `../../product/docs/screens/<url>.md`)

```markdown
## Визуал

**Скриншот-референс:** `../../product/docs/figma-snapshots/<screen-slug>.png` (режим A) или `../../product/docs/screens-references/<slug>.png` (режим Б, если есть)

### Layout Desktop
- Контейнер: max-width, padding, gap
- Сетка / колонки
- Sticky-элементы (header / sidebar)
- Hover-стейты ключевых элементов

### Layout Mobile (≤640px)
- Что меняется: сетка → стек, меню → бургер и т.д.
- Tap-таргеты ≥ 44px
- Что скрывается / сворачивается

### Компоненты (сверху вниз)
- `<имя>` → UI-кит компонент `shared/ui/<Name>` (вариант, размер, токены)
- ...

### Визуальные состояния
- **default:** ...
- **loading:** скелетон / спиннер / что именно
- **empty:** иконка + текст + CTA
- **error:** иконка + текст + кнопка повтора

### Edge cases визуально
- Длинный текст: усечение / wrap / tooltip
- Пустой список / 100+ элементов: пагинация / виртуализация / scroll

### Открытые вопросы / TODO
- TODO: ...
```

## Жёсткие правила

**Режим A** — применяется дисциплина `../../product/docs/rules/figma-design-fidelity.md`:
- Точные значения из Figma, не «примерно»
- Запрещённые слова: «адаптируй», «возьми за основу», «по образу», «упростим», «как обычно делается»
- Деталь не в Figma → TODO + вопрос, не угадывание

**Режим Б/В** — те же запрещённые слова применяются:
- Не «как обычно делается» а «по такому-то правилу из DESIGN.md» или «вот так, по решению пользователя»
- Деталь не описана пользователем → TODO + вопрос, не молчаливый дефолт
- Каждое AI-решение по дефолту явно помечено в секции, чтобы пользователь видел где принимать решение

В обоих режимах применяется дисциплина `../../product/docs/rules/prototype-interactivity.md`:
- Раздел «Визуал → Компоненты» в каждом экране заполняется явно: что за компонент, на какой компонент из UI-кит маппится
- Mobile-вид описан так же подробно как desktop

## После выполнения

- В каждом `../../product/docs/screens/<url>.md` есть раздел `## Визуал` с layout, компонентами, состояниями
- В режиме A — папка `../../product/docs/figma-snapshots/` содержит PNG-скриншот на каждый экран
- Все TODO либо разрешены через ответы пользователя, либо явно перечислены
- Пользователь подтвердил «всё покрыто, можно собирать»

Покажи пользователю:
- Превью разделов `## Визуал` из 2–3 файлов `../../product/docs/screens/<url>.md` (первые 50 строк каждого)
- В режиме A — `ls ../../product/docs/figma-snapshots/` (скриншоты на месте)
- Список открытых TODO (если есть)
