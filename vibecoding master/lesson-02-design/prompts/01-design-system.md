# Дизайн-система — DESIGN.md

> ⛔ **Этот этап — только локальный запуск, без выкладки наружу.** Единственный «запуск» здесь — `npm run dev` у тебя на компьютере (это разрешено и нормально). Нельзя: разворачивать приложение на хостинг/сервер (Vercel / Netlify / Render / VPS), подключать git-remote / GitHub, делать `git push`, запускать деплой-скиллы или предлагать деплой. Если кажется, что «ничего не задеплоено» — так и задумано: публикация в интернет, git и GitHub — отдельно, в Уроке 3.

Цель: собрать `../../product/docs/DESIGN.md` в формате Google Labs `design.md` — палитра цветов, типографика, скругления, отступы, тени, базовые компоненты с состояниями. Состав и количество ступеней каждой шкалы — **под выбранную стилистику и референс**, не по фиксированному шаблону.

> 📘 **Что такое токен.** Дизайн-токен — это именованное значение дизайн-системы: вместо `#1A1C1E` пишем `primary`, вместо `16px` пишем `spacing-md`, вместо `Inter 14px / 600` пишем `text-action-m`. Один токен → одно имя → используется везде через ссылку. Меняешь значение в DESIGN.md — обновляется во всём UI автоматически. Без токенов каждый цвет / отступ / шрифт пришлось бы менять в 50 местах вручную.
>
> Откуда берутся токены: в Figma они называются **variables** (переменные Figma), в DESIGN.md и Tailwind — **токены** (design tokens), в CSS они становятся **CSS-переменными** (`--color-primary`). Это один и тот же концепт на разных уровнях.

## Шаг 0 — Какой режим (один вопрос, обязательный)

Не предполагай и не выбирай за пользователя. Спроси одним сообщением:

> «Прежде чем собрать DESIGN.md — три варианта в зависимости от того, что у тебя уже есть:
>
> **1. Есть отдельная дизайн-система в Figma** — страница "Foundations" / "Library" / "Design System" с настроенными variables (цвета, шрифты, отступы) → я вытащу всё оттуда через MCP, 1:1 перенос.
>
> **2. Есть Figma с макетами**, но отдельной DS нет → я посмотрю на твои макеты, определю стилистику (цвета, шрифты, радиусы, ритм) и сгенерирую DS на основе того, что вижу.
>
> **3. Figma нет или хочешь начать с чистого листа** → задам несколько вопросов про стилистику (направление, цвета, тёмная/светлая тема, шрифт-пара) и сгенерирую подробную DS.
>
> Какой вариант твой? (1 / 2 / 3)»

Если пользователь сразу ответил материалами раньше в сессии (например, дал Figma на продуктовом этапе) — всё равно подтверди: «вижу что у тебя есть Figma, в ней отдельная страница Foundations с variables, или DS не выделена?» Не угадывай.

> ⚠️ Для режимов 1 и 2 нужен подключённый Figma MCP. Проверь наличие инструментов `mcp__figma__*`:
> 1. Попроси у Figma MCP `whoami`. Если работает — продолжай.
> 2. Если нет — закрой Claude Code (Cmd+Q) и открой заново. Reload Window часто не подхватывает MCP.
> 3. Если после рестарта всё ещё нет — выключи и включи Figma-плагин через `/plugin` (disable/enable).

## РЕЖИМ 1 — Есть отдельная DS в Figma (variables / Foundations)

### Шаг 1 — Берём переменные из Figma

**Какую ссылку дать:** ссылка на страницу `Foundations` (или `Library` / `Design System` — название зависит от файла), где хранятся variables. Если variables живут на уровне файла без отдельной страницы — дай ссылку на весь файл.

Как получить ссылку: в Figma Desktop выдели страницу `Foundations` в левой панели → ПКМ → Copy link to selection. Кинь её в чат.

Если такой страницы нет, но в файле точно настроены variables (видны в Figma → Local variables panel) — дай ссылку на файл целиком, MCP возьмёт variables независимо от выделения.

Через Figma MCP:

1. `get_variable_defs` — получи все переменные из Figma файла (цвета, размеры шрифта, скругления, отступы). Эта команда читает variables на уровне всего файла, выделение не влияет.

2. `get_libraries` — узнай какие библиотеки подключены (если variables приходят из внешней Library)

3. Сохрани сырой ответ в `../../product/docs/figma-variables-raw.json` для истории

**Если `get_variable_defs` возвращает пусто:** значит в Figma не настроены variables — только raw styles. Тогда:
- Сообщи пользователю «в Figma не настроены variables. Могу переключиться на Режим 2 (определю стилистику из макетов) или Режим 3 (интервью с нуля). Какой ближе?»
- Дальше следуй по выбранному режиму

### Шаг 2 — Маппим в формат `design.md`

Преобразуй извлечённые variables в YAML front-matter формата Google Labs:

```yaml
---
name: <название-продукта>
colors:
  primary: "<hex из Figma>"
  on-primary: "<hex>"
  background: "<hex>"
  foreground: "<hex>"
  ...
typography:
  display-lg:
    fontFamily: <Font Name>
    fontSize: 48px
    fontWeight: "700"
    lineHeight: 56px
  ...
rounded:
  sm: 0.25rem
  DEFAULT: 0.5rem
  lg: 1rem
spacing:
  unit: 8px              # базовый ритм — всё кратно ему (8/16/24/32/40…)
  xs: 4px                # внутри компонента: иконка ↔ текст
  sm: 8px                # между близкими элементами
  md: 16px               # между элементами в блоке
  lg: 24px               # padding карточки, между блоками
  xl: 40px               # между секциями
  "2xl": 64px            # крупные секции / лендинг
  container-padding: 24px  # боковые поля контейнера (mobile — меньше, напр. 16px)
  # значения шагов зависят от «Плотности»: компактная → меньше, просторная → больше
components:
  button-primary:
    backgroundColor: "{colors.primary}"
    textColor: "{colors.on-primary}"
    rounded: "{rounded.DEFAULT}"
---
```

### Шаг 3 — Markdown body в каноничном порядке

После YAML — markdown в 8 разделов:

```markdown
## Overview
[Brand & Style — характер, отсылки, для кого]

## Colors
[Палитра, использование, контраст]

## Typography
[Шкала шрифтов, использование]

## Layout
[Spacing scale с **usage** — что каким шагом: внутри компонента / между элементами / между блоками / между секциями / поля контейнера, + 1–2 примера («карточка: padding lg, gap между полями md»; «секции лендинга разделяются xl–2xl»). Выбранная **Плотность** (компактная / просторная / очень просторная) и как она влияет на шаги. Grid и max-width контейнера. Это контракт, по которому строятся ВСЕ экраны — без него отступы гуляют от экрана к экрану.]

## Elevation & Depth
[Shadows, blur, layering]

## Shapes
[Rounded corners, borders]

## Components
[Button, Card, Input — описание поведения]

## Do's and Don'ts
[Что можно, что нельзя]
```

### Шаг 4 — Проверка формата (внутренний шаг, не показывать пользователю)

```bash

```

## РЕЖИМ 3 — С нуля по интервью

### Шаг 1 — Собрать стилистику (8 тем, каждая отдельным вопросом)

Пройди 8 тем стилистики — **каждая отдельным сообщением**, по одному вопросу за раз. После каждого ответа извлеки и запиши в `../../product/docs/design-decisions.md`, переходи к следующей теме. На неполный/валидный ответ — используй разумный default (например, светлая тема + Inter + умеренные скругления + просторная плотность), не докручивай. Если пользователь говорит «не знаю» по конкретному пункту — в том же сообщении предложи 3 варианта на выбор и иди дальше после ответа.

**Темы по порядку** (формулируй вопросы сам в разговорном тоне, не копируй буквально):

1. **Стилистика / характер.** Минимал (Apple) / Brutalist (Linear) / Soft (Notion) / Playful (Duolingo) / Corporate (Stripe) / Cyber (Vercel) / свой гибрид

2. **Brand color.** Один акцентный цвет (hex или «как у X»: Notion, Linear, Spotify, Stripe…)

3. **Тема.** Только светлая (default) / только тёмная / обе (тогда нужны `light` + `dark` пары для всех токенов)

4. **Шрифт-пара.** Inter (default универсал) / Geist (Vercel-modern) / Manrope (геометр) / Space Grotesk (характер) / JetBrains Mono как акцент / своя пара (например Playfair + Inter) / другие бесплатные подходящие шрифты google font. Подключай выбранный шрифт через **`next/font`** (в `app/layout.tsx`) — он самохостит шрифт, грузит без блокировки рендера и без скачка вёрстки (CLS). Не подключай шрифт `<link>`-ом на Google CDN — это медленнее и даёт прыжок текста при загрузке.

5. **Скругления.** Острые (0–2px) / умеренные (6–8px) / мягкие (12–16px) / pill (9999px)

6. **Плотность.** Компактная (Linear, Notion) / просторная (Apple, Stripe) / очень просторная (лендинги)

7. **Тени.** Плоский / лёгкие тени карточек / выраженные тени модалок и поповеров

8. **Референсы (опц.).** 1–3 продукта-ориентира — Linear / Notion / Stripe / Apple / Discord / Vercel / Figma / Spotify / Duolingo / Arc / Raycast

### Шаг 2 — Сборка DESIGN.md

Собирай DESIGN.md под выбранную стилистику и референс (см. секцию «Полнота DESIGN.md» ниже — там логика, как определять объём шкал). Не делай универсальный шаблон «N токенов на всё».

Правила сборки:
- **Цвета** — палитра идёт от референса и характера бренда. Сколько ступеней neutral, нужно ли semantic, есть ли отдельные hover/active токены — решается под стилистику. Тёмная тема — только если выбрана в Шаге 1.
- **Типографика** — уровни, которые реально понадобятся продукту (например, для дашборда: h1/h2/body/caption + mono. Для лендинга: + display).
- **Spacing — это контракт, а не одно число.** Из выбранной «Плотности» собери **именованную шкалу** (xs/sm/md/lg/xl/2xl в px, всё кратно базовому ритму) и **обязательно пропиши usage** — какой шаг где: внутри компонента, между элементами, между блоками, между секциями, поля контейнера — с 1–2 примерами. Без шкалы с usage экраны берут отступы «на глаз» и расходятся между собой. Компактная плотность → меньше шаги; просторная → больше. Радиусы/тени — тоже от характера.
- **Components** — описываются те, что реально нужны: button + input + card как обязательный минимум, остальное (badge, modal, popover) — если в продукте есть.

Lint: `npx @google/design.md lint ../../product/docs/DESIGN.md`

## Полнота DESIGN.md — главный принцип

**DESIGN.md должен содержать всё, что понадобится при сборке экранов** — не больше и не меньше. «Больше» — это лишний шум, «меньше» — это сочинение токенов на лету при сборке экранов, что запрещено.

Конкретный набор и количество ступеней **определяется источником**, не фиксированным шаблоном. Минимально-универсальных «N радиусов» или «N оттенков» здесь нет.

### Откуда берётся набор токенов

| Откуда работаем | Откуда берётся набор |
|---|---|
| **Режим 1** (готовая DS в Figma) | 1:1 переносим, что есть в variables. Сколько ступеней у дизайнера — столько и в DESIGN.md. Ничего не выдумываем сверху, ничего не выкидываем. |
| **Режим 2** (Figma с макетами) | Извлекаем по факту использования в макетах. Если в макетах встречается 4 радиуса — фиксируем 4. Если 7 — фиксируем 7. Анализируешь `get_design_context` фреймов и собираешь реально встречающиеся значения. |
| **Режим 3** (с нуля по интервью) | Объём шкалы выбирается **под стилистику** (см. ниже). Сразу спрашиваешь у пользователя референс. |

### Режим 3 — спроси референс перед сборкой шкал

Прежде чем собирать шкалу цветов / типографики / радиусов / spacing — задай **один уточняющий вопрос** (даже если пользователь уже ответил на 8 вопросов из интервью выше):

> «Перед сборкой шкал — есть продукт, дизайн-систему которого хочешь взять за референс по плотности и набору токенов?
>
> Примеры:
> - **Linear / Notion** — компактные, узкая палитра, ровно столько токенов сколько нужно (минимализм)
> - **Stripe / Vercel** — средняя плотность, развёрнутая типографика, тонкие тени
> - **Apple / Things** — широкая spacing-шкала, лёгкие тени, мягкие радиусы, выраженная иерархия типографики
> - **Material Design / Google** — широкая палитра (10+ ступеней neutral), много semantic ролей, чёткие elevation-уровни
> - **Tailwind defaults / shadcn** — стандартный современный набор без сильного характера
> - Свой вариант — назови продукт или скажи "минимум, ничего лишнего"»

На основе референса определяешь количество ступеней:

- **Минимализм (Linear-стиль):** 3–4 neutral оттенка / 4 уровня типографики / 3 радиуса / компактный spacing scale
- **Средний (Stripe/Vercel):** 5–7 neutral / 5–6 уровней типографики / 4–5 радиусов / умеренный spacing
- **Богатый (Material/Google):** 9–11 neutral / 6+ уровней типографики / 5–6 радиусов / расширенный spacing + elevation

Это **ориентиры**, не догмы. Окончательное количество диктует стилистика + что реально нужно экранам продукта.

### Цвета — ДВА уровня: примитивы → семантические роли (обязательно)

Палитру всегда строим в два уровня — это и есть «правильная сборка»:

1. **Примитивы (palette)** — сырые именованные значения: `slate-50…900`, `blue-50…900`, при необходимости `green`/`amber`/`red` ступени. Здесь живут **уникальные hex** (одно значение = один примитив), и больше нигде hex не повторяется.
2. **Семантические роли** — **ссылки на примитивы по смыслу, без дублирования значений**: `background → white`, `foreground → slate-900`, `primary → blue-600`, `border → slate-200`, `status-done → green-800`. Роль не содержит hex — она указывает на примитив.

Компоненты используют **только семантические роли** (`bg-primary`, `bg-card`, `text-foreground`), никогда примитивы напрямую. Выгода: перекрасить продукт = поменять, на какой примитив смотрит роль (в одном месте); тёмная тема = те же роли на другие примитивы. В DESIGN.md и в CSS держим оба уровня — примитивы как значения, роли как ссылки (`--primary: var(--blue-600)`). В витрине Foundations они и показываются двумя блоками: «Примитивы (значения)» и «Семантические роли → примитив (ссылки)».

### Что должно быть **в любом случае** (независимо от режима и стилистики)

Это не про количество, а про **роли** — без них любой UI-кит не соберётся:

- **Surface roles** — `background`, `foreground`, `muted`, `muted-foreground`, `border`, `card`, `card-foreground`, `popover`, `popover-foreground`, `input`, `ring` (focus-ring). Это **роли**, которые shadcn ожидает увидеть. Сколько hex-значений за ними — это уже про стилистику.
- **Brand** — основной цвет + контрастный текст на нём (`primary` + `primary-foreground`). Состояния hover/active решаются либо отдельными токенами, либо `color-mix()` / `opacity` в коде — зависит от стилистики.
- **Semantic** — `success`, `warning`, `error`, `info` (каждый парой `<name>` + `<name>-foreground`) **только если в продукте есть соответствующие состояния**. Если в spec.md нет уведомлений и форм с ошибками — semantic не обязателен.
- **Если в Шаге 1 выбрана тёмная тема (или обе)** — каждое цветовое значение дублируется парой `light`/`dark`. Если только light — это явно фиксируется (`dark mode: not supported` в YAML).
- **Типографика** — минимум `body` + хотя бы один уровень заголовка. Сколько именно уровней (h1/h2/h3/display и т.д.) — от стилистики.
- **Spacing** — base unit + явная шкала, на которую можно ссылаться по имени. Размер шкалы — от стилистики.
- **Радиусы** — хотя бы один `DEFAULT`. Дополнительные ступени — если в стилистике встречаются.
- **Тени** — хотя бы одна, если в продукте есть card / popover / modal. Если flat-стилистика — теней может вообще не быть, фиксируется `elevation: flat`.
- **Z-index** — явный набор слоёв ровно под те UI-organisms, что будут в продукте (modal, popover, toast, dropdown — берём из списка компонентов в `02-ui-kit.md`).
- **Animation** — хотя бы одна `duration` + один `easing`, если в стилистике предполагаются переходы. Иначе фиксируется `motion: none`.

### Финальная сверка перед сдачей DESIGN.md

После сборки выведи пользователю не «количества», а **что покрывает каждая категория** — чтобы было видно, под какие сценарии система готова:

> «DESIGN.md готов. Что покрывает:
> - **Цвета** (<режим> темы): brand для акцентов, neutral для текста и фонов (<N> ступеней), surface roles (card/popover/border/ring), semantic — <перечисли какие> или «нет» если не нужны для этого продукта
> - **Типографика**: <уровни через запятую — display/h1/h2/body/caption или что вышло>
> - **Радиусы**: <ступени или "плоский: без скруглений"> 
> - **Spacing**: base unit <Xpx>, шкала <ступени>
> - **Тени**: <ступени или "flat: без теней">
> - **Z-index**: <слои>
> - **Анимации**: <длительности или "motion: none">
> - **Component refs**: <какие компоненты в YAML — button, card, input, ...>
> - **Lint**: passed»

Если пользователь видит, что какая-то категория «не покрывает» нужный сценарий — добавляем токены сейчас, не на этапе экранов.

## После выполнения (общее для всех режимов)

1. Покажи пользователю финальный `DESIGN.md` целиком.

2. Покажи вывод lint.

3. Краткое summary в зависимости от режима:
   - **Режим 1**: «Переменные взяты из Figma. Если в макете что-то поменяется — перегон через get_variable_defs ещё раз.»
   - **Режим 2**: «Стилистика определена по макетам. Если что-то нужно скорректировать — правь DESIGN.md напрямую.»
   - **Режим 3**: «Дизайн-система собрана с нуля по интервью. Это стартовая точка — можешь править токены, всё подхватится автоматически.»

## Правила

- DESIGN.md — это **контракт**. Любая правка дизайна → правка DESIGN.md сразу же (git/коммиты — в Уроке 3).
- Никаких хексов вне DESIGN.md. Каждый цвет в коде ссылается на токен.
