# PWA — manifest.json, иконки, service worker

> **Пути (монорепо после `00`).** PWA (manifest + service worker + офлайн) ставится в приложение **продукта** (`../../product/development/apps/app/...`) — устанавливают и используют офлайн сам сервис, а не лендинг. Лендинг и его страница-редирект — в `../../product/development/apps/landing/...`. Если монорепо-сплит был пропущен — замени `development/apps/app/` (и `development/apps/landing/`) обратно на корень продукта (`../../product/...`).

## Что такое PWA

Progressive Web App — веб-приложение которое можно «установить» на главный экран телефона/десктопа. Выглядит как нативное приложение, но это твой веб.

Минимум для PWA:

1. HTTPS (есть после деплоя)

2. `manifest.json` с описанием и иконками

3. Service Worker (даже пустой)

4. Подключение к HTML head

### Куда открывается приложение: `start_url` и `scope`

Это ключевой момент, и он зависит от выбора в Задании 1.1 (`03-app-domain.md`) — продукт на подстранице или на поддомене.

**Вариант «подстраница» (`/` — лендинг, `/app` — продукт, один домен) — дефолт ниже:**

- **`start_url`** — что открывается по тапу на иконку установленного приложения. Ставим `/app` (сам продукт), а не `/` (лендинг). Иначе при каждом запуске будет мелькать продающая страница, и приложение не ощущается нативным. Установленная иконка должна открывать сразу сервис.
- **`scope: "/"`** — какие URL считаются «внутри» приложения. Оставляем весь домен (`/`), чтобы переходы на лендинг/блог/`/pricing` открывались в окне приложения, а не выкидывали во внешний браузер. Сужать scope до `/app` не нужно — это ломает навигацию на публичные страницы.
- **`id: "/app"`** — стабильный идентификатор установки. Фиксируем его явно, чтобы при будущих правках `start_url` система не считала это «другим приложением» и не плодила дубли установки.

Лендинг при этом остаётся на `/` для тех, кто заходит из браузера, и для SEO. `start_url` (точка входа иконки) и `/` (маркетинговая страница) — две независимые вещи.

**Вариант «поддомен» (продукт на `app.<домен>`):** манифест обслуживает поддомен, продукт лежит в его корне, поэтому `start_url: "/"`, `scope: "/"`, `id: "/"` — всё относительно `app.<домен>`. Автоматическое переключение лендинг ↔ приложение ниже не нужно: лендинг и продукт уже разведены по хостам, а редиректы между ними настроены в Задании 1.1. Дальше в этом промте бери только манифест, иконки, service worker и проверку установки.

### Автоматическое переключение лендинг ↔ приложение

> Только для варианта «подстраница» (один домен). Если продукт на поддомене `app.<домен>` — этот раздел пропусти: лендинг и приложение уже разведены по хостам, а редиректы между ними настроены в Задании 1.1 (`03-app-domain.md`).

Цель: один домен сам отдаёт нужное нужной аудитории. Три слоя, и все автоматические:

1. **Залогинен** — заходит на `/`, сервер сразу редиректит в `/app` (серверный редирект на странице лендинга). Лендинг видят только те, у кого ещё нет аккаунта.
2. **Запущено как установленное приложение** — даже если человек внутри PWA попал на `/` (например, тапнул лого), страница определяет режим запуска и уводит в `/app`. Режим виден только в браузере, поэтому это маленький клиентский компонент.
3. **Не залогинен и зашёл на `/app`** — guard из Урока 4 (`middleware.ts`) отправляет на `/login`. Лендинг тут не показываем — раз человек целится в приложение, ведём его на вход.

Серверный редирект на лендинге (`/`):

```tsx
// ../../product/development/apps/landing/src/app/page.tsx — лендинг (серверный компонент)
import { redirect } from 'next/navigation'
import { getSession } from '@/shared/lib/auth'

export default async function LandingPage() {
  const session = await getSession()
  if (session) redirect('/app')      // залогинен → сразу в продукт
  return (
    <>
      <PwaRedirect />                  // запущено как PWA → тоже в продукт
      <Landing />
    </>
  )
}
```

Определение запуска из установленного PWA (клиентский компонент):

```tsx
// ../../product/development/apps/landing/src/app/_components/pwa-redirect.tsx
'use client'
import { useEffect } from 'react'
import { useRouter } from 'next/navigation'

export function PwaRedirect() {
  const router = useRouter()
  useEffect(() => {
    const isStandalone =
      window.matchMedia('(display-mode: standalone)').matches ||
      (window.navigator as any).standalone === true   // iOS Safari
    if (isStandalone) router.replace('/app')
  }, [router])
  return null
}
```

Итог: иконка установленного приложения открывает сразу `/app`; залогиненный пользователь с `/` тоже попадает в продукт; гость из браузера видит лендинг; гость, целящийся в `/app`, попадает на `/login`. Никаких ручных переключателей — всё решается по контексту запуска и авторизации.

## Шаг 3 — Service Worker

Самый простой — через `next-pwa` библиотеку:

```bash
npm install next-pwa
```

```ts
// ../../product/development/apps/app/next.config.js
const withPWA = require('next-pwa')({
  dest: 'public',
  register: true,
  skipWaiting: true,
  // офлайн-фолбэк: если страница недоступна в сети и нет в кэше — отдаём /offline
  fallbacks: { document: '/offline' },
})

module.exports = withPWA({
  // обычные настройки Next.js
})
```

Это сгенерирует `../../product/development/apps/app/public/sw.js` автоматически.

### Стратегия кэширования (что кэшируем, что всегда свежее)

`next-pwa` из коробки подбирает стратегию по типу ресурса (`runtimeCaching` из `next-pwa/cache`), и менять её обычно не нужно — но важно понимать логику, она ровно про «статика не качается заново, а контент остаётся живым»:

- **Статика (JS-бандлы, CSS, шрифты, иконки, картинки)** — `CacheFirst` / `StaleWhileRevalidate`: берётся из кэша service worker мгновенно, по сети не качается повторно. Имена файлов с хэшем, поэтому устаревания нет — новый деплой = новые имена.
- **HTML-страницы и API (`/api/*`, данные)** — `NetworkFirst`: всегда тянем свежее из сети, кэш только как fallback (например, когда офлайн). Так контент и данные не «залипают» в кэше.

Не накрывай `CacheFirst`-ом HTML и API — иначе пользователь увидит устаревшие данные после деплоя. Если кастомизируешь `runtimeCaching` — оставь этот принцип: хэшированная статика кэшируется агрессивно, контент/данные — network-first.

> **Кэш service worker и кэш nginx/CDN не конфликтуют, а дополняют друг друга:** nginx (Урок 3) кэширует статику на сервере, service worker — в самом браузере и даёт офлайн-режим. Оба отдают `/_next/static/` надолго, потому что имена файлов хэшированные.

### Офлайн и кэш — для ВСЕХ посетителей, не только для установленного PWA

Важно: service worker регистрируется у любого, кто открыл сайт в браузере, — не только у тех, кто «установил» приложение. Поэтому офлайн-режим и мгновенная отдача из кэша работают и на обычном заходе через браузер, и на основном домене, и в установленном PWA одинаково. Что закладываем:

- **Офлайн-фолбэк `/offline`.** Заведи простую страницу `../../product/development/apps/app/src/app/offline/page.tsx` (логотип, «Нет сети — часть данных доступна из кэша», кнопка «Обновить»). Через `fallbacks.document` (выше) её отдаёт service worker, когда страницы нет ни в сети, ни в кэше.
- **Прекэш оболочки и ключевых маршрутов.** `next-pwa` прекэширует собранные ассеты автоматически; дополнительно убедись, что лендинг и основные экраны продукта (`/app`, ключевой раздел) уже посещены/прогреты, чтобы открывались офлайн. Для критичных публичных страниц можно добавить их в `runtimeCaching` со `StaleWhileRevalidate`.
- **Данные — `StaleWhileRevalidate`, чтобы переключение было мгновенным.** Для GET-запросов отображаемых данных (списки, профиль) отдаём из кэша сразу и параллельно обновляем в фоне — пользователь видит контент без ожидания сети, свежие данные подтягиваются следом. Изменяющие запросы (POST/PUT/DELETE) и приватное — только сеть, не кэшируем.

```ts
// пример кастомного runtimeCaching (../../product/next.config.js, в опциях next-pwa)
runtimeCaching: [
  { urlPattern: ({request}) => request.destination === 'document',
    handler: 'NetworkFirst', options: { cacheName: 'pages' } },
  { urlPattern: /\/api\/(feed|catalog|profile)/,           // отображаемые GET-данные
    handler: 'StaleWhileRevalidate', options: { cacheName: 'data' } },
  { urlPattern: /\/_next\/static\//,
    handler: 'CacheFirst', options: { cacheName: 'static' } },
]
```

### Быстрое переключение страниц (в браузере и в PWA)

Скорость переходов даёт не PWA, а архитектура Next.js App Router — и она работает в обычном браузере тоже:

- **Общие элементы — в layout, а не в каждой странице.** Навигация, sidebar, шапка, провайдеры состояния живут в `layout.tsx` соответствующего сегмента. При переходе между дочерними роутами layout НЕ размонтируется → общие элементы не перерендериваются заново, переключение мгновенное. Не дублируй nav/sidebar в каждой `page.tsx` (см. правило shared-layout из Урока 5).
- **`<Link>` с префетчем.** Внутренние переходы — через `next/link`: Next.js префетчит код и данные целевого роута, пока человек ещё на текущей странице. К моменту клика страница уже почти готова.
- **Данные из кэша (SWR / React Query).** Оборачивай клиентские данные в SWR или TanStack Query с кэшем — повторный заход на экран отдаёт данные из памяти мгновенно, обновление идёт в фоне. Это и есть «часть данных остаётся в кэше, чтобы переключение было быстрым».

Проверь после сборки: при переходах между разделами общая навигация/сайдбар не мигает и не перерисовывается, а данные ранее открытого экрана показываются сразу.

## Шаг 6 — Push-уведомления (если пользователь подтвердил)

Web Push позволяет слать уведомления, даже когда вкладка закрыта — через service worker и сервис доставки браузера. Бесплатно, без сторонних сервисов, на стандарте Web Push + VAPID.

**Что нужно знать до старта:**

- **iOS — только установленный PWA.** На iPhone push приходит лишь если приложение добавлено на главный экран (iOS 16.4+). В обычном Safari-табе push на iOS не работает. На Android/Desktop — работает и в браузере.
- **Разрешение спрашиваем по действию пользователя**, а не на загрузке. Запрос прямо при входе → человек жмёт «Блокировать», и второго шанса нет. Сначала свой мягкий пре-промт («Включить уведомления о X?»), и только после согласия — системный `Notification.requestPermission()`.
- **Подписку храним на сервере.** `PushSubscription` (endpoint + ключи) сохраняем в БД, привязав к пользователю, чтобы потом слать.

## После реализации

1. Покажи пользователю установленный PWA на телефоне (или эмуляторе)

2. Проверь:
   - Manifest работает (открой `your-domain.com/manifest.json`)
   - Service Worker зарегистрирован (DevTools → Application)
   - PWA устанавливается на iOS и Android

3. Проверь точку входа по выбранному в Задании 1.1 варианту:
   - **подстраница:** установленное приложение по иконке открывается сразу на `/app`; залогиненный с `/` попадает в `/app`; гость из браузера на `/` видит лендинг; гость на `/app` уходит на `/login`.
   - **поддомен:** иконка открывает корень `app.<домен>` (сам продукт); лендинг живёт отдельно на основном домене; вход на лендинге переносится на поддомен через общую cookie.

4. Проверь офлайн и кэш (в обычном браузере, не только в установленном PWA): в DevTools → Network включи Offline, перезагрузи — ранее открытые страницы отдаются из кэша, недоступные показывают `/offline`. Переключения между разделами мгновенные, общая навигация не перерисовывается.

5. Зафиксируй в `spec.md` раздел «PWA»: что поддерживаем, версия manifest, выбранный `start_url` (`/app` для подстраницы или `/` для поддомена), как устроено переключение лендинг ↔ приложение, офлайн-стратегия и (если делали) push.
