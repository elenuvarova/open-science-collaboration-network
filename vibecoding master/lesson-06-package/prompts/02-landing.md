# Лендинг под сервис

## Когда делать

Если продукт публичный — лендинг полезен. Если внутренний инструмент — пропустить.

## Где живёт

После монорепо-сплита (`00-monorepo-split.md`) лендинг — это **отдельное приложение** `../../product/development/apps/landing/`, которое деплоится независимо от сервиса и импортит общие токены/компоненты из `@repo/ui` (`packages/ui`). Сервис живёт в `apps/app`. Адреса (один домен или поддомен) — по выбору из `03-app-domain.md`:
- `/` — лендинг (публичный, `apps/landing`)
- `/login`, `/signup` — auth (на стороне сервиса)
- `/app` (или поддомен `app.`) — сам продукт за логином (`apps/app`)

> Если сплит пропущен (внутренний продукт) — лендинг просто роут `/` (группа `(public)`) в одном приложении; пути ниже тогда читай как `../../product/src/...`.

## Производительность (лендинг должен открываться мгновенно)

Лендинг — первое, что видит посетитель, поэтому он должен быть лёгким и кэшируемым:

- **Серверный компонент, статический рендер.** Не вешай `'use client'` на всю страницу — держи лендинг серверным компонентом, чтобы Next.js отрендерил его статически (один HTML на всех). `'use client'` — только на мелких интерактивных кусках (мобильное меню, аккордеон FAQ), вынесенных в отдельные компоненты. Статический HTML лендинга кэшируется на nginx/CDN, и повторные заходы открываются мгновенно.
- **Картинки через `next/image`.** Hero-изображение, логотипы, скриншоты — через `<Image>` с `priority` для Hero (остальные ленивые). Никакого голого `<img>`. Форматы webp/avif и нужные размеры — это уже настроено в Уроке 2 (оптимизация картинок).
- **Навигация и CTA через `<Link>`.** Кнопка signup и якорные ссылки — `<Link href="/signup">` из `next/link`: переход в продукт уже префетчится, пока человек читает лендинг, и открывается мгновенно. `<a href>` — только для внешних ссылок.
- **Минимум клиентского JS.** Тяжёлые украшения (анимационные библиотеки, 3D, карусели) подключай через `next/dynamic`, чтобы они не блокировали первую отрисовку.

## Правило — DESIGN.md → UIKit → Лендинг

Лендинг строится по тому же принципу что и весь продукт:

1. Все токены (цвета, шрифты, отступы) — из `DESIGN.md`, общий слой темы — из `@repo/ui` (`packages/ui`). Не хардкодить.

2. Базовые UI-элементы — из `@repo/ui` (единый источник с сервисом). Блок, специфичный только для лендинга (Hero, PricingCard, ProductShowcase) → создать в самом лендинг-приложении `apps/landing/src/widgets/landing/`. Базовый переиспользуемый элемент, нужный и сервису → добавить в `@repo/ui`, потом использовать в обоих.

3. Нет нужного токена в DESIGN.md → сначала добавить туда (и в тему `@repo/ui`), прогнать lint, потом использовать.

## Дизайн: нешаблонно, но в рамках бренда

Лендинг — это лицо продукта, и «дефолтный AI-дизайн» (фиолетовый градиент, три одинаковые карточки в ряд, всё по центру в одну колонку) сразу читается как шаблон. Цель — собрать красиво и узнаваемо, опираясь на референсы и визуальное направление из брифа (раздел «Визуальный стиль»).

**Степень свободы — по брифу (раздел «Степень креатива»).** Лендинг состоит из блоков, которых внутри продукта нет (Hero, тарифы, FAQ), поэтому его вёрстка не обязана повторять интерфейс сервиса. Рекомендация по умолчанию: **цвета и шрифты держим из `DESIGN.md`** (единство бренда), а **лейаут, блоки и движение делаем свободно** — вплоть до максимально креативного в тех же цветах/шрифтах. Если в брифе выбрано «близко к продукту» — держим стилистику сервиса; если «совсем другое, вплоть до отхода от токенов» — следуем выбору пользователя, предупредив про риск для единства бренда. Когда явного выбора в брифе нет — спроси перед вёрсткой и порекомендуй вариант «токены из DESIGN.md + свободные блоки».

**Как добиваемся качества — скилл + доводка (кросс-тул):**

- **Claude Code:** вызови скилл **`frontend-design`** — он подгружает дизайн-гайдлайны и генерит нешаблонный, продуманный UI. Затем доводка: **`/critique`** (оценка по UX с баллами и списком проблем) → **`/polish`** или **`/bolder`** (если дизайн вышел слишком безопасным/пресным — усилить характер). Скиллы ставятся из дизайн-плагина; если их нет — поставь плагин или используй принципы ниже вручную.
- **Codex / Cursor / другой AI без скиллов:** скилл-механизма нет — применяй те же принципы вручную (ниже). Результат тот же, просто без обёртки-скилла.

**Ещё доводочные скиллы (Claude Code, по ситуации).** Помимо `/polish` и `/bolder` есть узкие — вызывай конкретный, когда нужно именно это:

- **Оценка:** `/critique` — UX-разбор с баллами и списком проблем; `/audit` — тех-качество (доступность, производительность, адаптив) с приоритетами P0–P3.
- **Характер:** `/bolder` — смелее ↔ `/quieter` — приглушить кричащий дизайн; `/overdrive` — вау-эффекты; `/delight` — приятные мелочи и индивидуальность.
- **Чистка:** `/distill` — убрать лишнее; `/normalize` — привести к дизайн-системе и токенам.
- **Точечно:** `/typeset` — типографика; `/colorize` — цвет; `/arrange` — лейаут и ритм; `/animate` — анимация и микроинтеракции; `/adapt` — адаптив; `/harden` — edge cases (overflow, i18n, состояния ошибок); `/optimize` — скорость; `/clarify` — UX-копирайт (кнопки, подписи, ошибки).

В Codex / Cursor этих скиллов нет — там доводка вручную по принципам ниже. Для лендинга обычно хватает `/critique` → `/polish` / `/bolder`, плюс по необходимости `/typeset` и `/adapt`.

**Принципы нешаблонного лендинга (работают в любом инструменте):**

1. Один сильный визуальный якорь в Hero (крупная типографика, выразительный образ или композиция), а не дефолтный «заголовок по центру + кнопка».
2. Осмысленная типографика: явная шкала размеров, контраст между display-заголовком и текстом, нормальная межстрочка. Шрифты — из `DESIGN.md`.
3. Ритм и воздух: щедрые и не везде одинаковые отступы, асимметрия, разная высота секций. Уходим от монотонной центральной колонки.
4. Палитра из `DESIGN.md`, один акцентный цвет используем уверенно и дозированно (CTA, ключевые акценты), а не заливаем им всё.
5. Реальная иерархия: видно, что главное, что второстепенное. Избегаем клише «три равные карточки в ряд», где это не оправдано контентом.
6. Анимация — по выбранному в брифе уровню (раздел «Степень креатива»): от классической статики до заметного движения (smooth scroll, параллакс, анимированный Hero). Если выбрана сдержанность — лёгкие появления при скролле и hover, без аттракциона; если выбран креатив — не делай пресно. Тяжёлые эффекты — через `next/dynamic`, чтобы не блокировать первую отрисовку.
7. Hover и курсор — база на любом уровне. На ВСЕХ кнопках, ссылках и интерактивных элементах обязательны hover-состояния (изменение фона/цвета/тени) и `cursor: pointer` (курсор-рука). Это не относится к «степени анимации» — это обязательная обратная связь интерфейса, она есть даже при выборе «классическая статика». Курсор-рука ставится автоматически у всего кликабельного, не только у `<a>`/`<button>`.
8. Что выдаёт AI-шаблон и чего избегаем: фиолетовый градиент на всём, generic-иконки наобум, одинаковые карточки, пустые «маркетинговые» фразы без конкретики из брифа.

## Текст: человеческий, а не AI-генерированный

Дизайн может быть нешаблонным, но если копирайт звучит как сгенерированный нейросетью — лендинг всё равно читается как штамповка. Hero, Features, «для кого», FAQ — это текст, и он должен звучать живо и конкретно, опираясь на факты из брифа, а не на пустые «маркетинговые» фразы.

**Как добиваемся — скилл + ручные принципы (кросс-тул):**

- **Claude Code:** когда текст уже на странице, прогони скилл **`/avoid-ai-writing`** (если установлен) — профиль `landing`, он строже к промо-языку и инфляции значимости. Скилла нет — открой `avoid-ai-writing.md` (в этой же папке `prompts/`) и выполни. Запускай на текстах из `page.tsx`: Hero, Features, блок «для кого», How it works, FAQ.
- **Codex / Cursor / другой AI:** обёртки-скилла нет — открой `avoid-ai-writing.md` (в этой же папке) и выполни протокол (профиль `landing`), либо применяй принципы ниже. Результат тот же.

**Что выдаёт AI-текст и что убираем:**

1. Пустые промо-фразы без конкретики из брифа: «инновационное решение», «выводит на новый уровень», «в современном мире». Заменяем фактами из `landing-brief.md` — конкретная job, результат, числа.
2. Инфляция значимости: «революционный», «уникальный», «мощный» без доказательства. Убираем или подкрепляем конкретикой.
3. Антитеза-шаблон «не X, а Y» / «это не просто …, это …» — переформулируем утвердительно полным предложением.
4. Тройные перечисления ради ритма («быстро, удобно и надёжно») — оставляем только то, что реально несёт смысл.
5. Однородный ритм: все предложения одной длины. Чередуем короткие и длинные.
6. Вода и связки-затычки: «стоит отметить», «важно понимать», «давайте разберёмся». Режем.

Цель: текст звучит так, будто его написал человек, который знает этот продукт и сегмент из брифа, — а не нейросеть «вообще про SaaS».

## Показ продукта: живой UI, а не стоковые картинки

Лендинг должен показать **сам продукт**, а не абстрактные иллюстрации «какого-то дашборда» из интернета. Это сильнейший аргумент: человек видит, что он получит, ещё до регистрации. И продукт уже собран — он лежит в этом же репозитории, на тех же компонентах. Используем это для максимального качества.

**Приоритет — перевёрстка реальных элементов (живой HTML/CSS).** Возьми настоящие компоненты продукта (карточка, ключевой экран, плеер, дашборд, форма): базовые — из `@repo/ui`, доменные — перенеси/перевёрстай по образцу из сервиса `apps/app`. Собери из них «витрину» как живую разметку внутри рамки телефона или браузера — отдельным компонентом `apps/landing/src/widgets/landing/ProductShowcase`. Накорми реалистичными демо-данными (не «Lorem ipsum» и не пустые заглушки — правдоподобный контент из домена продукта). Почему так, а не картинка:

- крик-резкость на любом экране и Retina (нет растрового мыла);
- адаптив из коробки — тот же mobile-first, что и весь лендинг;
- единая тема и токены `DESIGN.md` — витрина не разъезжается с брендом;
- ноль протухающих PNG — поменялся UI продукта, витрина обновляется сама;
- это тот же принцип, что и весь курс: переиспользуем компоненты, не хардкодим.

**Скриншот — только fallback**, когда экран дорого или бессмысленно воспроизводить как статику: видео-плеер, canvas/WebGL/3D, карты, тяжёлый интерактив или сложный data-gated экран за логином. Тогда:

- в Claude Code сними **реальный экран** запущенного продукта — через скилл `webapp-testing` (Playwright) на `http://localhost:3000` с демо-данными; в Codex/Cursor — сделай скрин вручную;
- сохрани оптимизированным (webp/avif, нужный размер) и подай через `next/image` (ленивая загрузка, не Hero) внутри той же рамки устройства/браузера, чтобы стилистика витрины была единой.

**Где разместить.** Витрина уместна в Hero (главный экран продукта рядом с крючком) и/или отдельным блоком «как это выглядит внутри» после Features / How it works. Что именно показывать (1–3 самых ценных экрана/элемента) — берётся из брифа `landing-brief.md` (раздел про показ продукта собирает `01-landing-research.md`).

**Производительность.** Рамка и статичная витрина — часть серверного компонента (никакого `'use client'` на весь блок). Живое интерактивное демо (если делаешь кликабельную витрину) — выноси в отдельный клиентский компонент через `next/dynamic`, чтобы не блокировать первую отрисовку. Скриншоты-fallback — через `next/image`.

**Чего избегаем:** стоковые «dashboard mockup» и абстрактные 3D-иллюстрации интерфейса из интернета; нарисованный фейковый UI, который не совпадает с реальным продуктом; растровый скрин там, где экран легко пересобрать живой разметкой.

## Структура лендинга (минимум)

1. **Hero** — что за продукт, для кого, главная ценность одним предложением (крючок главного сегмента, но не отсекающий остальных). CTA «Начать бесплатно».

2. **Features** — 3-5 ключевых возможностей с иконками и кратким описанием.

3. **Для кого / сценарии** — если в брифе несколько сегментов: блок с сильными сторонами под каждый (2-4 карточки/колонки «для X → ценность», «для Y → ценность»). Так главная страница презентует продукт в целом и говорит с разными аудиториями, не превращаясь в кашу. Если сегмент один — блок не нужен.

4. **How it works** — 3 шага: «Зарегистрируйся → Сделай X → Получи Y».

5. **Витрина продукта** — живой UI сервиса в рамке телефона/браузера (перевёрстка реальных компонентов, скрин только fallback — см. раздел «Показ продукта»). Что показывать — из брифа. Может жить и в Hero рядом с крючком, и отдельным блоком «как это выглядит внутри».

6. **Social proof** — отзывы, логотипы клиентов (если есть).

7. **Pricing** — если коммерческий продукт, тарифы. Иначе пропустить.

8. **FAQ** — 5-7 типовых вопросов.

9. **Footer** — ссылки, контакты, политика конфиденциальности.

## Деплой — лендинг отдельным деплой-юнитом

Код уже разнесён на монорепо в `00` (сервис стал самостоятельным деплой-юнитом). Теперь, **как только лендинг собран**, публикуем и его — как отдельный деплой-юнит, чтобы правка лендинга не задевала продакшен сервиса. (Сервис при этом нормально перезапускается, когда ты деплоишь/рестартишь **его сам** — независимость в том, что его не трогает **чужой** деплой.)

- **Своя сборка** — `npm run build -w apps/landing`, контекст только лендинга (не компилирует сервис).
- **Свой контейнер/процесс** — отдельный сервис в docker-compose (`landing`), свой образ/порт/рестарт.
- **Своя команда деплоя** — собирает и поднимает ТОЛЬКО лендинг (`docker compose build landing && docker compose up -d landing`), без общего `up -d`.
- **nginx** — лендинг на корневом домене `/`. Где живёт сам сервис (`/app` или поддомен) — решается в `03-app-domain.md`; лендинг всегда на корне.
- Единственное исключение — правка общего `packages/ui`: её раскатывают в оба приложения. Правки внутри `apps/landing` затрагивают только лендинг.

**Независимость обеспечиваем автоматически в деплой-скрипте (Урок 3), а не «руками».** Две вещи прямо в скрипте:

1. **Деплой по изменениям.** Скрипт смотрит, что изменилось с прошлого деплоя (`git diff --name-only <last_sha> HEAD`), и катит только затронутое: пути `apps/landing/` → только лендинг, `apps/app/` → только сервис, `packages/ui/` → оба (общий бренд). Незатронутое приложение не пересобирается и не рестартует само по себе.
2. **Авто-ассерт независимости.** Перед деплоем лендинга скрипт запоминает `docker inspect -f '{{.State.StartedAt}}' <service>`, после — сверяет; если у сервиса сменился `StartedAt` (рестартнул из-за деплоя лендинга) — скрипт падает с ненулевым кодом. Тот же ассерт можно повесить в pre/post-deploy gate (`deploy.sh`).

```bash
# фрагмент deploy-скрипта: деплоим только изменившееся + ассерт независимости
CHANGED=$(git diff --name-only "$LAST_DEPLOYED_SHA" HEAD)
ui=$(grep -q '^development/packages/ui/'    <<<"$CHANGED" && echo 1)
ld=$(grep -q '^development/apps/landing/'    <<<"$CHANGED" && echo 1)
ap=$(grep -q '^development/apps/app/'        <<<"$CHANGED" && echo 1)
svc_before=$(docker inspect -f '{{.State.StartedAt}}' app 2>/dev/null)
if [ "$ld" ] || [ "$ui" ]; then docker compose build landing && docker compose up -d landing; fi
if [ "$ap" ] || [ "$ui" ]; then docker compose build app     && docker compose up -d app;     fi
# ассерт: если катили ТОЛЬКО лендинг — сервис не должен был рестартнуть
if [ "$ld" ] && [ -z "$ap" ] && [ -z "$ui" ]; then
  [ "$(docker inspect -f '{{.State.StartedAt}}' app)" = "$svc_before" ] \
    || { echo "FAIL: сервис рестартнул при деплое лендинга"; exit 1; }
fi
```

Если продакшен сложнее docker-compose — всё равно добейся раздельных сборки+рестарта на приложение; цель «деплой лендинга ≠ рестарт сервиса» должна выполняться и проверяться автоматически прямо в деплой-скрипте.

## После лендинга

1. Проверь Hero — главное сообщение понятно с первого взгляда?

2. Все кнопки CTA ведут на signup

3. Адаптив — на мобиле лендинг хорошо читается?

4. **Витрина показывает реальный продукт.** Это перевёрстка настоящих компонентов (а не стоковая картинка), на Retina чётко, на мобиле не разъезжается. Скрин-fallback использован только там, где экран нельзя пересобрать живой разметкой.

5. **Текст не звучит как AI.** Прогони копирайт лендинга через `/avoid-ai-writing` (Claude Code, профиль `landing`) или по `avoid-ai-writing.md` из этой папки (Codex/Cursor или если скилл не установлен). Hero, Features, FAQ — живо и конкретно из брифа, без пустых промо-фраз и шаблонных оборотов.

6. **Лендинг — отдельный деплой, проверка автоматическая.** Своя сборка/контейнер/команда деплоя, nginx на корне `/`. В деплой-скрипте — деплой по изменениям (катим только затронутое приложение) и авто-ассерт: деплой лендинга не рестартит сервис (скрипт падает, если рестартнул). Не ручной `docker ps`. Сам сервис при этом штатно перезапускается на своём деплое.

7. **Инфраструктура зафиксирована.** В `../../product/docs/memory/infrastructure.md` записана новая топология: основной домен `/` → лендинг (`apps/landing`, свой деплой-юнит), сервис (`apps/app`) — свой деплой-юнит (по умолчанию `/app`; итог `/app`↔поддомен — в `03-app-domain.md`), `packages/ui` — общий, nginx-роутинг, правило независимости деплоев. В новой сессии видно, где что развёрнуто, без пересказа.
