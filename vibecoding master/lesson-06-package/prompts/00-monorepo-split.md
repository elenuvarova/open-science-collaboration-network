# Монорепо-сплит — разделяем код: сервис ⟂ лендинг

## Когда делать

Прямо перед сборкой лендинга (до `02-landing.md`). Здесь появляется второй деплой-артефакт (лендинг), и мы разделяем его и сам сервис на независимые приложения — чтобы правка лендинга не пересобирала и не трогала продакшен сервиса.

> Если у тебя продукт внутренний и публичного лендинга не будет — этот шаг можно пропустить (останешься на одном приложении). Тогда читай только раздел «Чистый корень» и иди дальше.

## Зачем (коротко)

Сейчас лендинг и сервис — одно Next.js-приложение. Любое изменение лендинга запускает полную пересборку и рестарт всего сервиса: медленные итерации, общий build/test-гейт, риск задеть активных пользователей. Делаем **монорепо**:

- `packages/ui` — дизайн-токены (из `DESIGN.md`) + `shared/ui`. **Единый источник** бренда.
- `apps/app` — сам сервис (FSD), импортит `packages/ui`.
- `apps/landing` — лендинг, импортит `packages/ui`.

Лендинг **ссылается** на токены и компоненты сервиса, а не копирует — ноль дублирования, единый бренд, при этом каждый `apps/*` собирается и деплоится **независимо**. Весь код уезжает в `development/`, и корень продукта остаётся чистым: `docs/` + `development/`.

Это вписано в правило `../../product/docs/rules/project-structure.md` (раздел «После монорепо-сплита»). Полное обоснование — в дизайн-доке курса по структуре.

## Целевая раскладка

```
../../product/
├── docs/                       ← вся документация остаётся в корне продукта (НЕ трогаем)
├── AGENTS.md / CLAUDE.md       ← правила-хаб (остаётся)
└── development/                ← весь код; конфиг живёт ТУТ, не в корне продукта
    ├── package.json            ← корень workspace: "workspaces": ["apps/*", "packages/*"]
    ├── packages/
    │   └── ui/                 ← @repo/ui: токены DESIGN + shared/ui (единый источник)
    │       ├── package.json
    │       └── src/
    │           ├── styles/theme.css   ← @theme токены (Tailwind v4) — импортят обе apps
    │           └── ui/                 ← компоненты из бывшего src/shared/ui
    └── apps/
        ├── app/                ← сервис: бывший src/ (минус shared/ui), prisma/, конфиг
        │   ├── package.json
        │   ├── next.config.*
        │   └── src/{app,pages,widgets,features,entities,shared/{lib,api,config}}
        └── landing/            ← новый Next.js-проект под лендинг
            ├── package.json
            ├── next.config.*
            └── src/app/        ← / (лендинг), импортит @repo/ui
```

> Имя scope `@repo/ui` — placeholder, можно заменить на скоуп продукта (например `@<slug>/ui`). Менеджер пакетов — npm workspaces по умолчанию (как в Уроке 2); если используешь pnpm — `pnpm-workspace.yaml` вместо поля `workspaces`.

## Миграция-гард: работает с любой текущей раскладкой

Этот шаг — **миграция, а не сборка с нуля**. Он приводит к целевой структуре любую входящую: и одно приложение после Уроков 1–5 (`../../product/src/…`), и уже частично разделённую. Идемпотентен: повторный прогон на готовом монорепо ничего не ломает. Перед началом AI определяет, что уже есть, и переносит без потерь.

## Промт-команда

```
Преврати продукт в монорепо (сервис + лендинг как независимые приложения с общим
пакетом UI). Это МИГРАЦИЯ существующего кода, не сборка с нуля — ничего не потеряй,
работай идемпотентно.

0. БЕЗОПАСНОСТЬ. Сначала убедись, что git-дерево чистое, и сделай коммит текущего
   состояния как точку отката ("chore: точка отката перед монорепо-сплитом"). Если
   есть незакоммиченное — закоммить/застэшь до начала. Весь перенос файлов делай
   через `git mv`, чтобы сохранить историю.

1. ОПРЕДЕЛИ ТЕКУЩУЮ РАСКЛАДКУ:
   - если `../../product/development/` уже существует и в нём apps/app + apps/landing +
     packages/ui — монорепо уже собран: только проверь сборку (шаг 7) и выходи;
   - если код лежит в `../../product/src/` (одно приложение после Уроков 1–5) — это
     основной случай, делай миграцию ниже;
   - иначе — опиши мне, что нашёл, и предложи план переноса к целевой раскладке.

2. КАРКАС МОНОРЕПО. Создай `../../product/development/` и в нём корневой package.json
   workspace:
     { "name": "<slug>-workspace", "private": true,
       "workspaces": ["apps/*", "packages/*"] }
   (pnpm — `pnpm-workspace.yaml` с packages: apps/*, packages/*). Заведи папки
   apps/ и packages/.

3. СЕРВИС → apps/app. Перенеси (git mv) существующее приложение в
   `../../product/development/apps/app/`: src/, prisma/ (если есть), public/,
   package.json, next.config.*, tsconfig.json, eslint.config.*, postcss.config.*,
   next-env.d.ts, components.json, .gitignore-строки приложения, .env* (НЕ коммить
   .env). docs/ и AGENTS.md/CLAUDE.md ОСТАЮТСЯ в корне ../../product/ — их не трогай.

4. ОБЩИЙ ПАКЕТ packages/ui (@repo/ui) — единый источник токенов и компонентов:
   - перенеси `apps/app/src/shared/ui/` → `packages/ui/src/ui/`;
   - вынеси токены DESIGN.md (слой @theme из globals.css — цвета, шрифты, радиусы,
     отступы) в `packages/ui/src/styles/theme.css`; и сервис, и лендинг импортят этот
     файл в свой globals.css (один источник темы);
   - создай packages/ui/package.json: name "@repo/ui", "exports" на ./src/ui и
     ./styles/theme.css, peerDependencies react/react-dom; tsconfig пакета;
   - в apps/app замени импорты `@/shared/ui/...` на `@repo/ui` (или оставь тонкий
     `src/shared/ui/index.ts`, реэкспортящий из `@repo/ui`, чтобы минимизировать
     правки) и добавь "@repo/ui" в зависимости apps/app.
   ВАЖНО: после сплита НИКТО не хардкодит компоненты/токены у себя — общие живут только
   в packages/ui, apps импортят оттуда (правило DESIGN.md → UIKit сохраняется).

5. ЛЕНДИНГ → apps/landing. Создай новый Next.js-проект (тот же стек: TS, Tailwind v4,
   App Router, --src-dir) в `../../product/development/apps/landing/`. Подключи "@repo/ui"
   в зависимости, импортируй тему из @repo/ui в его globals.css, настрой alias @/* .
   Саму вёрстку лендинга здесь НЕ делаем — это следующий промт (02-landing.md); тут
   только рабочий каркас приложения, открывающийся на / .

6. ССЫЛКИ И АЛИАСЫ. Проверь tsconfig обеих apps (paths @/*), workspace-зависимость
   @repo/ui резолвится (npm install в development/). Прогони поиск битых импортов.

7. СБОРКА (обязательно). В development/: `npm install`, затем собери КАЖДОЕ приложение
   отдельно — `npm run build -w apps/app` и `npm run build -w apps/landing` — без ошибок
   и TS-warning. Подними оба dev-сервера (на разных портах), открой сервис и лендинг,
   убедись, что лендинг тянет токены/компоненты из @repo/ui (единый бренд).

8. ДЕПЛОЙ СЕРВИСА НА НОВОМ ПУТИ (лендинг деплоим в `02-landing`, не здесь).
   Реструктуризация сдвинула код, поэтому деплой из Урока 3 надо починить — но не
   делать «один общий билд на всё». «Монорепо» — это про общий код (`packages/ui`), а
   не про общий билд: каждое `apps/*` — самостоятельный деплой-юнит со своей сборкой
   (`npm run build -w apps/<name>`), своим контейнером/процессом и своей командой
   деплоя. На этом шаге настрой как отдельный деплой-юнит только **сервис** (`apps/app`):
   - свой Dockerfile/билд с контекстом только `apps/app` (`npm run build -w apps/app`),
     чтобы сборка сервиса не зависела от лендинга;
   - свой сервис в docker-compose (`app`), свой образ/порт/рестарт, своя команда деплоя
     (`docker compose build app && docker compose up -d app` — без общего `up -d`);
   - сервис снова собирается и деплоится сам по себе на новом пути.
   Лендинг сейчас — пустой каркас, и его собственный деплой-юнит (контейнер + nginx +
   команда) настраивается в следующем шаге `02-landing`, когда у лендинга появится
   содержимое — там же проверяется независимость (деплой лендинга ≠ рестарт сервиса).
   Здесь лендинг ещё не публикуем.

8.1. ПУТИ В ХУКАХ, СКРИПТАХ И КОНФИГАХ (чиним ЗДЕСЬ, не «отдельно»). Реструктуризация
   сдвинула не только деплой: старые пути часто остаются в `../../.claude/hooks/*`
   (например `src/app/`, `src/proxy.ts`), в `deploy.sh`/`remote.sh`/`security-precheck.sh`,
   в `.env`/конфигах сборки. Прогони поиск по старым путям и почини КАЖДОЕ найденное под
   новые `development/apps/app/...` прямо на этом шаге — не оставляй на «обновить потом».
   ```bash
   grep -rnE "src/app|src/proxy|(^|[^/])\bsrc/" ../../.claude ../../product/*.sh \
     ../../product/development/*.sh 2>/dev/null
   ```
   Почему обязательно сейчас: хук или скрипт, ссылающийся на несуществующий путь, не падает
   с ошибкой — он молча перестаёт срабатывать (guardrail отключился, а ты думаешь, что он
   работает). Сборку/деплой это не блокирует, поэтому легко пропустить — но защита уже не та.
   После правок прогони хуки руками (`bash ../../.claude/hooks/session-start.sh` и
   ключевые) — убедись, что отрабатывают на новой раскладке.

9. ДОКИ И ПАМЯТЬ. Обнови ../../product/docs/spec.md (раздел «Стек»/«Архитектура»:
   монорепо, apps/app + apps/landing + packages/ui, независимый деплой), зафиксируй
   ADR «монорепо-сплит» и обнови docs/rules/project-structure.md, если нужно. Запиши
   в state.md, что код переехал в development/.

9.1. ИНФРАСТРУКТУРА В ПАМЯТИ (обнови ЗДЕСЬ — иначе память врёт про пути). Переезд в
   development/ сдвинул деплой и окружение, а `memory/infrastructure.md` всё ещё
   показывает на старый корень — в новой сессии AI будет искать deploy/.env не там.
   Обнови `../../product/docs/memory/infrastructure.md`, перечислив РЕАЛЬНЫЕ новые пути:
   - **Деплой-файлы** — где теперь `deploy.sh`/`remote.sh`, Dockerfile'ы и docker-compose,
     и что они РАЗДЕЛЕНЫ: сервис (`development/apps/app`) и лендинг (`development/apps/landing`)
     деплоятся как отдельные юниты, `packages/ui` катится в оба. Укажи команду сборки/деплоя
     каждого (`npm run build -w apps/<name>`).
   - **Окружение и секреты** — где лежат `.env`-файлы после переезда. Их может быть несколько
     (корень продукта и/или внутри `development/`, у каждого app свой) — выпиши КАЖДЫЙ путь;
     если значения дублируются в нескольких местах, явно пометь это (один источник правды +
     где копии), чтобы при ротации секрета было видно все файлы, которые надо поменять.
     Сами значения в память НЕ пиши — только пути и назначение.
   Прогони проверку, что выписанные пути реально существуют (`ls`/`test -f`), и добавь/обнови
   строку в `../../product/docs/memory/INDEX.md`.

В конце покажи мне `tree -L 3 ../../product/development/`, результат обеих сборок,
подтверди, что лендинг использует @repo/ui, и что в хуках/скриптах/конфигах НЕ осталось
ссылок на старые пути (покажи пустой вывод grep из шага 8.1). Если что-то не собирается —
чини до конца, не оставляй наполовину; крайний случай — откат на коммит из шага 0.
```

## После сплита — путь к коду меняется

С этого момента код продукта живёт в `development/`:
- сервис — `../../product/development/apps/app/src/…`
- лендинг — `../../product/development/apps/landing/src/…`
- общие токены/компоненты — `../../product/development/packages/ui/…`

Документация по-прежнему — `../../product/docs/…`. Следующий промт (`02-landing.md`) собирает лендинг уже в `apps/landing`, импортируя `@repo/ui`.

## Edge cases

- **Незакоммиченные изменения / грязное дерево** — сначала коммит или стэш, потом сплит (шаг 0). Перенос — через `git mv`, чтобы не потерять историю.
- **Монорепо уже собран** (повторный запуск) — гард только проверяет сборку и выходит, ничего не пересоздаёт.
- **Внутренний продукт без лендинга** — сплит не нужен; остаёшься на одном приложении, чистый корень держишь по `project-structure.md`.
- **Tailwind v3 (Next 15)** — вместо `@theme` тема в `tailwind.config`; вынеси общий конфиг/preset в `packages/ui` и подключи в обе apps.
- **Сломалась сборка после переноса** — не нагромождай поверх; почини импорты/алиасы или откатись на точку отката из шага 0 и перенеси аккуратнее.
