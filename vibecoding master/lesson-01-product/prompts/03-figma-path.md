# Детализация спецификации по Figma — ветка А

> **Universal AI prompt.** Этот файл написан так, чтобы любой AI (Claude Code, OpenAI Codex, Cursor) мог прочитать и выполнить. Подключение Figma в Шаге 0 разводится на два варианта в зависимости от AI — официальный плагин для Claude Code, Framelink + PAT для остальных.

## Зона ответственности этого промта

**Что делаем здесь:**
1. **Скелет состава продукта.** Через Figma MCP сканируем файл, группируем найденные экраны по разделам (Публичная часть / Личный кабинет / Админка / Прочие), **согласовываем с пользователем**: что включаем в первую версию, что не нужно, чего не хватает. Финальный индекс — в `spec.md → ## Экраны (индекс)`.
2. **Детализация по каждому согласованному экрану.** Отдельный файл `../../product/docs/screens/<url>.md` с разделами: доступ, layout, данные, состояния (default / loading / empty / error / success), действия по элементам, связи с другими экранами, валидация форм.
3. **Сопутствующие разделы в `spec.md`:** «Данные (модель)», «Доступы и роли», «Уведомления».

**Что НЕ делаем здесь:** не спрашиваем «что за продукт», «для кого», «какая проблема», «какой главный сценарий» — это **уже было** в `02-product-context.md` и лежит в `spec.md` в разделе «Продукт». Не возвращаемся к концепции; работаем только со скелетом и экранами.

**Предусловие:** в `../../product/docs/spec.md` уже заполнены разделы «Продукт» и «Платформа» (через `02-product-context.md`). У пользователя есть Figma-аккаунт с доступом к нужному файлу.

Этот промт ведёт пользователя через всю работу с Figma за один проход. Шаги выполняй последовательно. По окончании каждого шага показывай короткую сводку того, что сделано, и сразу переходи к следующему шагу — не жди подтверждения «дальше», прерывайся только на шагах с реальным вопросом к пользователю.

## Шаг 0 — Подключаем Figma MCP

Этот шаг — разовый. Если у тебя в этой сессии уже доступны инструменты `mcp__figma__*` (попробуй `whoami` через Figma MCP — если возвращает аккаунт, всё подключено) — переходи к **Шагу 0.5**.

### 0.0 Определи окружение и выбери способ подключения

| Ты в | Способ подключения | Тариф Figma |
|---|---|---|
| **Claude Code** | Официальный плагин `figma@claude-plugins-official` (см. 0.1A) | Professional / Organization / Enterprise + место Dev/Full |
| **Claude Code, но Free/Starter тариф Figma** | Fallback через Framelink + PAT (см. 0.1B) | Работает на любом тарифе |
| **OpenAI Codex** | Framelink + PAT (см. 0.1B) | Любой тариф |
| **Cursor** | Framelink + PAT (см. 0.1B) либо плагин Cursor для Figma если установлен | Любой тариф |
| **Другой AI** | Framelink + PAT (см. 0.1B) | Любой тариф |

### 0.1A Установка официального плагина (Claude Code, платный Figma)

Только для Claude Code с платным аккаунтом Figma. Иначе пропусти и иди к 0.1B.

Проверь с пользователем что у него:
- Платный тариф: **Professional** ($20/мес), Organization или Enterprise. На Free и Starter официальный плагин не работает.
- Тип места: **Dev** или **Full**. У Viewer и Collab лимит 6 вызовов в месяц.

Если эти условия не выполнены — иди к 0.1B (fallback).

Пользователь в чате вводит:
```
/plugin install figma@claude-plugins-official
```

Если плагин уже установлен (перенос с другого компьютера) — команда напишет `already installed`, нужен disable/enable (см. подраздел «Если плагин уже стоял»).

**Первый запуск (свежая установка):**

1. После `/plugin install` пользователь **перезапускает клиент**:
 - **VS Code:** `Cmd+Shift+P` (Windows: `Ctrl+Shift+P`) → `Developer: Reload Window` → Enter
 - **CLI:** `Cmd+Q` и открыть заново
 - **JetBrains:** File → Restart IDE

2. Когда клиент перезагрузится — открыть Figma Desktop App (именно desktop, не браузер) и выделить любой frame.

3. Попроси пользователя: «Прочитай выбранный frame в Figma и опиши что в нём». Через Figma MCP вызови `get_design_context`.

4. **При первом обращении** Claude Code откроет в браузере `mcp.figma.com` с кнопкой Authorize. Пользователь авторизуется через свой Figma-аккаунт.

5. Опиши содержимое frame — это значит подключение работает. Переходи к **Шагу 0.5**.

**Если плагин уже стоял (новый компьютер / переустановка):**

В `~/.claude/settings.json` плагин отмечен как enabled, но локального auth-состояния нет. Пошагово:

1. В чате Claude: `/plugin` → найди `figma@claude-plugins-official` → **Disable**.

2. Тем же `/plugin` → снова найди → **Enable**.

3. **Полностью закрой клиент** (Cmd+Q) и открой заново. `Reload Window` здесь не помогает.

4. Дальше — обычный первый запуск (пункты 2–5 выше).

**Если ничего не помогает:**
- «Plugin not found» при `/plugin install` — обнови Claude Code до последней версии.
- Браузер не открылся — попроси пользователя ещё раз попросить что-то из Figma (OAuth запускается лениво).
- «Figma MCP server is not available» — Figma Desktop не открыт. Открой Figma Desktop, оставь файл активным.
- «No selection / Forbidden» — у seat нет Dev/Full доступа. Проверьте Settings → Workspace → Members.

### 0.1B Универсальный fallback — Framelink + PAT (для всех AI и любого тарифа)

Для Codex/Cursor/других AI или Claude Code с Free/Starter тарифом. Использует open-source MCP-сервер `figma-developer-mcp` от Framelink. Работает с Figma REST API через Personal Access Token (PAT) — не требует платного тарифа.

**Шаги:**

1. **Получить Figma Personal Access Token (PAT)**

 Попроси пользователя:
 - Открыть в браузере: https://www.figma.com/settings/personal-access-tokens
 - Создать токен с минимальным scope: `file_content:read` (можно добавить `library_content:read`, `current_user:read` для шире функциональности)
 - Срок жизни: 30 дней (или максимум что доступно)
 - Скопировать токен

2. **Положи токен в env-файл (НЕ в чат, НЕ в терминал!)**

 Сам создай файл `../../product/.env.local` (или дополни существующий) строкой-плейсхолдером:
 ```
 FIGMA_API_KEY=впиши-сюда-свой-Figma-токен
 ```
 Скажи пользователю: «Я создал `../../product/.env.local`. Открой его и впиши свой токен после `FIGMA_API_KEY=` вместо плейсхолдера, сохрани». Пользователь вписывает токен прямо в файл — ни в терминал, ни в чат вводить ничего не нужно, и ты значение токена не видишь. Git в этом уроке ещё не подключаем, так что в репозиторий токен сейчас попасть не может; когда git инициализируется в Уроке 3, `.env*` сразу добавляется в `.gitignore` — этот файл туда тоже попадёт.

3. **Пропиши MCP-сервер (это делает AI, не пользователь)**

 Подключи Framelink MCP так, чтобы он брал `FIGMA_API_KEY` из `../../product/.env.local`. Команда сервера: `npx -y figma-developer-mcp --stdio`. Куда прописать:
 - **Claude Code:** секция `mcpServers` в `~/.claude/settings.json`.
 - **Codex:** MCP-сервер в `~/.codex/config.json`.
 - **Cursor:** Cursor Settings → MCP Servers.
 Передай серверу переменную `FIGMA_API_KEY` со значением из `../../product/.env.local`. Само значение токена в чат не выводи.

4. **Перезапустить AI** — чтобы MCP-сервер подцепился.

5. **Проверить подключение** — попробуй вызвать любой Figma MCP-инструмент (`whoami` / `get_metadata`). Если возвращается ответ — переходи к Шагу 0.5.

**Замечание про производительность:** Framelink даёт меньше контекста чем официальный плагин (нет dev mode features, нет access к variables через Variables API), но базовые `get_metadata` + `get_design_context` работают. Для большинства задач курса достаточно.

### 0.5 Идеальная структура Figma-файла и какие ссылки кидать

Точность переноса из Figma в код зависит от двух вещей: (a) как организован Figma-файл, (b) на что именно даётся ссылка для каждой задачи.

**Идеальная структура Figma-файла** (если есть возможность попросить дизайнера организовать или организовать самому):

```
 <Название продукта>
├── Foundations (Library) ← variables: colors, typography, spacing, rounded
├── UI Kit ← все компоненты: Button, Input, Card, Modal, ...
│ └── каждый компонент — отдельный component set с variants
├── Screens — Auth ← login, signup, forgot, reset (по экрану = frame)
├── Screens — Onboarding
├── Screens — Dashboard
└── Screens — <раздел продукта>
```

**Что важно для точности:**
- Variables (Figma variables) реально настроены — не «хексы прямо в layer style». Без variables MCP не вернёт токены и DESIGN.md соберётся хуже.
- Каждый компонент UI-кита — настоящий **component** в Figma (не сгруппированный frame), с **variants** и **properties**. Тогда AI читает их через `get_design_context` и видит вариативность.
- Каждый экран — отдельный **top-level frame** с осмысленным именем (`/login`, `/dashboard`, не `Frame 23`). MCP возвращает имена — они становятся именами файлов и url в коде.

Если файл организован «не идеально» — работаем как есть, AI пройдётся по тому что есть. Просто точность будет ниже на масштабе.

**Какие ссылки кидать в зависимости от задачи:**

| Что делаем | Ссылка | Как получить | Что произойдёт |
|---|---|---|---|
| Карта экранов / spec.md (этот промт) | Весь файл, без `?node-id=` | Figma → → Share → Copy link | AI делает `get_metadata` → видит все страницы и фреймы |
| DESIGN.md / токены дизайн-системы (далее — `01-design-system.md`) | Ссылка на страницу **Foundations** (или весь файл) | в Figma выдели страницу слева → ПКМ → Copy link to selection | `get_variable_defs` возвращает все variables Figma → станут токенами в DESIGN.md |
| UI-кит → код (далее — `02-ui-kit.md`) | Ссылка на страницу **UI Kit** | страница → Copy link to selection | AI пройдёт по всем компонентам, классифицирует на atoms/molecules, разложит по `shared/ui/` |
| Все экраны → визуальный контракт (далее — `05-ui-design-spec.md` в Уроке 2) | Весь файл с экранами или страница со всеми экранами | страница → Copy link to selection | AI пройдёт по всем frame'ам, для каждого сделает get_design_context + get_screenshot, допишет раздел `## Визуал` в существующий `../../product/docs/screens/<url>.md` |
| Один экран → код (далее — `06-screens.md`) | Ссылка с `?node-id=<id>` на frame экрана | выдели frame экрана → ПКМ → Copy link to selection | `get_design_context` точечно, минимум токенов |
| Правка одного компонента | Ссылка на конкретный component | выдели component → Copy link to selection | Точечно |

**Когда не уверен какую ссылку дать:** дай ссылку на всю страницу — AI сам пройдёт `get_metadata` и попросит уточнения, если нужно.

После этого шага — переходи к Шагу 1.

## Шаг 1 — Получаем URL Figma и проверяем доступ

Попроси пользователя прислать **ссылку на Figma-файл с макетами продукта**. Формат:
- `figma.com/design/:fileKey/:fileName?node-id=:nodeId` — конкретный экран
- `figma.com/design/:fileKey/:fileName` — весь файл

Когда получил URL:

1. Извлеки `fileKey` из URL.

2. Проверь доступ через `get_metadata` (узнать что в файле).

3. Если доступа нет → объясни пользователю что нужно: «зайди на Figma → файл → Share → дай view-доступ ссылке».

**Покажи пользователю:** название файла, количество страниц, количество фреймов. Спроси «всё ли это что нужно перенести, или только определённые страницы?»

## Шаг 2 — Скелет состава продукта (сканируем Figma + согласовываем с пользователем)

Цель этого шага — получить **согласованный список экранов** в виде разделов (Публичная часть / Личный кабинет / Админка / другое). Это **скелет** — без детализации каждого экрана (детали в Шагах 3–4). После этого шага у нас и у пользователя есть единое понимание: «вот эти экраны делаем, эти — нет».

### 2.1 — Сканируем Figma

Через `get_design_context` пройдись по каждому фрейму (или ограниченному списку из ответа пользователя). Для каждого экрана выпиши в `../../product/docs/screens-map.md`:

```markdown
## Экран: <название из Figma>
- **node-id:** `<id>`
- **Layout:** max-width контейнера, padding, gap между блоками, особенности адаптации — извлеки из Figma auto-layout / constraints / frame constraints. Семантическое описание, не точные хексы. Если не очевидно из Figma — пометь как «уточнить у пользователя»
- **Состояния нарисованы:** default / loading / empty / error / success
 *(перечисли только те что реально нарисованы)*
- **Ключевые компоненты:** [формы, списки, табы, модалы, карточки...]
- **Интерактивные элементы:** [кнопки/ссылки/инпуты — перечисли все с подписями]
- **Какие данные показываются:** [имя пользователя, цена, дата...]
- **Скриншот:** [используй `get_screenshot` и сохрани в `../../product/docs/screens/<name>.png`]
```

**Важно:** не додумывай ничего что не нарисовано. Только что видишь.

### 2.2 — Группируем найденное по разделам

Сгруппируй все найденные в Figma экраны по типовым разделам. Под продукт из `spec.md → Продукт` могут быть и свои разделы — добавляй их как отдельные группы:
- **Публичная часть** — что видит неавторизованный (главная, регистрация, вход, восстановление пароля, публичные страницы)
- **Личный кабинет** — основной флоу + сервисные экраны (профиль, настройки, история/логи)
- **Админка** — если есть роль админа
- **Прочие разделы** — что выходит за рамки трёх типовых (например онбординг, публичный каталог)

### 2.3 — Согласовываем скелет с пользователем

Перед показом бегло пойми продукт и назови про себя 1–3 аналога этого типа (маркетплейс / дашборд / CRM / соцсеть / контент-сервис) — чтобы предложить функционал, которого обычно ждут, а не только то, что нарисовано.

Покажи пользователю один сводный список **сгруппированный по разделам**. Для каждого экрана — одна строка: `URL — Название (одно предложение что показывает)`. Дальше спроси одним сообщением **четыре вещи**:

> «Вот скелет состава продукта по Figma:
> [сгруппированный список]
>
> 1. Из этих экранов — все нужны в первой версии? Что-то можно исключить (нарисовано, но в scope не входит)?
> 2. Каких экранов не хватает? Бывают: восстановление пароля, профиль, настройки уведомлений, страницы ошибок (404 / 403), онбординг для новых, экраны под отдельные действия из «Основных действий» в spec.md.
> 3. По аналогам ({назови 1–3}) на ключевых экранах обычно есть функционал, которого тут пока нет — например {2–4 конкретных предложения под этот продукт: фильтры/сортировка/поиск, пагинация, массовые действия, избранное, экспорт, пустые/loading-состояния}. Что из этого добавляем? (по каждому: да / нет / позже)
> 4. Группировка по разделам — корректная или поправить?»

Жди ответа. По ответу:
- Исключённые экраны помечаем в `screens-map.md` строкой `*[не делаем в первой версии]*` — карта остаётся для истории, но дальше в детализацию не идут.
- Недостающие экраны добавляем с пометкой `*[экран нужен, но в Figma не нарисован — описываем словами далее]*`.
- Принятые усиления функционала записываем (новый экран → в индекс, фича на экране → в его описание); отклонённые помечаем `*[не делаем в первой версии]*`.
- Группировку правим под пользователя.

### 2.4 — Финальный индекс экранов в spec.md

Запиши в `spec.md` раздел `## Экраны (индекс)` — согласованный список со ссылками на будущие файлы экранов (сами файлы создадутся в Шагах 3–4):

```markdown
## Экраны (индекс)

### Публичная часть
- [`/login` — Вход](screens/login.md)
- [`/signup` — Регистрация](screens/signup.md)

### Личный кабинет
- [`/dashboard` — Главный экран](screens/dashboard.md)
- ...

### Админка
- ...
```

Только теперь переходи к Шагу 3 — раскрытию каждого экрана.

## Шаг 3 — Выписываем пробелы логики

Для каждого экрана из карты пройдись по чек-листу. Записывай **только то, на что ответа в Figma НЕТ**, в `../../product/docs/logic-gaps.md`:

### Чек-лист (для каждого экрана)

1. **Все кнопки/ссылки** — куда ведут? Что делают при клике?

2. **Все формы** — какие правила валидации? Что показываем после submit (toast / переход / inline-сообщение)? Что при ошибке валидации?

3. **Все списки** — что при пустом? при ошибке загрузки? при загрузке (skeleton/spinner)?

4. **Откуда данные на экране?** Из БД? Из API? Из сессии? Из URL-параметра?

5. **Куда уходят данные при действии пользователя?** POST в API? Локально в state?

6. **Кто видит этот экран?** Все? Только залогиненные? Только определённая роль?

7. **Что если пользователь без прав попадёт сюда?** Редирект? Ошибка 403? Сообщение?

8. **Связи с другими экранами:** откуда сюда приходят, куда отсюда уходят?

Формат `logic-gaps.md`:

```markdown
## Экран: <название>

### Действия (нет ответа в Figma)
- [ ] Клик на «Сохранить» → ?
- [ ] Клик на «Назад» → ?

### Состояния (не нарисованы в Figma)
- [ ] Что показываем когда список пуст?
- [ ] Что показываем при ошибке загрузки?

### Данные
- [ ] Откуда берётся имя пользователя?
- [ ] Куда уходит форма после submit?

### Доступы
- [ ] Кто видит этот экран?
- [ ] Что если нет прав?
```

После обхода всех экранов покажи пользователю `logic-gaps.md` со списком вопросов и сразу переходи к Шагу 4 — без отдельного подтверждения «начинаю?».

## Шаг 4 — Закрыть пробелы (по одному вопросу за раз)

Покажи пользователю весь `logic-gaps.md` одним сообщением — это **сводка** найденных пробелов, сгруппированная по экранам (не вопрос — обзор). Сразу после сводки начинай задавать вопросы **по одному за раз** — каждый пробел отдельным сообщением. Жди ответа на текущий пробел перед переходом к следующему. На неполные ответы используй разумные defaults; если ответ «не знаю» — на месте предложи 2–3 типовых варианта на выбор и иди дальше.

После ответа пользователя:

1. Ясные ответы → добавь в файл экрана `../../product/docs/screens/<url>.md`.

2. Если визуал не нарисован в Figma (например, нет error state экрана X) → предложи блоком три варианта:
 > «На экране X не нарисовано состояние "ошибка". Варианты:
 > 1. Нарисуй в Figma и пришли ссылку — я подтяну
 > 2. Опиши словами — я сгенерирую placeholder по описанию
 > 3. Я предложу стандартный паттерн (большая ошибка + кнопка повтора) — ты подтвердишь»

После закрытия всех пробелов — отметь `[x]` у всех пунктов в `logic-gaps.md` и сохрани его в `../../product/docs/logic-gaps.md` (история разговора пригодится).

## Данные (модель)

Извлекай сущности из ответов пользователя и того что видно в Figma (если на экране есть «список заказов» — значит есть сущность Order).

## Шаг 6 — Сборка spec.md (обзор) + файлов экранов

Детали каждого экрана сложи в отдельный файл `../../product/docs/screens/<url>.md`, а в `spec.md` оставь обзор и индекс экранов со ссылками — так файл не разрастается, а AI грузит только нужный экран.

**`spec.md` (обзор):**
```markdown
# Spec продукта <name>

## Продукт
*[из 02-product-context]*

## Платформа
*[из 02-product-context]*

## Данные (модель)
*[Шаг 5]*

## Экраны (индекс)
- [/login — Вход](screens/login.md)
- [/profile — Профиль](screens/profile.md)
- ...

## Доступы и роли
*[из ответов «кто видит этот экран»]*

## Уведомления
*[если были email/Telegram/in-app]*
```

**Файл экрана — `../../product/docs/screens/login.md` (пример):**
```markdown
# /login — Вход

**Доступ:** только неавторизованные; авторизованных редиректим на /
**Figma node-id:** <id>
**Layout:** контейнер max-width 480px, центрирован; padding 32/24; gap 16 между полями, 24 перед кнопкой; на ≤640px растягивается на весь экран, padding 16
**Данные:** email + password (форма), POST /api/auth/login
**Состояния:**
- default: форма видна
- loading: кнопка со спиннером, форма заблокирована
- error: «Неверный email или пароль» под формой
**Действия:**
- Submit → POST /api/auth/login → success: редирект на /; error: сообщение
- Клик «Забыли пароль?» → /forgot-password
- Клик «Регистрация» → /signup
**Связи:** откуда сюда (лендинг, /signup) / куда отсюда (/, /forgot-password, /signup)
**Валидация:** email — формат; password — не пусто
```

На каждый экран — свой файл по этому шаблону.
