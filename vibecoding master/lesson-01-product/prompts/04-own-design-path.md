# Детализация спецификации по своему дизайну или с нуля — ветка Б/В

Этот промт работает в двух режимах:
- **Режим Б:** у пользователя есть свой дизайн в другом инструменте (Sketch / Penpot / Photoshop), наброски на бумаге, скриншоты — но не Figma с MCP-доступом
- **Режим В:** дизайна нет вообще, только идея

Пользователь в начале говорит какой режим — далее ты работаешь по соответствующей ветке.

## Зона ответственности этого промта

**Что делаем здесь:**
1. **Скелет состава продукта.** В режиме Б — анализируем присланные скриншоты; в режиме В — предлагаем типовой набор экранов под продукт. В обоих режимах группируем по разделам (Публичная часть / Личный кабинет / Админка / Прочие) и **согласовываем с пользователем**: что включаем, что не нужно, чего не хватает. Финальный индекс — в `spec.md → ## Экраны (индекс)`.
2. **Детализация по каждому согласованному экрану.** Отдельный файл `../../product/docs/screens/<url>.md` с разделами: доступ, layout, данные, состояния (default / loading / empty / error / success), действия по элементам, связи с другими экранами, валидация форм.
3. **Сопутствующие разделы в `spec.md`:** «Данные (модель)», «Доступы и роли», «Уведомления».

**Что НЕ делаем здесь:** не спрашиваем «что за продукт», «для кого», «какая проблема», «какой главный сценарий» — это **уже было** в `02-product-context.md` и лежит в `spec.md` в разделе «Продукт». Не возвращаемся к концепции; работаем только со скелетом и экранами.

**Предусловие:** в `../../product/docs/spec.md` уже заполнены разделы «Продукт» и «Платформа» (через `02-product-context.md`).

## Шаг 0 — Уточнение режима

Сначала спроси:
> «Какой режим работы?
> Б. У меня есть скриншоты сервиса — я пришлю картинки/скрины
> В. Дизайна нет, есть только идея — будем придумывать с нуля»

Дальше работа отличается в Шагах 1–3, дальше (с Шага 4) — одинаково.

## РЕЖИМ Б — Свой дизайн (картинки)

### Шаг 1Б — Получаем картинки и описание

Попроси пользователя:
> «Пришли все картинки/скриншоты экранов которые у тебя есть (можно прямо сюда, можно положить в `../../product/docs/screens/`). По каждой картинке напиши одной строкой суть экрана.»

Когда пользователь пришлёт картинки, проверь что:
- Картинки доступны (либо загружены в чат, либо в папке `../../product/docs/screens/`)
- К каждой есть подпись (название + URL). Придумай url сам.

Если что-то непонятно — спроси: «Этот экран что показывает? Куда с него можно перейти? А что делает нажатие этой кнопки?»

### Шаг 2Б — Анализ картинок и карта экранов

Для каждой картинки внимательно посмотри что нарисовано и запиши в `../../product/docs/screens-map.md`:

```markdown
## Экран: <название> (`<url>`)
- **Источник:** `../../product/docs/screens/<filename>.png`
- **Что вижу:**
  - Заголовок / какой текст
  - Какие блоки и в каком порядке
  - Кнопки / ссылки / формы / списки
  - Какие данные показываются
- **Что НЕ видно (но возможно есть):**
  - Состояния (loading/empty/error)
  - Что при клике на кнопки X, Y, Z
```

**Важно:** описывай только то что РЕАЛЬНО видно на картинке. Не додумывай.

### Шаг 2.5Б — Согласовываем скелет состава продукта

Сгруппируй найденные на скриншотах экраны по разделам: **Публичная часть** (главная, регистрация, вход, восстановление, публичные страницы) / **Личный кабинет** (основной флоу, профиль, настройки, история) / **Админка** (если есть роль админа) / **Прочие** (если выходит за рамки трёх типовых).

Перед показом бегло пойми продукт и назови про себя 1–3 аналога этого типа (маркетплейс / дашборд / CRM / соцсеть / контент-сервис) — чтобы предложить функционал, которого обычно ждут.

Покажи пользователю **один сводный список по разделам** и спроси одним сообщением четыре вещи:

> «Вот скелет состава продукта по присланным скриншотам:
> [сгруппированный список — по разделам, на экран одна строка: URL — Название (что показывает)]
>
> 1. Из этих экранов — все нужны в первой версии? Что-то можно исключить (нарисовано, но в scope не входит)?
> 2. Каких экранов не хватает? Бывают: восстановление пароля, профиль, настройки уведомлений, страницы ошибок (404 / 403), онбординг, экраны под отдельные действия из «Основных действий» в spec.md.
> 3. По аналогам ({назови 1–3}) на ключевых экранах обычно есть функционал, которого тут пока нет — например {2–4 конкретных предложения под этот продукт: фильтры/сортировка/поиск, пагинация, массовые действия, избранное, экспорт, пустые/loading-состояния}. Что из этого добавляем? (по каждому: да / нет / позже)
> 4. Группировка по разделам — корректная или поправить?»

По ответу:
- Исключённые помечаем `*[не делаем в первой версии]*` в `screens-map.md`.
- Недостающие добавляем с пометкой `*[экран нужен, но не нарисован — описываем словами далее]*`.
- Принятые усиления функционала записываем (новый экран → в индекс, фича на экране → в его описание); отклонённые помечаем `*[не делаем в первой версии]*`.
- Группировку правим под пользователя.

Запиши финальный согласованный индекс в `spec.md` → раздел `## Экраны (индекс)` со ссылками на файлы экранов (файлы появятся после Шагов 4–7):

```markdown
## Экраны (индекс)

### Публичная часть
- [`/login` — Вход](screens/login.md)
- ...

### Личный кабинет
- [`/dashboard` — Главный экран](screens/dashboard.md)
- ...
```

## РЕЖИМ В — Без дизайна

### Шаг 1В — Скелет состава продукта (предлагаем + согласовываем)

Цель этого шага — получить **согласованный с пользователем список экранов**, сгруппированный по разделам. Это скелет: без детализации каждого экрана, она в Шагах 2В и далее.

Подбирай типовой набор под продукт из `spec.md → Продукт` и платформу. Предложи **сгруппированный по разделам**:

```
Для веб-сервиса обычно нужны:

Публичная часть (видит неавторизованный):
- Главная (лендинг или список)
- Регистрация
- Вход
- Восстановление пароля

Личный кабинет (после авторизации):
- Главный экран (основной сценарий из spec.md)
- Профиль пользователя
- Настройки
- История / логи действий — если в продукте есть аудит-нагрузка

Админка (если в spec.md → Для кого есть роль админа):
- Список пользователей
- Детали пользователя
- Управление контентом / данными

Прочие разделы — если выходит за рамки трёх типовых
(например онбординг, публичный каталог, страницы ошибок 404/403).

Какие из этих нужны для твоего продукта? Какие специфические экраны
ещё нужны под основные действия (поле «Основные действия» в spec.md)?
Что-то из предложенного, наоборот, **не делаем** в первой версии?

И по аналогам ({назови 1–3 похожих продукта этого типа}) на ключевых экранах
обычно есть функционал, которого тут пока нет — например {2–4 предложения под
этот продукт: фильтры/сортировка/поиск, пагинация, массовые действия, избранное,
экспорт, пустые/loading-состояния}. Что из этого добавляем? (по каждому: да / нет / позже)
```

Жди ответа. Принятые усиления функционала фиксируй в `screens-map.md` (новый экран — в список, фича на экране — в его строку); отклонённые помечай `*[не делаем в первой версии]*`. Если пользователь не знает «делаем / не делаем» по конкретному экрану — предложи 2–3 варианта на выбор (пример: «Настройки уведомлений — А: один переключатель „включить все", Б: по каждому событию отдельно, В: не делаем в первой версии»).

Уточняй пока не будет полный список ~5–15 экранов сгруппированный по разделам. Важно – лендинг пока не детализируем, его отдельно создадим в Уроке 6.

Сохрани список в `../../product/docs/screens-map.md`:

```markdown
## Скелет состава продукта

### Публичная часть
| URL | Название | Доступ | Что показывает |
|---|---|---|---|
| `/` | Главная | все | ... |
| `/login` | Вход | неавторизованные | форма |

### Личный кабинет
| URL | Название | Доступ | Что показывает |
|---|---|---|---|
| `/dashboard` | Главный экран | авторизованные | ... |

### Админка
| URL | Название | Доступ | Что показывает |
|---|---|---|---|
| ... | ... | ... | ... |
```

Параллельно запиши тот же согласованный индекс в `spec.md` → раздел `## Экраны (индекс)` со ссылками на файлы экранов (сами файлы появятся далее):

```markdown
## Экраны (индекс)

### Публичная часть
- [`/login` — Вход](screens/login.md)
- ...

### Личный кабинет
- [`/dashboard` — Главный экран](screens/dashboard.md)
```

### Шаг 2В — Описание каждого экрана

Для каждого экрана задавай 3 вопроса ПО ОДНОМУ:

1. «Что на экране — какой заголовок и какие основные блоки?»

2. «Какие действия пользователя — что он может нажать/заполнить?»

3. «Куда переходим/что меняется после действия?»

После каждого ответа добавляй в `screens-map.md` под соответствующий экран:

```markdown
### /<url> — <название>
- Что на экране: ...
- Действия: ...
- Переходы / изменения: ...
```

## Шаг 4 — Выписываем пробелы логики (общий для Б и В)

Для каждого экрана из карты пройдись по чек-листу. Записывай в `../../product/docs/logic-gaps.md` ВСЕ вопросы (в режиме В пробелов будет больше чем в Б, потому что визуала нет).

**Жёсткое правило:** записываешь ВСЁ что не определено — даже если кажется очевидным. Лучше лишний вопрос, чем незакрытый пробел в спеке.

### Чек-лист (8 групп)

1. **Все кнопки и ссылки** — куда ведут? Что происходит при клике? Активны ли при всех состояниях?

2. **Все формы** — поля, правила валидации, что при submit, что при ошибке, что при успехе

3. **Все попапы, модалки и диалоги подтверждения** — что в заголовке? Какие кнопки? Что происходит при «Да» и «Нет»? Что при закрытии крестиком?

4. **Все тосты и уведомления** — при каком событии появляются? Какой текст? Сколько показываются? Есть ли крестик?

5. **Все списки и таблицы** — что при пустом состоянии (текст + CTA)? При загрузке? При ошибке?

6. **Откуда данные** — из БД / API / сессии / пропсов? Что если данные не пришли?

7. **Доступы** — кто видит этот экран? Что если зайдёт не тот — редирект или ошибка?

8. **Навигация** — откуда сюда можно попасть? Куда ведут переходы отсюда?

Формат записи:

```markdown
## Экран: <название>
### Действия
- [ ] Клик на "[кнопка]" → ?
- [ ] Клик на "[ссылка]" → ?
### Модалки / попапы
- [ ] Попап "[название]" — кнопки? что после подтверждения? что после отмены?
### Состояния
- [ ] Пустое состояние — какой текст и CTA?
- [ ] Ошибка загрузки — что показываем?
### Данные
- [ ] Откуда берётся [поле]?
### Доступы
- [ ] Кто видит? Что если нет прав?
```

Покажи пользователю полный `logic-gaps.md` одним сообщением и сразу переходи к Шагу 5 — без отдельного подтверждения «начинаем?».

## Шаг 5 — Закрыть пробелы (по одному вопросу за раз)

Покажи пользователю весь `logic-gaps.md` одним сообщением — это **сводка** найденных пробелов, сгруппированная по экранам (не вопрос — обзор). Сразу после сводки начинай задавать вопросы **по одному за раз** — каждый пробел отдельным сообщением. Жди ответа на текущий пробел перед переходом к следующему. На неполные ответы используй разумные defaults; если ответ «не знаю» — на месте предложи 2–3 типовых варианта на выбор. После ответа:

1. Заполни файл экрана `../../product/docs/screens/<url>.md` (логика экрана: состояния, действия, связи, валидация). Общие разделы — данные, доступы, уведомления — в `spec.md`, а в раздел «Экраны (индекс)» добавь ссылку на файл экрана.

2. Отметь `[x]` у закрытых пробелов в `logic-gaps.md`.

3. Если по конкретному пункту пользователь ответил «не знаю» — **не принимай в таком виде**. Предложи 2–3 конкретных варианта прямо в ответном сообщении:
   > «Выбери один:
   > А. [конкретный сценарий]
   > Б. [другой сценарий]
   > В. [третий вариант]
   > Или скажи своё»

4. Если описание экрана становится яснее — предложи уточнение:
   > «Представляю экран так: [описание]. Похоже? Если нет — поправь».

**Правило: нельзя перейти к Шагу 6 пока в `logic-gaps.md` есть хотя бы одна незакрытая `[ ]` строка.** Оставшиеся открытые точки — это будущие баги или «неопределённые элементы» при генерации кода.

### Верификационный проход перед сборкой

Когда все вопросы в `logic-gaps.md` отмечены `[x]`, сделай проход по экранам:

0. **Файл на каждый экран — обязательно.** Сверь: на **каждый** экран из `screens-map.md` создан отдельный файл `../../product/docs/screens/<url>.md` с логикой. Какого-то нет — **создай его сейчас** из карты + общих разделов `spec.md` (доступ, данные, состояния default/loading/empty/error/success, действия, связи, валидация). Это главная цель детализации, а не только карта: без поэкранных файлов сборка в Уроке 2 пойдёт «по карте на глаз». Не опускай этот пункт.

1. Прочитай секцию «Действия» каждого экрана — нет ли строк без результата?

2. Прочитай все модалки и попапы — у каждой есть список кнопок и что они делают?

3. Прочитай «Состояния» — есть ли empty, loading, error у каждого экрана с данными?

Если что-то нашлось — задай вопрос именно по этому элементу. **Не двигайся к Шагу 6, пока на каждый экран из карты нет файла `../../product/docs/screens/<url>.md` и все пробелы не закрыты.**

> «Проверил всё — [N] экранов, каждое действие закрыто. Переходим к модели данных?»

## Шаг 6 — Модель данных

Когда экраны и логика собраны, выпиши модель в `spec.md`:

```markdown
## Данные (модель)

### User
- id, email, name, role, createdAt

### <Сущность 2>
...
```

Извлекай сущности из ответов: если на экране «список заказов» — есть Order. Если «список постов» — Post. И т.д.

## Шаг 7 — Сборка финального spec.md

Сложи всё в каноничную структуру (см. Шаг 6 в `03-figma-path.md` или шаблон в `05-prd-spec-template.md`):

```markdown
# Spec продукта <name>

## Продукт
## Платформа
## Данные (модель)
## Экраны
  ### /url — Название
    Доступ, Данные, Состояния, Действия, Связи
## Доступы и роли
## Уведомления
```

## Шаг 8 — Показать результат

1. Покажи пользователю `spec.md` целиком.

2. Покажи `screens-map.md` и `logic-gaps.md`.

3. Покажи `tree ../../product/docs/screens/` и подтверди: на **каждый** экран из карты есть файл `../../product/docs/screens/<url>.md` (число экранов в карте = число файлов). Если не сходится — вернись и создай недостающие, иначе в Уроке 2 нечего будет дополнять визуалом.


## Дизайн-система и UIKit — строятся на этапе прототипа

Спека описывает что строим. Как это выглядит — определяет дизайн-система. На этапе прототипа первым делом создаётся `DESIGN.md` (токены цветов, типографики, скруглений) и UIKit в `shared/ui/` на shadcn.

Правило которое работает на всех этапах после первичной сборки прототипа:

> DESIGN.md → UIKit (shared/ui/) → Экраны

Любое изменение визуала начинается с токена или компонента в UIKit — никогда напрямую на странице.

Если в режиме В у пользователя нет визуальных предпочтений — предупреди сейчас:

> «На этапе прототипа первым шагом я задам 5 вопросов про стиль (основной цвет, шрифт, характер). Если есть продукт с похожим дизайном (Linear, Notion, Stripe, Apple, Discord) — запомни его название, это ускорит сборку дизайн-системы.»

## Важные правила

- **Не додумывай.** В режиме Б — только то что на картинке. В режиме В — только то что сказал пользователь.
- **По одному вопросу.** Никогда не вываливай списком.
- **Заполняй spec.md по ходу.** Не жди финала.
- **В режиме Б сохраняй картинки** в `../../product/docs/screens/` — пригодятся при сборке UI.
