# Финальная сверка спецификации + одностраничник PRD

## Зона ответственности этого промта

**Что делаем здесь:** **полировка** уже готовой спецификации. Сверяем `spec.md` и файлы `../../product/docs/screens/<url>.md` с каноничной структурой, дочитываем Figma/скриншоты на предмет пропущенных кликабельных элементов или нерасписанных состояний, закрываем оставшиеся `[?]` через короткое интервью. В конце генерируем `../../product/docs/PRD.md` — одностраничную проекцию раздела «Продукт» для не-технической аудитории.

**Что НЕ делаем здесь:** не описываем продукт «с нуля», не задаём вопросы про концепцию (что/для кого/проблема), не строим новые экраны. Все эти слои уже сделаны: концепция в `02-product-context.md`, экраны и логика — в `03-figma-path.md` или `04-own-design-path.md`. Здесь только сверка, добивание пропусков и генерация одностраничника.

**Предусловие:** в `../../product/docs/spec.md` уже есть разделы «Продукт», «Платформа», индекс экранов, и в `../../product/docs/screens/` лежат файлы экранов (через `02` → `03`/`04`).

## PRD.md vs spec.md — зачем оба

Два файла, но **источник правды один** — `spec.md`. `PRD.md` — это сжатая выжимка из `spec.md` для людей, которые не будут читать технические детали.

| Файл | Для кого | Что внутри | Длина |
|---|---|---|---|
| **`../../product/docs/spec.md`** | AI и разработчик (контракт сборки) | Обзор: продукт, платформа, модель данных, доступы и роли, уведомления + индекс экранов со ссылками | ~150–400 строк |
| **`../../product/docs/screens/<экран>.md`** | AI и разработчик | Полная детализация одного экрана: доступ, layout, данные, все состояния, действия, связи, валидация. Отдельный файл на каждый экран | 40–150 строк на экран |
| **`../../product/docs/PRD.md`** | Партнёр / инвестор / будущий ты через 6 месяцев / новый человек в команде | Что за продукт, какую проблему решает, для кого, главные сценарии, что НЕ делаем | 1 страница |

**Правило синхронизации:** PRD.md генерируется из раздела «Продукт» spec.md. При изменении продуктовой части — сначала обновляется spec.md, потом перегенерируется PRD.md. Двух истин не бывает.

**Если работаешь один с AI и партнёров/инвесторов нет** — PRD.md всё равно полезен: через месяц-два, открыв проект после паузы, ты прочитаешь одну страницу и вспомнишь зачем строил это. spec.md в этой роли тяжёл — он про «как сделано», а не «зачем сделано».

## Что делаем

1. Прочитай `../../product/docs/spec.md` и файлы экранов в `../../product/docs/screens/`.

2. **Если есть Figma или скриншоты** — пройдись по каждому макету ещё раз и дозаполни спеку всем, что в ней пропущено. Цель: чтобы в каждом файле `../../product/docs/screens/<url>.md` была описана **каждая кнопка, ссылка, иконка, поле, переключатель** — что это и что происходит при клике. См. блок «Дочитывание Figma/скриншотов» ниже.

3. Сверь со структурой ниже.

4. Если каких-то разделов нет или они пустые — задай пользователю вопросы чтобы заполнить.

5. Особое внимание — на раздел «Действия» каждого экрана: каждый кликабельный элемент должен иметь описание того, что происходит. Если чего-то нет — задай вопрос именно об этом элементе.

6. На выходе покажи финальный `spec.md`.

7. Сгенерируй `../../product/docs/PRD.md` — короткую выжимку из раздела «Продукт» spec.md по шаблону ниже.

## Дочитывание Figma/скриншотов (если макеты есть)

Цель этого блока — догнать спеку до состояния «всё что нарисовано — описано». Это самый важный шаг для полноты: после него в `../../product/docs/screens/` не должно остаться кликабельного элемента без описания.

**Если Figma подключён (есть `mcp__figma__*`):**

1. По каждому экрану из индекса `spec.md` вызови `get_design_context` (или `get_screenshot` + `get_design_context`) и выпиши все интерактивные элементы: кнопки, ссылки, иконки-кнопки, тоглы, чекбоксы, поля ввода, табы, дропдауны, аватары-меню, контекстные меню, навигация.

2. Для каждого элемента сверь с файлом экрана. Если элемента нет в файле — добавь строку в раздел «Действия»: `Клик на «<название элемента из макета>» → <что происходит>`. Если из макета понятно куда ведёт (есть линк / ховер-стейт / следующий фрейм) — заполни сам. Если не понятно — поставь маркер `[?]` и собери в один список вопросов пользователю.

3. Состояния: для каждого экрана с данными проверь, есть ли в макете empty / loading / error / success. Если в макете есть — перенеси описание в файл экрана. Если нет — пометь как «не нарисовано, нужен ответ».

4. Формы: для каждой формы выпиши все поля + правила валидации, видимые в макете (required, маски, подсказки). В раздел «Валидация» файла экрана.

**Если только скриншоты (нет Figma MCP):**

1. По каждому скриншоту в `../../product/docs/screens/*.png` (или другому формату) — последовательно опиши, что видно: заголовок, блоки, все интерактивные элементы. Это твоя зона ответственности: пользователь не должен сам перечислять «что на картинке».

2. Дозаполни файл экрана так же, как с Figma: каждая кнопка/ссылка → строка в «Действиях». Что не понятно из картинки — собери в один список вопросов.

**После прохода по всем макетам** — задай пользователю собранные вопросы по одному отдельным сообщением (не списком). Каждый ответ — сразу в файл экрана.

Только после этого переходи к проверке по чек-листу.

## Каноничная структура spec.md

```markdown
# Spec продукта <name>

## Продукт
- **Что:** [одно предложение — что это за продукт]
- **Проблема, которую решаем:** [одно-два предложения — какую боль или задачу пользователя продукт закрывает]
- **Ключевая ценность:** [одно предложение — почему пользователь выбирает этот продукт, а не альтернативу или ничего]
- **Для кого:** [роли в системе: один тип / админ+пользователь / гость+авторизованный / B2B иерархия]
- **Главная задача:** [главный пользовательский сценарий за один проход]
- **Что НЕ делаем в первой версии (out of scope):** [список фич/flow которые сознательно отложены — чтобы не разрастаться]

## Платформа
- **Основная:** web (responsive) — адаптируется под мобильный браузер

## Данные (модель)

### User
- id: uuid
- email: string (уникальный)
- name: string
- role: 'user' | 'admin'
- createdAt: timestamp

### [Сущность 2]
...

## Экраны (индекс)

Список всех экранов со ссылками на детальные файлы. Полное описание каждого экрана — в отдельном файле `../../product/docs/screens/<url>.md`, так spec.md остаётся обзорным, а AI грузит только нужный экран.

- [/<url> — <Название>](screens/<url>.md) — одной строкой назначение экрана
- [/<url2> — <Название2>](screens/<url2>.md) — назначение
- ...

## Доступы и роли

| Роль | Что видит |
|---|---|
| user | свои данные, основной флоу |
| admin | всё + админка |
| гость (неавторизованный) | главная, login, signup |

## Уведомления

| Триггер | Канал | Получатель | Текст / шаблон |
|---|---|---|---|
| Регистрация | Email | пользователь | «Добро пожаловать, {{name}}» |
| ... | ... | ... | ... |
```

## Каноничная структура файла экрана — `../../product/docs/screens/<url>.md`

На каждый экран продукта — отдельный файл `../../product/docs/screens/<url>.md`:

```markdown
# /<url> — <Название>

**Доступ:** [все / только залогиненные / роль]
**Источник:** [Figma node-id / `../../product/docs/screens/<file>.png` / текстовое описание]
**Layout:** контейнер (max-width), padding, внутренний gap, поведение на ≤640px / 768px
**Данные:** [откуда берутся: API endpoint, useSession, props]
**Состояния:** default / loading / empty / error / success — что показывается в каждом
**Действия:**
- Клик на [элемент] → [куда ведёт / что делает]
- Submit формы [имя] → POST [endpoint] → success / error
**Связи с другими экранами:** откуда сюда / куда отсюда
**Валидация (если есть формы):** поле — правило — сообщение об ошибке
```

## Проверка по чек-листу

После сверки скажи пользователю что есть и чего нет:

- [ ] Раздел «Продукт» заполнен (что/для кого/задача)
- [ ] Раздел «Платформа» указан
- [ ] Раздел «Данные» — есть хотя бы User, есть основные бизнес-сущности
- [ ] Каждый экран вынесен в свой файл `../../product/docs/screens/<url>.md`, а в `spec.md` есть индекс со ссылками
- [ ] В файле каждого экрана указан Доступ, Источник, **Layout**, Данные, Состояния (минимум default + loading + empty + error), Действия
- [ ] **В «Действиях» каждого экрана нет пустых строк и «TBD»** — у каждого кликабельного элемента есть конкретный результат (куда ведёт / что происходит / какое сообщение показываем)
- [ ] **У каждого экрана есть хотя бы один путь входа** (откуда сюда попадают) и **один путь выхода** (куда отсюда уходят) — нет тупиков и orphan-экранов
- [ ] Раздел «Доступы и роли» заполнен
- [ ] Раздел «Уведомления» — если в продукте есть email/Telegram/in-app

Для каждого пункта где нет данных — задай пользователю 1 вопрос. Не вываливай списком.

### Как заполнять пробелы в «Действиях»

Если для какого-то кликабельного элемента поведение не описано — не пропускай молча. Предложи пользователю один из вариантов:

1. **Предложи логику:** «Предлагаю вот так: [конкретный сценарий]. Подходит?»

2. **Спроси точно:** «Эта кнопка "[название]" на экране "[экран]" — [вариант А] или [вариант Б]?»

3. **Запроси материал:** «Покажи этот экран в Figma — или опиши словами что должно произойти»

Называй конкретный экран и конкретный элемент — не спрашивай «что делает эта кнопка?» в воздух.

## Генерация PRD.md

Создай `../../product/docs/PRD.md` — короткую одностраничную выжимку. Поля бери **только** из раздела «Продукт» уже заполненного spec.md, не задавай пользователю новые вопросы:

```markdown
# PRD — <название продукта>

> Краткое описание продукта на одну страницу — для партнёров, инвесторов, новых людей в команде, а также для себя через несколько месяцев. Источник правды — `../../product/docs/spec.md`. Любое изменение продуктовой части → сначала в spec.md, потом перегенерация этого файла.

## Что за продукт
<одно предложение из spec.md «Продукт → Что»>

## Какую проблему решает
<одно-два предложения из spec.md «Продукт → Проблема»>

## Ключевая ценность
<одно предложение из spec.md «Продукт → Ключевая ценность» — почему пользователь выбирает этот продукт>

## Для кого
<роли из spec.md «Продукт → Для кого»>

## Главный пользовательский сценарий
<сценарий из spec.md «Продукт → Главная задача»>

## Основные действия в продукте
<список из spec.md «Продукт → действия» — крупными блоками, без UI-деталей>

## Платформа
<из spec.md «Платформа»>

## Что НЕ делаем в первой версии (out of scope)
<из spec.md «Продукт → Out of scope»>

## Где детали
- **Технический контракт со всеми экранами, состояниями, данными:** [`spec.md`](spec.md)
- **Дизайн-система (токены, типографика, компоненты):** [`DESIGN.md`](DESIGN.md) — появится далее
- **История архитектурных решений:** `../../product/docs/memory/decisions/` — появится далее
```

**Правила:**
- PRD.md = **проекция** из spec.md, не источник новой информации. Если пользователь хочет что-то изменить — менять в spec.md, потом перегенерировать PRD.md.
- Не добавляй в PRD.md технические детали (схемы БД, API, состояния экранов). Это место spec.md.
- Если в spec.md какое-то поле пустое — оставь в PRD.md плейсхолдер `<заполни в spec.md>`, не выдумывай.

Запиши в `state.md` (если есть):
```markdown
## Продуктовое интервью — Завершено
- spec.md готов: <date>
- PRD.md сгенерирован: <date>
- Путь: <A/Б/В>
```
