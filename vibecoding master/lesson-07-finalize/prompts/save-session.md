# Промт: Сохранение сессии (save-session)

> **Универсальный промт.** Завершает рабочую сессию: обновляет state, создаёт session-файл, добавляет строку в INDEX. В Claude Code зашит в скилл `/save-session`.

---

## Когда применять

- В конце большого этапа работы
- В конце большой задачи (если занимались > 1 часа и есть что зафиксировать)
- Перед длинным перерывом в работе (день+) — чтобы следующая сессия знала «где остановились»
- После реализации значимой фичи — после `feature-dev` промт

**Не применять для:** мелких правок (опечатки, цвет одной кнопки) — для них достаточно git-коммита.

---

## Параметры

Спроси у пользователя одной строкой, если не указано в запросе:

- **Slug сессии** — короткое имя для файла, например `deploy`, `auth-refactor`, `payments-mvp`
- **Краткое описание** — 1-2 предложения что делали (если AI участвовал — он сам помнит)

Дата сессии = текущая (вызови `date +%Y-%m-%d` если нужно точное значение).

---

## Шаги промт

### Шаг 1 — Собери саммари из текущей сессии

Если ты участвовал в работе (Claude Code / Cursor с длинным контекстом) — у тебя есть память о сессии. Собери:

- **Что сделано:** 3-7 пунктов главных результатов
- **Какие файлы изменены / созданы:** проверь через `git diff --stat HEAD~N..HEAD` (где N = количество коммитов сессии) или `git status` если ещё не коммитили
- **Какие решения приняты:** если были архитектурные выборы — отдельным разделом, со ссылками на ADR (если уже создан) или предложением создать ADR
- **Какие находки:** неочевидное поведение, лимиты, нюансы — кандидаты в `findings/`
- **Открытые вопросы:** что осталось нерешённым или отложено

Если ты не участвовал (свежий старт сессии) — попроси пользователя описать в одном сообщении.

### Шаг 2 — Создай session-файл

Путь: `../../product/docs/memory/sessions/<YYYY-MM-DD>-<slug>.md`

Если файл с такой датой и slug уже есть — добавь номер: `<YYYY-MM-DD>-<slug>-2.md`.

Шаблон содержимого:

```markdown
# <YYYY-MM-DD> — <Описание сессии>

**Длительность:** <если знаешь — иначе пропусти>
**Задача:** <название задачи>

## Что сделано

- ...
- ...
- ...

## Изменённые файлы

```
<список из git diff --stat>
```

## Принятые решения

- <решение>: ссылка на ADR-XXX (если есть) или «требует ADR»
- ...

## Находки

- <нюанс>: ссылка на F-XXX или «требует findings»

## Открытые вопросы / следующие шаги

- ...

## Связанное

- ADR: ADR-XXX, ADR-YYY
- Findings: F-XXX
- Предыдущая сессия: <YYYY-MM-DD>-<slug>.md
```

Заполняй только реально применимые разделы. Пустые удаляй.

### Шаг 3 — Обнови state.md

В `../../product/docs/memory/state.md`:

- **Текущая шаг** — обнови на следующий шаг (например, «Готов к этапу БД и Auth» после деплоя)
- **Что сделано** — добавь главное (1-2 пункта про текущую сессию). Старые пункты не удаляй, но если раздел разрастается > 80 строк — переноси старые в `feature-registry.md` или просто удаляй (история всё равно в sessions/)
- **Активный бэклог** — убери выполненные задачи, добавь новые на следующее
- **Последние решения** — если был ADR в этой сессии, добавь строку (держи раздел до 5 свежих)
- **Доступы** — обнови если появились новые (новый сервер, новый сервис, новые credentials в .env)

Помни правило: **state.md ≤80 строк**. Длинные разделы — кандидаты на вынос.

### Шаг 4 — Обнови memory/INDEX.md

В таблицу «Журнал сессий» добавь строку (в начало — реверс-хронологически):

```
| YYYY-MM-DD | <Задача> | [<filename>](sessions/<filename>) |
```

Если в сессии создал ADR / finding — убедись, что строки в соответствующие таблицы тоже добавлены (в идеале — это сделал `feature-dev` промт в шаге 8, проверь что не пропущено).

### Шаг 5 — Обнови feature-registry.md (если нужно)

Если в сессии реализована новая фича — добавь строку в нужный раздел `../../product/docs/memory/feature-registry.md` (если файл существует — он появляется на этапе спек).

### Шаг 6 — Закоммить и запушить память (если git подключён)

Правило: **есть реально подключённый git — память сразу уезжает в репозиторий; нет git — просто остаётся на диске.** Проверь по факту, а не «правило запрещает коммит».

Из папки проекта проверь, что это git-репо с настроенным remote:

```bash
git rev-parse --is-inside-work-tree 2>/dev/null && git remote
```

- **Git подключён** (это git-репо и есть хотя бы один remote — после Урока 3 так и будет) — закоммить файлы памяти/документации этой сессии и запушь:

  ```bash
  git add ../../product/docs/memory/ ../../product/docs/memory/state.md   # подставь реальные пути файлов сессии
  git commit -m "memory: <YYYY-MM-DD> <slug> — закрытие сессии"
  git push
  ```

  Коммить только файлы памяти/документации, не код и не чужие незакоммиченные правки. Если push отклонён — `git pull --rebase` и повтори.

- **Git не подключён** (нет `.git` или нет remote — например, до Урока 3) — не коммить и не пушь, просто сообщи: «git ещё не подключён, зафиксировал только в памяти проекта; закоммитим, когда появится git».

### Шаг 7 — Сообщи результат пользователю

Кратко: какой файл создан, какие разделы state обновлены, закоммичена/запушена ли память (или git ещё не подключён), какие открытые вопросы остались.

---

## Платформенные нюансы

**Claude Code:** скилл `/save-session` запускает этот промт. Можно вызвать командой или просто описать «закрой сессию, сохрани прогресс».

**Codex / Cursor:** вызови этот промт явно — «выполни `prompts/save-session.md`, slug `<X>`, описание `<Y>`».

**Что важно для любого AI:** session-файл должен быть **компактным** (50-150 строк). Не переписывай в него весь diff кода — это уже есть в git. Цель — чтобы через месяц человек / AI прочитал файл и понял суть за минуту.
