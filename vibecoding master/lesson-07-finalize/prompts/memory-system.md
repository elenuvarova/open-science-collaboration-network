# Память проекта — объединённая система (файлы + движок)

Этот документ собирает в одном месте всё про память проекта: из чего она состоит, что у неё за преимущества и как сюда подключается опциональный движок `agentmemory`. Файловое ядро вы уже собрали в Шаге 5 урока. Движок добавляется поверх него и ничего в нём не ломает.

---

## Из чего состоит память

Память проекта работает в два слоя. Нижний слой обязательный, верхний — по желанию.

### Слой 1 — файловое ядро (обязательный)

Это то, что вы собрали в Шаге 5: набор markdown-файлов под `../../product/docs/memory/` плюс `state.md` и `project-context.md`. Вот его карта:

```
../../.claude/
├── state.md                  ← текущая фаза, бэклог, доступы
├── project-context.md        ← бренд, цели, роли, ограничения
└── memory/
    ├── INDEX.md              ← оглавление, читается при каждом старте сессии
    ├── decisions/ADR-*.md    ← архитектурные решения, по одному на файл
    ├── findings/F-*.md       ← неочевидные находки
    ├── sessions/*.md         ← журнал работы по сессиям
    └── feature-registry.md   ← что уже реализовано
```

Это ядро лежит в git, читается глазами и правится руками. Вы видите каждую запись, проверяете её на ревью и откатываете через `git revert`, если что-то записалось не так. Решения вида «выбрали Prisma, а Drizzle отвергли вот почему» живут именно здесь, потому что их нужно формулировать точно и хранить долго.

### Слой 2 — движок `agentmemory` (опциональный)

`agentmemory` — это плагин, который сам записывает ход работы из ваших сессий и потом умеет находить нужные куски по смыслу, а не по точному совпадению слов. Он хранит данные в локальной базе SQLite на вашем компьютере (по умолчанию ничего в облако не уходит). Перед сохранением вырезает секреты и ключи, поддерживает изоляцию по проектам.

Движок берёт на себя рутину, которую вручную вести скучно: запоминать, что обсуждалось в прошлой сессии, и подтягивать это обратно, когда AI снова касается той же темы. За счёт этого AI реже просит вас заново объяснять контекст проекта.

Репозиторий: https://github.com/rohitg00/agentmemory (Apache-2.0).

## Какое преимущество откуда

Каждый слой закрывает свою часть. Они не дублируют друг друга.

| Преимущество | Даёт файловое ядро | Даёт движок agentmemory |
|---|---|---|
| Архитектурные решения «почему X, а не Y» хранятся точно и долго | ✅ `decisions/ADR-*.md` | — (авто-захват для этого слишком шумный) |
| Запись видна глазами, проверяется на ревью, откатывается через git | ✅ | — (база SQLite непрозрачна) |
| Журнал сессий ведётся сам, без ручного `/save-session` каждый раз | частично (через `/save-session`) | ✅ авто-захват |
| Поиск по памяти по смыслу запроса, а не по точным словам | частично (`/memory-search` по INDEX) | ✅ семантический retrieval |
| Меньше повторных объяснений контекста, экономия токенов | — | ✅ заявлено ~92% экономии токенов на повторном контексте |
| Реестр того, что реализовано, как опора перед новой задачей | ✅ `feature-registry.md` | — |

Если коротко: ядро отвечает за то, что должно храниться точно и проверяться человеком, движок — за рутинный захват и умный поиск.

## Как слои работают вместе

1. **На старте сессии** AI по-прежнему читает `state.md` и `memory/INDEX.md` — это дёшево и даёт точную картину закрытых решений. Это поведение из Шага 5 остаётся.
2. **По ходу работы** движок сам записывает, что происходило, в свою базу. Параллельно важные решения вы фиксируете в `decisions/` как ADR — руками, потому что их формулировка должна быть точной.
3. **Когда AI снова касается старой темы**, движок находит относящиеся к ней куски прошлых сессий по смыслу и подаёт их в контекст. Вам не нужно пересказывать, что вы решали неделю назад.
4. **Источник правды** при расхождении — файловое ядро. ADR в `decisions/` главнее, чем то, что движок выудил из истории, потому что ADR прошёл ваше ревью.

## Честные оговорки

Прежде чем ставить, держите в голове три вещи:

- **Это не «вечная память».** Движок подтягивает релевантные куски через поиск по смыслу с точностью около 95% по бенчмаркам авторов. Иногда нужный фрагмент не попадёт в выдачу. Поэтому решения, которые нельзя терять, всё равно держите в `decisions/`.
- **Установка не в один клик.** Нужен Node версии 20 и выше, запущенный фоновый сервис движка (по умолчанию на порту 3113) и бинарь `iii-engine` либо Docker. Это разворачивается один раз, но это не «нажал кнопку».
- **Версия молодая (0.9.x).** Проект активно развивается, API может меняться. Ставьте, если готовы разбираться, когда что-то отвалится. На обязательной части курса (Уроки 0–6) движок не нужен: файлового ядра достаточно.

## Установка движка (опционально)

Шаги для Claude Code. Для Codex и Cursor отличается только последний блок — смотрите README проекта по ссылке выше.

1. Проверьте, что стоит Node 20+:

   ```bash
   node -v
   ```

2. Запустите сервис движка в отдельном окне терминала (он должен работать, пока вы пользуетесь памятью):

   ```bash
   npx @agentmemory/agentmemory
   ```

3. В Claude Code подключите маркетплейс плагина и поставьте его:

   ```
   /plugin marketplace add rohitg00/agentmemory
   /plugin install agentmemory
   ```

4. Проверьте, что секреты не утекают в базу: откройте просмотрщик памяти (он поднимается на порту 3113) и убедитесь, что в записях нет ключей и токенов из `.env`. Движок вырезает их сам, но проверка перед первым реальным проектом не повредит.

## Когда стоит подключать, а когда нет

**Стоит**, если проект тянется месяцами, сессий накопилось много, и вы устали пересказывать AI одно и то же.

**Не стоит** на учебном проекте курса и на коротких задачах: файлового ядра хватает, а лишний фоновый сервис только усложняет setup. Сначала доведите до автоматизма работу с `decisions/`, `findings/` и `/save-session` — это база, на которую движок ложится сверху.
