# BDD тест-кейсы на критичные пути

> **Цель:** в `../../product/docs/test-cases.md` лежат 3-5 BDD-сценариев на критичные пути сервиса (auth, IDOR, главный флоу). Сценарии проходимы вручную в браузере, а на финальном этапе превращаются в автотесты.

## Что такое BDD

**BDD (Behavior-Driven Development)** — описание ожидаемого поведения продукта на почти обычном языке, в формате **Дано / Когда / Тогда** (Given / When / Then):

- **Дано** — предусловие (в каком состоянии система и пользователь до действия);
- **Когда** — действие пользователя (клик, отправка формы, запрос к API);
- **Тогда** — что должно произойти (видимый результат + побочные эффекты: запись в БД, redirect, email).

Почему именно так: один и тот же сценарий читается человеком, проходится руками в браузере и превращается в автотест без переписывания. И он **black-box** — описывает поведение снаружи (через UI/API), а не внутренние функции, поэтому код можно переписать, а тест-кейс останется валидным. Это и есть защита от регрессий: меняем реализацию — сценарии ловят, если поведение разъехалось.

## Промт

```
Создай ../../product/docs/test-cases.md с 3-5 сценариями на критичные пути сервиса.

ФОРМАТ КАЖДОГО СЦЕНАРИЯ:

## Сценарий N: <Название>

- **Дано:** <предусловие>
- **Когда:** <действие пользователя>
- **Тогда:** <ожидаемый результат 1>
- **Тогда:** <ожидаемый результат 2>
- **Тогда:** <side effect — email, audit log, redirect, и т.д.>

ОБЯЗАТЕЛЬНЫЙ МИНИМУМ:

## Сценарий 1: Регистрация и первый вход

- **Дано:** пользователь не зарегистрирован
- **Когда:** заполняет форму регистрации с валидным email и паролем ≥ 8 символов
- **Тогда:** создаётся User в БД с hashedPassword (не plaintext)
- **Тогда:** пользователь редиректится на /dashboard
- **Тогда:** cookie сессии установлено: HttpOnly + Secure (на проде) + SameSite=Lax
- **Тогда:** в Header виден avatar / имя пользователя

## Сценарий 2: Логин с неверным паролем — единый ответ

- **Дано:** пользователь зарегистрирован
- **Когда:** пытается войти с неверным паролем
- **Тогда:** возвращается ошибка «Неверный email или пароль» (одинаковая и для
  несуществующего email — защита от user-enumeration)
- **Тогда:** время ответа примерно одинаковое для обоих случаев
- **Тогда:** после 5 неудачных попыток с одного IP — 429 Too many requests
  (rate limit с этапа деплоя на /api/auth/*)

## Сценарий 3: IDOR закрыт

- **Дано:** два авторизованных пользователя A и B; у каждого есть свой <ресурс>
- **Когда:** A пытается открыть /<ресурс>/<id-B> по URL
- **Тогда:** 404 (не данные B). Не «Forbidden» — это утечка информации
- **Когда:** A пытается DELETE /api/<ресурс>/<id-B>
- **Тогда:** 404 / 403, ресурс B остаётся в БД

## Сценарий 4: Защита роутов

- **Дано:** пользователь не авторизован
- **Когда:** пытается открыть /dashboard напрямую по URL
- **Тогда:** редирект на /login
- **Когда:** успешно логинится
- **Тогда:** редирект на /dashboard (а не на главную или /login)

## Сценарий 5: <Главный флоу продукта по PRD>

- (по основной работе пользователя из PRD — пример: «Создание задачи»)
- **Дано:** пользователь залогинен, на /dashboard
- **Когда:** нажимает «Создать», заполняет форму, отправляет
- **Тогда:** запись создаётся в БД с правильным userId
- **Тогда:** в списке появляется новая запись с ожидаемыми полями
- **Тогда:** показывается toast «Создано» (или из спеки экрана)
- **Тогда:** при перезагрузке страницы запись видна (сохранилась в БД)

(Адаптируй сценарий 5 под СВОЙ продукт. Если у тебя e-commerce — сценарий «положить
в корзину и оформить заказ»; если трекер привычек — «отметить выполнение».)

## Сценарий 6 (опц): Постоянная обвязка и быстрая навигация

- **Дано:** залогиненный пользователь на любом внутреннем экране (есть меню/шапка)
- **Когда:** переключается между 2-3 разделами через меню (ссылки `<Link>`)
- **Тогда:** меню/шапка не мигают и не перезагружаются — меняется только контент
  (обвязка живёт в `(app)/layout.tsx` и переживает навигацию — заложено в Уроке 2)
- **Тогда:** в DevTools → Network при переходе по `<Link>` нет запроса документа
  целиком (нет нового `document`) — это мягкая навигация, а не полная перезагрузка
- **Тогда:** активный пункт меню подсвечен по текущему URL

(Защита от регрессии: при доработках легко случайно положить меню внутрь страницы
или заменить `<Link>` на `<a href>` — тогда навигация снова станет «тяжёлой». Этот
сценарий это ловит.)

ВАЖНО — black-box подход:

Тест-кейс описывает поведение через UI / API endpoint, НЕ через внутренние функции.
Это гарантирует, что код можно полностью переписать — тест-кейс не сломается.

❌ Тест-кейс «функция createTask должна вызвать prisma.task.create» — это white-box,
   привязан к реализации
✅ Тест-кейс «после клика на «Создать» в БД появилась запись и она видна на /dashboard»

ПРОГОН СЕЙЧАС ВРУЧНУЮ:

После создания ../../product/docs/test-cases.md — пройди по каждому сценарию вручную в браузере.
Делай отметки в файле:

- ✅ Прошёл — описанное поведение работает
- 🟡 Частично — что-то отличается, но не критично
- 🔴 Сломано — пофиксить

Если 🔴 или 🟡 — это сигнал, что код расходится со спекой. Обсуди со мной — что
правильно, spec или код, и поправь нужное.

СНАЧАЛА — ТЕКСТ И РУЧНОЙ ПРОГОН.

На этом шаге собираем текстовые сценарии и проходим их руками. Автотесты — следующим
блоком ниже (на финальном этапе курса), когда сценарии уже устаканились.

ПОКАЖИ МНЕ:
- Финальный ../../product/docs/test-cases.md (все 5 сценариев)
- Результаты прогонов: ✅/🟡/🔴 на каждом
- Если были 🟡 или 🔴 — что починили
```

## Автоматизация защиты от регрессий (финальный этап)

Когда сценарии устаканились — превращаем их в **автотесты**, которые гоняются сами и ловят регрессии до прода. Цель: вся защита «зашита» в проект, а не держится на ручном прогоне.

Два слоя автотестов под наши BDD-сценарии:

- **e2e (Playwright)** — главные пользовательские пути через реальный браузер (регистрация, логин, главный флоу, защита роутов). Один e2e-тест ≈ один BDD-сценарий: Дано — подготовка состояния, Когда — действия в браузере, Тогда — проверки на странице и в БД.
- **Интеграционные (Vitest + supertest / route handlers)** — серверная логика и API без браузера: IDOR (A открывает ресурс B → 404), user-enumeration (единый ответ + примерно равное время), rate limit (429 после N попыток), валидация. Быстрее e2e, ловят защиту авторизации точечно.

```
Автоматизируй BDD-сценарии из ../../product/docs/test-cases.md — финальный этап,
защита от регрессий зашивается в проект. Стек — Next.js (App Router), Playwright
для e2e, Vitest для интеграционных. Источник истины — test-cases.md (каждый
автотест соответствует сценарию по номеру и названию).

1. Поставь и настрой Playwright (`npm init playwright@latest`) и Vitest. Конфиги в
   ../../product/ . Тестовая БД отдельная (НЕ боевая): подними тестовую базу или
   schema, прогоняй миграции на ней, чисти между тестами. Боевую базу не трогаем.

2. e2e (../../product/e2e/*.spec.ts) — по сценариям главных путей: регистрация и
   вход, защита роутов (гость на /app → /login), главный флоу продукта. Проверяй
   видимый результат И побочные эффекты (запись в БД, redirect, cookie HttpOnly).

3. Интеграционные (../../product/tests/*.test.ts) — на безопасность авторизации:
   IDOR (пользователь A → ресурс B → 404, ресурс B цел), user-enumeration (единый
   ответ для неверного пароля и несуществующего email), rate limit (429 после
   лимита на /api/auth/*), серверная валидация полей.

4. Скрипты в package.json: `test` (Vitest), `test:e2e` (Playwright), `test:all`.
   Детерминированные данные (фабрики/seed тестовой базы), не Math.random().

5. ГЕЙТ В ДВУХ ТОЧКАХ — чтобы тесты срабатывали ВСЕГДА (на push и на каждом
   деплое), а не по памяти:
   - pre-push хук (или CI, если есть GitHub Actions): гоняет `test:all` перед
     push/мержем; красные тесты блокируют отправку;
   - `deploy.sh` (из Урока 3): гоняет `test:all` перед переключением трафика;
     красные тесты останавливают выкат — непротестированный код не доедет до прода;
   - свяжи с уже существующими гейтами проекта (спека-гейт из Урока 3,
     security-precheck) — не дублируй, добавь запуск тестов рядом.

6. Зафиксируй: ADR-XXX-test-automation (что покрыли, чем), раздел «Тесты» в
   spec.md/AGENTS.md (как запускать, где тестовая БД), строка в memory/INDEX.md.

ПОКАЖИ МНЕ:
- Зелёный прогон `test:all` локально
- Что красный тест блокирует push И останавливает `deploy.sh` (продемонстрируй на заведомо ломающей правке)
- Какие BDD-сценарии покрыты e2e, какие — интеграцией, и почему
```

> Если проект совсем маленький и пользователей пока нет — можно ограничиться e2e на 2-3 главных пути и интеграционным тестом на IDOR/auth. Но хотя бы эти автотесты в гейте лучше иметь: они дешевле, чем чинить прод после регрессии.

## Edge cases

- Если в Сценарии 5 главный флоу занимает много шагов — разбей на 2-3 сценария (каждый одним фокусом)
- Если у проекта нет auth (полностью публичный сервис) — Сценарии 1-4 не применимы; замени на сценарии главного флоу
- Если ресурс публичный (share by link) — IDOR-сценарий проверяет токен, не userId
