# Инструкция: Правила проекта в `../../product/docs/rules/`

## Предусловия

Перед запуском проверь:

- Папки `.claude/` и `../../product/docs/rules/` существуют.
- `../../product/AGENTS.md` существует с разделом «Правила (читать по триггеру)».

Если папок нет — скажи: «Сначала пройди промт `04-init-project.md` — нужен структуру проекта». Не продолжай.

## Задача

Создай в `../../product/docs/rules/` шесть правил проекта. Каждое правило — отдельный файл. `../../product/AGENTS.md` в корне проекта должен содержать только ссылки на эти файлы в таблице «Правила (читать по триггеру)». НЕ копируй содержимое правил в `../../product/AGENTS.md` — он остаётся компактным индексом.

Если в проекте уже есть некоторые правила (например, скопированные из другого проекта) — интегрируй, не перезаписывай.

## Правило 1 — `../../product/docs/rules/ui-components-first.md`

Содержимое:

```markdown
# UI Components First — всё через компоненты, без хардкода

## Принцип
Любой UI собирается ИЗ components/ui/ (или src/shared/ui/ после сборки UI-кита). Хардкод
классов в страницах, фичах, виджетах — запрещён. Меняется визуал → меняется компонент,
не место использования.

## Жёсткие правила

1. Все базовые элементы — компоненты в components/ui/. Минимум: Button, Card, Input,
   Textarea, Select, Checkbox, Radio, Switch, Badge, Avatar, Modal, Dialog, Tabs, Tooltip,
   Toast, Skeleton, EmptyState, ErrorState.

2. Состояния (hover, focus, disabled, loading) — ВНУТРИ компонента, не на местах
   использования.

3. Темизация через token refs из docs/DESIGN.md:
   ✅ bg-primary, text-foreground, rounded-md
   🔴 bg-[#1A1C1E], text-white, rounded-[6px]

   Если нужного токена нет — сначала добавь токен в DESIGN.md, потом используй.

4. Хардкод классов в страницах / фичах / виджетах — запрещён.
   Если нужного варианта нет — добавь variant в существующий компонент.

5. Композиция через Slot/asChild для семантики (например, Button как ссылка) —
   не плоди отдельные LinkButton, AnchorButton.

## После генерации UI — самостоятельная проверка

После каждой большой UI-генерации — самостоятельно прогоняй:
  grep -rE '#[0-9a-fA-F]{3,8}|\[\d+px\]' components/ui/ src/app src/pages src/widgets src/features

Если что-то нашлось — переделать через токены или добавить вариант.

## Hook-страховка
В `.claude/hooks/post-tool-use-edit.sh` (настраивается на этапе защиты от регрессий) — автоматический
grep после каждой правки UI-файла. Это второй слой защиты.
```

## Правило 2 — `../../product/docs/rules/design-system-first.md`

Содержимое:

```markdown
# Design System First — DESIGN.md как контракт

## Принцип
docs/DESIGN.md — единый источник правды для токенов. Все цвета, шрифты, отступы,
скругления — оттуда.

## Правила

1. Любой UI следует docs/DESIGN.md.

2. Если нужного токена нет — добавь в DESIGN.md, прогон lint, потом используй.

3. Не использовать шрифты / цвета вне контракта.

4. При изменении DESIGN.md — обязательный прогон перед коммитом:
   npx @google/design.md lint docs/DESIGN.md
   (errors блокируют коммит; warnings — разобрать или зафиксировать причину)

5. Изменения токенов фиксируются в коммите вместе с зависимыми UI-правками
   (если меняется colors.primary — все компоненты, где он использован,
   автоматически обновляются через Tailwind, ничего трогать не надо)
```

## Правило 3 — `../../product/docs/rules/spec-first.md`

Содержимое:

```markdown
# Spec First — спека экрана как источник правды

## Принцип
Прежде чем менять экран или его поведение, сначала прочитай спеку этого экрана.
Спека ведёт код, а не наоборот.

## Правила

1. Перед правкой экрана / компонента / поведения AI читает:
   - docs/spec.md (общая логика, модель данных, доступы);
   - docs/screens/<экран>.md (состояния, элементы, условия видимости, тексты, валидация);
   - docs/screens/_global.md (сквозные правила: auth guard, ошибки сети, успехи, loading,
     защита от двойного submit, формат дат, empty states) — соблюдать на любом экране.

2. Меняется поведение или дизайн экрана → спека правится в ТОМ ЖЕ коммите, что и код
   (docs/screens/<экран>.md, при необходимости docs/spec.md). Это же стережёт спека-гейт.

3. Поведение не меняется (рефактор, стиль) → не нарушай описанное в спеке: код остаётся
   в рамках зафиксированного.

4. Спеки нет или она поверхностна для нужного экрана → сначала допиши спеку, потом код.

5. Расходится спека с кодом → почини ОДНУ сторону до совпадения. Спека = источник правды.
```

```markdown
# Verification — проверки перед коммитом

## Принцип
Никогда не заявляй "готово" без прохождения проверок.

## Чек-лист (для UI-задач — минимум 1-6, для бэкенд — 1-5 + spec sync)

   npm run build
   (нет ошибок компиляции)

2. Типы:
   npx tsc --noEmit
   (нет TS-ошибок)

3. Lint:
   npm run lint
   (если настроен)

4. Хардкод стилей в UI-файлах:
   grep -rE '#[0-9a-fA-F]{3,8}|\[\d+px\]' src/app src/pages src/widgets src/features components/ui

5. Console / debugger / TODO:
   grep -rE 'console\.(log|debug)|debugger|TODO|FIXME' src/

6. Spec sync (для UI-фич):
   - docs/screens/<screen>.md обновлён под новое поведение?
   - docs/test-cases.md обновлён, если изменилась логика?

7. Public API через index.ts:
   - Импорты не обращаются к @/<slice>/ui/X напрямую — только через @/<slice>
```

## Правило 5 — `../../product/docs/rules/commits.md`

Содержимое:

```markdown
# Commits — авто-коммит после каждого логического шага

## Принцип
Каждая завершённая фича, багфикс, законченная доработка или оформленный документ →
**ОБЯЗАТЕЛЬНО сразу делай commit, не дожидаясь отдельной команды.** Не накапливай
изменения и не спрашивай «закоммитить?». Коммит — часть выполнения шага, а не отдельное действие.

## Правила
1. После каждого завершённого шага: `git add <конкретные файлы шага>` + `git commit` с
   осмысленным сообщением — автоматически, сразу.
2. Атомарность: одна фича / один фикс = один коммит. Разные изменения не сваливать в кучу.
3. НЕ `git add -A` вслепую — добавляй только файлы этого шага (не утащить `.env`, дампы, мусор).
4. Формат сообщения (на русском): `проект (тип): описание`
   - `проект` — короткое имя продукта (одно и то же во всех коммитах);
   - `тип` — один из: `feat`, `fix`, `refactor`, `docs`, `chore`;
   - описание — что сделано.
   Примеры: `myapp (feat): форма входа с валидацией email`, `myapp (fix): кнопка не активировалась при пустом поле`.
   Документация / спека / тесты — в ТОМ ЖЕ коммите, что и код (см. spec-first, verification).
5. **Push — зависит от автодеплоя.**
   - Если push завязан на автодеплой (push в `main` → выкат в прод) — перед каждым push СПРОСИ
     разрешение (случайный push не должен уехать в прод).
   - Если автодеплоя на push нет (деплой по команде `./deploy.sh`) — push безопасен: пушь сразу
     после коммита (или предложи это сделать).
   - Shared-репозиторий — `git pull --rebase` перед push. Нет remote/git — просто коммить локально.
```
