# Промт 02: Спеки экранов в `../../product/docs/screens/` — финальная сверка

> **Цель:** убедиться, что на каждый ключевой экран есть полный spec в `../../product/docs/screens/<screen>.md` (состояния, элементы, сообщения, валидация), и довести до полноты. Поэкранные файлы уже заведены раньше (логика + визуал) — здесь проверяем и дополняем, а не пересоздаём.

---

## Промт

```
Проверь и доведи до полноты ../../product/docs/screens/. Поэкранные spec'ы уже
заведены в Уроках 1–2 (логика + раздел `## Визуал`) — НЕ пересоздавай: проверь
полноту на ключевых экранах, допиши недостающее, создай файл только если его нет.
Сверь каждый с кодом — расходится, чини одну сторону (спека = источник правды).

Минимум — на эти экраны:
- ../../product/docs/screens/auth.md (логин + регистрация)
- ../../product/docs/screens/dashboard.md
- ../../product/docs/screens/<основной-флоу>.md (главный сценарий из PRD)
- ../../product/docs/screens/settings.md

Делай ПО ОДНОМУ. На каждый экран — отдельный проход с моими подтверждениями.

ФОРМАТ ../../product/docs/screens/<screen>.md (строго):

# Экран: <Название>

**URL:** `/path`
**Доступ:** роль = ... | все авторизованные | гость

---

## Состояния экрана

| Состояние | Условие |
|---|---|
| Загрузка | данные ещё не получены |
| Пустой | список пуст |
| Заполненный | есть ≥ 1 запись |
| Ошибка | запрос к API вернул ошибку |

## Элементы интерфейса

### <Название элемента, например "Кнопка Создать">

- **Видим:** условие = значение ИЛИ другое условие
- **Скрыт:** роль ≠ администратор
- **Активен:** статус ≠ завершён
- **Неактивен:** статус = завершён ИЛИ нет прав
- **При действии:** что происходит — куда ведёт, какой запрос, какое сообщение

(Используй символы: =, ≠, >, <, ≥, ≤, ИЛИ, И, НЕ, ∈, ∉)

### <Следующий элемент>
...

## Сообщения

| Ситуация | Тип | Текст сообщения |
|---|---|---|
| Успешное сохранение | success | «Изменения сохранены» |
| Нет прав | error | «Недостаточно прав для этого действия» |
| Поле не заполнено | error | «Заполните поле <название>» |
| Сеть недоступна | error | «Нет соединения. Попробуйте позже» |

| Триггер | Канал | Получатель | Текст / Действие |
|---|---|---|---|

## Валидация полей

| Поле | Правило | Сообщение об ошибке |
|---|---|---|
| Email | формат email, уникальный | «Введите корректный email» |
| Пароль | ≥ 8 символов | «Минимум 8 символов» |
| Название | не пустое, ≤ 100 символов | «Введите название» |

---

ЧТОБЫ НАПИСАТЬ SPEC — иди по реальному коду ../../product/development/apps/app/src/pages/<page>/. Видишь компоненты —
описываешь их поведение. Если поведение неочевидное (например, кнопка скрывается
по сложному условию) — спроси меня одной строкой и опиши.

ВАЖНО — spec должен описывать НАМЕРЕНИЕ, а не текущий код. Если в коде сейчас
кнопка просто всегда показана, но логически она должна скрываться у гостя —
пиши в spec логически правильное поведение. Тогда при следующем прогоне через
тест-кейсы (Промт 04) выяснится расхождение и починим.

ПОСЛЕ КАЖДОГО SPEC:

1. Покажи мне результат

2. Жди подтверждения / правок

3. Переходи к следующему

ПОКАЖИ МНЕ финальный ../../product/docs/screens/dashboard.md как пример законченной спеки.
```

## Edge cases

- Если у экрана есть несколько режимов (например, /settings — табы Профиль / Безопасность / Уведомления) — каждая вкладка отдельным разделом внутри файла или отдельный spec, выбирай по объёму
- Если правил много (15+ элементов) — разбей на разделы по функциональным группам, чтобы spec оставался читаемым
- Сообщения — это **именно тексты**, не описания. «Успех» — плохо, «Изменения сохранены» — хорошо
